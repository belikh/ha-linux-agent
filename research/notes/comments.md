summary: 'PRIMARY SOURCE: full 22-comment thread of home-assistant/core issue #135266
  via GitHub API. Resolution: the user''s MQTT broker had an allowed-maximum-queued-messages
  limit that was too low — at HA startup, HA subscribes to ''#'' and the broker replays
  ~5374 entities worth of retained discovery/state messages; the per-client queue
  overflowed and the broker SILENTLY DROPPED retained messages (56 of 112 topics for
  the affected device arrived empty). Raising the broker''s max_queued_messages ''seems
  to be the instant cure''. Diagnostic trail: HA debug logs showed ''Found new component''
  for other platforms but not the missing sensors; a manual listen on ''#'' in HA
  MQTT settings made all messages arrive instantly (the listen triggered a fresh subscription
  which re-queued under the new session); MQTT Explorer on the same broker showed
  messages present the whole time — the messages were on the broker but not delivered
  to HA. Maintainer jbouwh''s framing: ''Seems like an issue with availability of
  the sensors. If the config is retained, the sensors might be configured if their
  config still remains at the MQTT broker'' and noted the diagnostics showed empty
  message lists. Key retained line from debug log: ''Subscribing with mid: 11 to topics
  with qos: [(''#'', 0)]''. LOAD-BEARING for jupiterOS fleet design: at fleet scale,
  HA-restart retained-message replay storms can silently overflow broker queue limits
  (Mosquitto max_queued_messages default is 1000) — a per-client drop that looks exactly
  like ''my agent is flaky''. Fleet checklists must include broker-side queue limits,
  not just agent-side retain discipline.'
