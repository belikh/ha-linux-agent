# Two Located Bugs and a Fleet: Fixing ha-linux-agent for Every Host in jupiterOS

**The answer first.** "never reliable" is not a vague aura of sloppiness — it is two located bugs in one 198-line file, amplified by three default-shaped traps. The symptom was observed live: this run's fleet audit on 2 September 2026 found all four TCxWave kiosks reading UNAVAILABLE on callisto's Home Assistant instance — the complaint, dated, not a standing state. The agent subscribes to its command topics exactly once in a fire-and-forget setup task (`agent.rs:134-138`) and swallows every connection acknowledgement in its poll loop (`Ok(_) => {}` at `agent.rs:190`): after the first broker restart or network blip the client reconnects forever but never re-establishes subscriptions, so every agent goes permanently deaf [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]]. The mirror-image bug publishes retained availability `online` exactly once (`agent.rs:139-144`), so every host reads dead in HA while its telemetry still flows. The cure — a ConnAck-driven supervisor that re-subscribes, re-asserts availability, and republishes discovery on every connect — ships on the pinned rumqttc 0.24.0 with zero dependency churn, and is the same disease the incumbent Windows agent fixed in a patch release [[releases-hass-agenthassagent-github]]. The order is non-negotiable: fix reliability first, deploy fleet-wide second (one system service per host, a role-driven NixOS module replacing the kiosk-only wiring), add features third — and adoption is answered at full strength in §4, where it fails on packaging and expressibility.

## 1. Current State: A Verified Reliability Audit

ha-linux-agent is a Rust daemon bridging Linux host state to Home Assistant: sensors in, controls out, commands back, all over MQTT. This audit reads the repository itself — measured exit codes, file:line reads, the fleet's own NixOS configurations — because ground truth here means observed behaviour and verbatim source, not recollection. The workspace is twelve crates, eleven commits, 43 files — audited directly at HEAD commit 8369f44 by this run in September 2026 — with a 198-line `Agent::run()` at its centre and backend-hardware, core/config, and backend-gamescope at the top of the reference graph [[repo-map-ha-linux-agent]]. The run's live fleet audit on 2 September 2026 found the four kiosks' entities reading unavailable on callisto's HA.

**The reliability defects are located, not diffuse**:

| Defect | Location | Failure mode |
|---|---|---|
| Deafness after reconnect | `agent.rs:134-138` subscribe-once; `agent.rs:190` ConnAck swallowed | Reconnects but never re-subscribes; commands never arrive again |
| Availability stuck offline | `agent.rs:139-144` online once; retained offline will at `agent.rs:55-60` | Host reads dead in HA while telemetry flows |
| No birth republish | absent | HA restart strands entities until manual re-send |
| Unbounded stale queue | `AsyncClient::new(opts, 64)` at `agent.rs:62` | Stale state replays as a burst on reconnect |
| Hung-backend starvation | `backend-syncthing/src/lib.rs:75,98` no-timeout HTTP; sequential polls at `agent.rs:154-157` | One hung daemon freezes every sensor while availability says online |
| No graceful shutdown | zero signal-handling across `crates/` | A clean DISCONNECT silently discards the will; availability sticks online |
| Crash stays dead | `ha-agent.nix:104-106` unitConfig `ConditionUser` only; NixOS user services default `Restart=no` | A panicked agent stays dead until the next reboot — no telemetry at all, the third leg of never reliable |
| Session/broker defaults unpaired | rumqttc defaults; callisto `mqtt.nix` sets neither `max_queued_messages` nor `persistence` | Clean sessions plus an amnesiac broker compound the deafness |

**The privilege workaround is broken, not just ugly.** `ha-agent.nix:117-124` ships a root-owned oneshot chmodding backlight and cpufreq sysfs nodes (sysfs being the kernel's pseudo-file interface under `/sys`) to 0664, behind a comment at line 112 claiming "io is in the groups that own the nodes (video for backlight...)". The comment is false: sysfs attributes default to `root:root 0644`, so 0664 grants group-write to group *root*, and io's only group anywhere is `wheel` (`common.nix:139` — no host adds io to `video`). The agent's brightness, governor, and EPP (energy-performance-preference) writes therefore fail EACCES today, logged only as a `warn!` in `write_sys_file` (`backend-hardware/src/lib.rs:108-111`), invisible at the HA layer — on kiosks running one-second polling against a control surface that silently does not work.

**The backends the fleet never runs.** The audit closes on the three crates no host exercises:

- **backend-kde** hard-fails without a session bus (`Connection::session().await?` at `backend-kde/src/lib.rs:41`) and has zero fleet consumers because no jupiterOS host runs Plasma — greps for plasma/kde across hosts and modules return nothing, and the hard-fail is the stated boundary condition for ever hosting a desktop class (it must adopt the generic backend's warn-and-continue degradation first).
- **backend-gamescope**'s only fleet consumer is callisto's arcade session, with kiosks reaching gamescope via the shared dashboard-gaming modeSpecs.
- **backend-lutris** ships behind the `jupiter.gaming.console` appCatalog but no host configuration exercises its launch-only buttons, its JSON field names hedged unverified — lutris among the backends the repo itself flags "Unverified in a live environment" (alongside zfs and syncthing) [[repo-map-ha-linux-agent]].

**The quality gates are absent, not merely failing.** Eight test functions exist — three in `discovery.rs`, five in `backend-launcher`, all pure shape guards, zero on any hardware, D-Bus (Linux's inter-process message bus), or MQTT path — but the flake's (the repo's Nix build definition) checks hold only a build and clippy (Rust's linter) with `--deny warnings`: no test hook exists, so zero of the eight ever run in any gate. Clippy is red now (`unnecessary_map_or` at `backend-hardware/src/lib.rs:117`), so the observed exit codes are 0 (build), 0 (test — nothing runs), 101 (clippy): the check cannot go green before a one-line fix. There is no `.github/`; there is no CI at all. A dead `tls` knob sits at `config.rs:88`; zfs, syncthing, and lutris are flagged by the repo itself as "Unverified in a live environment" [[repo-map-ha-linux-agent]]; and the audit's direct read of `backend-hardware/src/lib.rs:74-93` shows the governor/EPP select options enumerated from sysfs, with hardcoded lists only as fallback when the sysfs read fails.

**The fleet coverage fact.** The agent runs on four of seven hosts — the TCxWave kiosks (amalthea, adrastea, metis, thebe) — while callisto deliberately opts out (its arcade-console config strips the wiring), europa runs nothing despite the zfs/syncthing/headscale backends existing for exactly that host, and pallene — a ZFS-less Kamatera VPS whose own header reads "No ZFS, no impermanence, no sops-nix, no disko, no ha-linux-agent" — hard-opts-out. "Every host" is an ambition the fleet's configuration contradicts.

**The defect distribution is the strategic fact:** failures cluster in the lifecycle core every host class shares — `agent.rs` and config plumbing — while the per-backend surfaces are small, self-contained crates of 100–330 lines behind two traits. A flat audit reads as *prototype, replace it*; the precise reading is that fixing `agent.rs` lifts kiosks, servers, and future desktop hosts simultaneously, which no incumbent substitution delivers.

## 2. The MQTT Lifecycle Problem: Why It Is Never Reliable

MQTT (a lightweight publish/subscribe protocol) is the agent's nervous system: HA learns about entities through discovery messages, tracks host liveness through an availability topic, and sends commands over subscribed topics. Two properties make or break it. A broker (the MQTT server — mosquitto, on callisto) forgets clean-session clients on every reconnect, a clean session being the default mode in which the broker discards a client's stored state, subscriptions included. And HA marks an entity unavailable until a payload arrives on its availability topic — fresh state alone never flips it back [[mqtt-home-assistant]]. The agent drives its lifecycle from the wrong place entirely, and that one error produces every symptom the fleet has felt.

### A. The library contract that decides everything

rumqttc's poll loop reconnects unconditionally — "Continuing to poll will reconnect to the broker if there is a disconnection" — and advertises "Automatic reconnections by just continuing the eventloop.poll()/connection.iter() loop", re-subscription conspicuously absent [[eventloop-in-rumqttc-rust]] [[rumqttc-rust]]. Reconnection is not re-subscription. Issue #250, open since February 2021 and still labelled in-pipeline, documents the footgun: after a clean-session reconnect, "I'm not seeing any data coming in from subscribed topics", because subscriptions live only in broker-side session state [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]]. The in-pipeline fix, PR #1052, is open, unreviewed, v5-scoped, and only emits a reconnect *signal* — its own caller pattern re-subscribes in application code, so subscription ownership stays with the application even if it merges [[rumqttc-emit-eventreconnect-on-successful-re-connack-closes-250-by-pbujanda1978]]. And the pinned version offers no alternative hook: 0.24.0's `Event` enum has exactly two variants — `Incoming` and `Outgoing`, no `Reconnect` — so `poll()` yielding `Packet::ConnAck` on every connect is the only reconnect signal the pinned version has, making the raw ConnAck match not a workaround but the mandatory design [[event-in-rumqttc-rust]]. 

Paho, the alternative, exposes rich reconnect callbacks but leaves re-subscription application-owned too, and drags a C toolchain onto every NixOS fleet build — default builds need CMake, a C compiler, and system OpenSSL, a foreign dependency chain in every host closure (whether nixpkgs' paho-c packaging is already clean is an unverified open question; the application-owned re-subscription point alone decides the client question) [[asyncclient-in-paho_mqttasync_client-rust]] [[github-eclipse-pahopahomqttrust-pahomqttrust-github]]. No single source announces that the supervisor must live in the application forever, but the rumqttc PR design (signal-only) and the Paho callback surface jointly imply exactly that. Waiting for upstream saves nothing; switching clients buys nothing.

### B. The two bugs, mechanically

rumqttc defaults to `clean_session=true`, keepalive 60 s, inflight 100 [[librs]], and callisto's mosquitto sets no `persistence`, so the default applies — "stored in memory only" — meaning every broker restart wipes all sessions fleet-wide [[mosquittoconf-man-page-eclipse-mosquitto]]. Combine that with subscribe-once and the swallowed ConnAck: the first mosquitto restart, HA restart with a broker drop, or network blip permanently deafens every agent. The poll task keeps publishing state — telemetry flows, dashboards look half-alive — but no command ever arrives again. Then the mirror image fires: the broker publishes the retained `offline` last will (LWT — the message a broker publishes when a client vanishes ungracefully) on the ungraceful disconnect, and the agent never re-publishes `online`, so the availability topic permanently reads `offline` while state flows normally [[what-is-mqtt-last-will-and-testament-lwt-mqtt-essentials-part-9]]. The community's step-by-step demonstration — publish state, sensor stays unavailable; publish availability, sensor appears — is the failure mode in miniature [[mqtt-discovery-availability-home-assistant-os-home-assistant-community]]. Users read the two together as the agent being broken, because it is.

### C. The HA-side contract, and the one contested broker question

HA is explicit: "A device or service that exposes the MQTT discovery should subscribe to the Birth message and use this as a trigger to send the discovery payload. To avoid high IO loads on the MQTT broker, adding some random delay in sending the discovery payload is recommended" — HA publishes `online` to `homeassistant/status` at startup, and discovered entities sit unavailable until a discovery message is processed [[mqtt-home-assistant]]. Retained discovery alone is necessary but not sufficient. Issue #135266 shows the mechanism at scale: at 5,374 entities the broker's per-client queue overflowed during HA's startup retained replay and silently dropped messages — 56 of 112 affected topics arrived empty while MQTT Explorer showed them present. The cure was "I have raised the allowed maximum number of queued messages on my broker" [[some-mqtt-devices-unavailable-after-ha-restart-issue-135266-home-assistantcore-g]] [[comments]]. The queue mechanics are per-client: mosquitto counts each client's queued messages against `max_queued_messages` (default 1000), and for a disconnected client the in-flight adjustment zeroes, freeing the full queue depth for offline replay [[databasec]]. The older #38661 shows the same stranded-entity class ending in manual delete-and-rediscover [[mqtt-sensors-unavailable-in-01140bx-others-stay-unknown-issue-38661-home-assista]].

Here the sources genuinely disagree with themselves, and the resolution is conjunctive: retain everything (config, state, availability — the Zigbee2MQTT/ESPHome posture), AND republish on birth and ConnAck with jitter, AND persist the broker. Retention without republish strands entities when replay drops; republish without retention strands them when the broker forgets [[mqtt-client-component-esphome-smart-home-made-simple]] [[device-availability-zigbee2mqtt]]. One calibration keeps the sizing honest: at the fleet's current per-host entity counts (tens, not thousands) the default 1000 never binds — the binding quantity in #135266 was HA's own `#`-wildcard client against broker-wide retained replay [[comments]] — so the broker work is cheap hygiene plus a `$SYS` confirmation check on `$SYS/broker/publish/messages/dropped` (not the never-published `$SYS/broker/mqtt/*` variants mosquitto 2.1.2 excludes) rather than urgent resizing [[documentation-on-sysbrokermqtt-topics-is-wrong-issue-3726-eclipse-mosquittomosqu]]. The load-bearing half is `persistence true`: broker restarts still wipe sessions, so the ConnAck re-subscribe is mandatory regardless of queue arithmetic.

### D. The aggravators, and the supervisor that fixes all of it

The request-channel capacity of 64 at `agent.rs:62` contradicts rumqttc's recommendation to set capacity 0 when managing pending state — during an outage, up to 64 stale messages queue and replay as a burst [[rumqttrumqttcsrceventlooprs-at-main-bytebeamiorumqtt-github]]. Worse is starvation: `backend-syncthing` builds its reqwest client with no timeout (reqwest has none by default), and `Agent::run` polls all backends sequentially in one task. One hung syncthing daemon freezes every sensor while availability still reads `online` — sensors that lie rather than sensors that vanish, the worst failure class a fleet can carry. The shutdown path is an accident, and the crash path is worse: the current user unit ships only `unitConfig ConditionUser` — NixOS user services default `Restart=no` — so a panicked agent stays dead until the next reboot, taking the host's telemetry with it; nothing restarts the process today. The graceful half works only by accident too: the broker discards the stored will on a graceful DISCONNECT, so SIGTERM *works* only because the process dies ungracefully and the TCP close fires the will — the day someone adds a clean shutdown without first publishing `offline`, availability sticks `online` forever. ESPHome solves exactly this with a `shutdown_message` distinct from the will [[mqtt-client-component-esphome-smart-home-made-simple]].

The supervisor is one structural change: drive the lifecycle from the ConnAck event. On every `ConnAck` — first connect or reconnect, either `session_present` — re-issue all command-topic subscribes (idempotent; subscribe-before-connect is safe because requests buffer in the bounded channel until post-ConnAck) and re-assert retained `online` [[rumqttrumqttcsrceventlooprs-at-main-bytebeamiorumqtt-github]]. Subscribe to `homeassistant/status` and republish all discovery on HA's birth with 0–30 s per-host jitter, after the production reference: Zigbee2MQTT applies `Math.random() * max_jitter` with a 30 s default, ×1.5/×3/×6/×12 backoff, retained QoS 1 (at-least-once delivery) availability, and dedup of consecutive identical states [[availabilityts]] [[device-availability-zigbee2mqtt]]. Channel capacity 0 with per-tick publish timeouts bounds staleness to one poll interval — and because all state lands on one retained topic per host, a fresh publish overwrites any stale payload: staleness self-heals by construction. Wrap every backend poll and command handler in `tokio::time::timeout`, dispatch commands via `tokio::spawn` with 5 s HTTP timeouts (rumqtt's rule: "Don't block this while iterating"), handle SIGTERM as retained `offline`, await, then `disconnect()` — shipped in the pinned 0.24.0 — and add `--decommission`: zero-length payloads published to every owned topic, HA's official removal semantic. 

The decommission design earns its detail because retained discovery configs survive HA restarts and resurrect removed entities (ESPHome ships clean-mqtt for exactly this problem, and v3.1.1 forecloses message expiry as the alternative cure): the topic list derives from the same descriptors used for discovery so the two can never drift, state and availability topics clear FIRST and config topics LAST (mirroring Homie's state-first ordering rule), and the mode also fires opportunistically — when the configured sensor/command set differs from the last published set, persisted in `/var/lib/ha-linux-agent/last-discovery.json`, the removed topics clear on next start. The unit hardening closes the crash leg: `Restart=on-failure` plus `WatchdogSec` via sd_notify — ESPHome's `reboot_timeout` analogue, rebooting the agent after 15 minutes without a healthy loop — so a panic costs one restart, not the host's telemetry until the next boot. Reconnect backoff runs 1→60 s with ±20 % jitter so a broker restart cannot synchronise seven hosts into a stampede.

Two boundary judgements carry conditions. **First**, `clean_session = true` (explicit, stable client id) against the persistent-session instinct: a persistent session's only unique deliverable here is broker-side queueing of QoS 1 commands for an offline agent, and the kiosks power off overnight — a week-old launcher toggle or reboot replaying as fresh on Monday boot, with no TTL in v3.1.1 (issue #211, open and stale since December 2020) and no payload timestamp to age it by, is a hazard no source states directly but the overnight-off pattern and rumqtt's documented lack of any pending-message TTL jointly imply [[rumqttc-reconnection-to-mqtt-broker-and-pending-messages-ttl-issue-211-bytebeami]]. Always-on servers lack the hazard and gain nothing from session state given ConnAck re-subscribe, so the design is unconditional. 

**Second**, a premise correction that strengthens the design: 0.24.0 is *not* v3.1.1-locked — `src/lib.rs:113` declares `pub mod v5;` with full property support inside the pinned version, and the module is not a stubbed half-implementation: its single `unimplemented!()` sits on request variants (PubComp/SubAck/UnsubAck/PingResp) the public client never sends — unreachable from agent code — so message and session expiry are a module switch away, a named future option rather than the reason for any workaround. The 0.25.1 upgrade was actually run — check, test, clippy all exit 0, zero code changes — and reverted, because it buys nothing the supervisor needs; the identical public API across the two versions is itself evidence the bump is cosmetic.

The precedent that makes this credible: the incumbent Windows companion shipped the identical bug class and fixed it in a patch release — HASS.Agent 2.1.1, "MQTT autodiscovery messages were not republished after connection was lost and recovered" (#230), alongside rename-triggered discovery-removal failures (#376, #388) and a sensor class stopping on a WMI restart (#205) [[releases-hass-agenthassagent-github]]. Reconnect-deafness is the generic companion-agent disease; this instance is diagnosed to the line and has a spec.

## 3. What a Proper Linux Agent Looks Like: The Comparison Set

A companion agent, in HA's vocabulary, is a per-host daemon that both reports (sensors) and obeys (controls) — the role the mobile apps play for phones and HASS.Agent for Windows. The 2026 Linux field divides into companion-class candidates (go-hass-agent, lnxlink, halinuxcompanion) and monitoring-class stacks (Glances, Telegraf, Netdata — eliminated next); the remaining alternatives, System Bridge (a WebSocket-API companion) and IoTuring (a thinner MQTT transport), are covered by the class arguments — System Bridge joins the native-API class and inherits exactly the halinuxcompanion concession (values stranded when a host goes offline, no LWT), IoTuring is MQTT-transport with a far thinner surface than lnxlink's ~50 modules [[lnxlink]]. Four axes set the bar, and the incumbents set them high.

**The sensor bar.** go-hass-agent (v14.15.1, 2026-08-09, packaged in nixpkgs — the NixOS package collection — for all 24 Linux platforms, ~monthly cosign-signed releases) sources its Linux surface from D-Bus (logind sessions, power state, screen lock, NetworkManager, XDG portal, UPower, MPRIS, fwupd), ProcFS (memory, disk, load, per-core CPU usage and frequency, uptime, kernel, CPU vulnerabilities), SysFS (disk I/O rates, hwmon), and Netlink (link states, rates) [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[go-hass-agent-mynixos]] [[releases-joshuargo-hass-agent-github]]. Its cadence is the depth evidence: v14.15.1 fixed a concurrent map-read data race in the CPU usage worker, v14.15.0 added NVIDIA and AMD GPU memory sensors, v14.10.3 fixed ddcutil backlight detection [[releases-joshuargo-hass-agent-github]]. lnxlink's ~50 modules — idle-time, media control, brightness, screenshot streaming, audio-device selection, systemd unit management, GPU usage, restart-required tracking, WOL, in-use sensors for mic, speaker, camera, gamepad — define the fullest desktop envelope [[lnxlink]]. The mobile companion documentation supplies the canonical vocabulary: battery, connection, storage, frontmost app, active camera and audio, displays, media session [[sensors-home-assistant-companion-docs]]. By sensor count ha-linux-agent is roughly a quarter of go-hass-agent's generic surface, and that concession stands on the record.

**The control bar — where the comparison inverts.** The kiosk contract is not sensor breadth but controls whose state genuinely synchronises and entity shapes richer than buttons. The incumbents fail on their own documentation. go-hass-agent's `commands.toml` vocabulary is button, switch, and number only, and its README states plainly: "States are not kept in sync. This is most important for all controls besides buttons. For example, if you configure a switch, any changes to the state you make outside of Home Assistant will not be reflected in Home Assistant automatically" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. Its users hit the wall in January 2026: a PipeWire output-device selector — the user "can't see a means to do a drop-down selector box with multiple text items" — because the commands vocabulary has no dropdown [[go-hass-agent-a-native-app-integration-for-desktoplaptop-devices-share-your-proj]]. jupiterOS's session-switching requires a select whose options reflect real systemd unit state — grouped launcher profiles become one mutually exclusive select, the shared state topic reshaping through discovery — a vocabulary the incumbent architecturally lacks. lnxlink ships dropdowns (a Steam game-launcher select among them) and systemd unit control, but no mutual-exclusion semantics and no state round-trip tied to fleet power services [[lnxlink]].

**The identity and notification bars.** go-hass-agent is dual-transport by mandate — mobile_app registration, no MQTT-only mode, optional MQTT v5 side — and documents the consequence itself: sensors and controls land as two HA devices that "cannot be combined in a single place" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. A single-device MQTT-only identity is not cosmetic; every dashboard and automation targeting a kiosk sees one coherent device.

**On notifications,** HA 2024.5 shipped a native MQTT notify platform — PR #115653, Quality Scale gold, `notify` in the mqtt integration's `SUPPORTED_COMPONENTS`, upstream test payload `{{'name': 'test'; 'command_topic': 'test-topic'}}` — giving an MQTT-only agent a first-class notify entity, strictly better than the current payload-hack button, implementable today, with the notify.py source (MqttEntity wired via `async_setup_entity_entry_helper`, command_topic required) as the primary-source leg of the confirmation chain [[add-mqtt-notify-platform-by-jbouwh-pull-request-115653-home-assistantcore-github]] [[corehomeassistantcomponentsmqttconstpy-at-dev-home-assistantcore-github]] [[test_notifypy]] [[corehomeassistantcomponentsmqttnotifypy-at-dev-home-assistantcore-github]]. One ceiling comes named: notify.mqtt lands as a notify *entity*, and legacy notify-service consumers such as the alert integration cannot target entity notifiers directly — the community thread documents exactly an MQTT notify entity being unusable as the alert integration's notifier, with `notify.send_message` plus `entity_id` targeting as the entity-ecosystem route, so alert-style consumers take the automation path [[notification-entities-and-alert-integration-configuration-home-assistant-communi]]. The platform is one-way — command topic plus optional template, no actions schema, no event round-trip [[mqtt-notify-home-assistant]] — and the round-trip exists on Linux in exactly one place: halinuxcompanion, the native-API-class exception, implements it over mobile_app with a local aiohttp HTTP server that HA POSTs to (its README advertises "Actionable Notifications (Triggers event in Home Assistant)" and "Notification cleared/dismissed (Triggers event in Home Assistant)", with its own to-do conceding "Finish notifications functionality") — a 90-star Python project whose roadmap's other item is "Move sensors to MQTT" because the native API strands values offline, the LWT problem already cited two paragraphs back [[github-muniterhalinuxcompanion-homeassistant-linux-companion-github]]. No MQTT-transport agent implements it: HASS.Agent on Windows remains the gold standard with its `hass_agent_notifications` event [[actionable-notifications-hassagent]] [[home-hassagent-documentation]], while go-hass-agent's actionable-notification requests (#667, December 2025) and clear_notification support (#926, August 2026) sit open with zero maintainer engagement [[feature-request-smart-notifications-with-action-buttons-issue-667-joshuargo-hass]] [[feature-request-add-support-for-clear_notification-issue-926-joshuargo-hass-agen]]. The single Linux round-trip implementation living in a project that concedes MQTT is the better transport is the strongest possible evidence for how small the MQTT-only sacrifice is.

**The transport question, resolved on scope.** A long-time HA contributor's objection, at full strength: "Could you clarify your reasoning behind going through MQTT for influxdb injection? Seems an unnecessary point of failure to me. I go directly from telegraf to influxdb, then use the influxdb integration inside HA" [[system-design-architecting-ha-data-flows-with-telegraf-mqtt-influxdb-and-grafana]]. Correct for a DB-centric time-series pipeline, irrelevant here: jupiterOS runs no InfluxDB and wants automations, dashboards, and kiosk *control* — the bidirectional case MQTT natively provides. The counter-architecture concedes from the inside: halinuxcompanion, the one native-API Linux agent, lists "Move sensors to MQTT" on its to-do because the native API leaves sensor values *stuck* when a host goes offline, whereas an MQTT last-will reflects it [[github-muniterhalinuxcompanion-homeassistant-linux-companion-github]]. The community demand signal ends the same way — a moderator answering "there is no Windows and Linux HA app" with the monitoring-class shelf while the original poster's "I personally hate mqtt" draws the correction that "most features rely on it for bidirectional communication" [[wth-there-is-no-windows-and-linux-ha-app-similar-to-macos-month-of-what-the-heck]]. Want control rather than readout, and the ecosystem routes you to MQTT. If long-horizon metric history ever matters, Telegraf-to-database belongs alongside the agent, not instead of it.

| Axis | ha-linux-agent | go-hass-agent v14.15.1 | lnxlink | HASS.Agent (Windows) |
|---|---|---|---|---|
| Transport / identity | MQTT-only, one device per host | mobile_app + MQTT v5; two devices, cannot be combined | MQTT-only | MQTT, one device |
| Sensor surface | sysinfo CPU/memory/disk/load/uptime, logind idle/locked, UPower (~25 % of go-hass) | D-Bus/ProcFS/SysFS/Netlink catalogue, SMART, GPU, OOM | ~50 desktop modules | Windows WMI surface |

The comparison set does not show a better agent to adopt. It shows the companion class's definitional features — single identity over MQTT discovery, controls whose state syncs, headless operation — are exactly the axes where the incumbents are weakest and this architecture is already right. The question is not which crate has the most sensors but which architecture can express the fleet's control plane; the sensor deficit is real, quantified, and addressed by the roadmap rather than denied.

## 4. The Build-vs-Buy Dialectic: Custom Rust Agent vs Telegraf, Glances, and Netdata

Build-versus-buy here has two forks: a monitoring stack for the hosts, or a companion agent to replace this one. The monitoring stacks are mature metrics pipelines, not HA citizens; the companion agents were sized above. The monitoring fork dies on audited evidence quickly; the agent fork deserves its strongest case first.

### A. The case for adoption, at full strength

go-hass-agent v14.15.1 is one `environment.systemPackages` line away on every host — verified in nixpkgs proper, not broken, not unfree, building for all 24 Linux platforms, maintained on a ~monthly cosign-signed cadence with 3,909 commits of sensor and hardware polish [[go-hass-agent-mynixos]] [[releases-joshuargo-hass-agent-github]] [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. Its maintainer designs the systemd path for servers ("The systemctl service is primarily for 'headless' usage (i.e., servers)" [[running-the-agent-as-a-service-and-tray-icon-joshuargo-hass-agent-discussion-387]]), its changelog shows it paying the MQTT lifecycle dues in public — "reconnect to MQTT on disconnect and fix issue with MQTT commands not working", graceful channel shutdown, constant device ids — and it carries SMART with capability handling, per-core frequencies, link rates, OOM events, fwupd firmware security [[changelogmd]] [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. lnxlink covers the desktop long tail, including a Steam game-launcher dropdown, a Lutris launcher dropdown shipped as a custom module, and a bash-command module creating sensors, buttons, and switches from shell scripts [[lnxlink]]. Against that maturity stands a twelve-crate workspace with eleven commits, eight tests that never run, a red lint gate, verified reconnect deafness, and three backends self-flagged "Unverified in a live environment" — a prototype, not a foundation. 

**The sharpest form of the objection:** the launcher mutual-exclusion select is one custom module away — lnxlink's bash surface cannot emit a select at all (its catalogue: *Create custom sensors, binary_sensors, buttons, or switches using shell scripts*), but its custom-module surface demonstrably can (the Lutris Game Launcher dropdown ships that way), and the mutual exclusion already lives in the systemd units and polkit rules (the system action-authorization layer) jupiter-os owns — the backend is a systemd-and-polkit design wearing a Rust relay as a coat, and relays are commodities [[repo-map-ha-linux-agent]] [[lnxlink]]. The maintenance arithmetic clinches it: improving means one solo maintainer re-deriving, on a single-machine budget, a reliability curriculum every incumbent burned years of multi-contributor production reports to learn — on a library whose own reconnect bug has been open five-plus years. Even the split-brain price is arguable: a split identity that works beats a unified identity that does not.

### B. Why the evidence refutes it

**The packaging counter first.** One custom module away carries a heavy deployment cost on this fleet: lnxlink is not in nixpkgs at all — an individual hit a wall packaging it in October 2025 and no one has upstreamed a service module in the year since an unmerged draft appeared in August 2024 — and its Python dependency surface (pygobject3, ewmh, xlib, opencv-python, pulsectl, pyalsaaudio, docker, speechrecognition in one propagated list) is the ongoing per-release maintenance cost for whoever owns that packaging [[python-packaging-error-needs-specific-setuptools-version-nixos-discourse]]. Even granting the module: lnxlink's bash surface cannot emit selects (sensors, binary_sensors, buttons, or switches only), so the launcher select is a hand-written custom module per host — while the fleet's design generates it declaratively from `jupiter.services.haAgent.launcherApps`, with the state round-trip through the shared state topic reflecting real systemd unit state. No module precedent exists for that class: lnxlink modules are hand-written per host, not generated from fleet configuration [[lnxlink]]. go-hass-agent is packaged as a *binary* but has no NixOS service module: a full-text pass over module-list.nix returns zero occurrences of either incumbent, while the home-automation directory hosts home-assistant, esphome, zigbee2mqtt, zwave-js, matter-server, govee2mqtt, evcc, ebusd, and homebridge [[module-listnix]]. Adoption means writing the module anyway, inheriting the split-brain, and building the launcher/session layer as configuration glued around an agent that does not natively model it.

**Second**, the adopter's fork that dissolves the expressibility objection over time: contribute the select support and a NixOS service module upstream — go-hass-agent takes feature requests, and its audio-select gap shows the control vocabulary CAN be extended — rather than gluing around the gaps. The evidence on record prices that path: it runs through a maintainer whose changelog shows zero select/state-sync occurrences across 3,909 commits and whose two open notification feature requests have sat unassigned since December 2025 [[feature-request-smart-notifications-with-action-buttons-issue-667-joshuargo-hass]] [[changelogmd]]. Contributing upstream means paying the solo-maintainer wait on someone else's release cadence — the same maintenance arithmetic the objection itself raises, with less control.

**Third**, the expressibility record. go-hass-agent's complete changelog from v4.3.1 through v14.15.1 contains zero occurrences of select entities, control state synchronisation, or NixOS support — the gaps persist through the current era [[changelogmd]]. The mechanism-versus-surface decomposition is conceded in full: the mutual exclusion lives in fleet-owned systemd units and polkit rules, and would survive any adoption. But the *entity surface* — the typed, declarative select generated from `jupiter.services.haAgent.launcherApps`, the state round-trip through the shared state topic, the per-profile binary sensors — is agent-owned differentiation, regression-tested in this repo, inexpressible in a commands-file vocabulary whose own documentation disclaims state sync. A mutual-exclusion group whose whole point is that the compositor's real session state, not HA's last command, is the truth cannot be backed by a control model that never learns out-of-band changes. The unsynced-switch problem is a dashboard annoyance on an incumbent; on a kiosk session switcher it is a wrong-state machine.

**Fourth**, the reliability-provenance argument inverts on inspection. The incumbent's public fix history proves the bug class is generic, not that the incumbent is immune in this fleet's shape: adopting means inheriting two devices per host, unsynchronised controls, an MQTT v5 requirement (already satisfied by callisto's version-current mosquitto, so a non-cost on this fleet), and manual registration — configuration problems, admittedly — while the custom agent's are existence problems, admittedly worse today but scoped to two locations in one file, with a specification already written. The objection's strongest sentence — a split identity that works beats a unified identity that doesn't — is time-bound. The unified identity stops not-working the moment the ConnAck supervisor lands, which is the Phase 1 estimate of one to two weeks, not a research programme.

Glances is HA's own documented monitoring path, and its record is a six-year cautionary tale: sensors renamed with `_2` suffixes after every restart ("This renaming is undone if I remove then re-add the integration using the web UI until the next restart. USED memory. The concessions stay on the record, because improve-don't-adopt is only honest with costs named: ~25 % of go-hass-agent's sensor coverage; eight test functions against 3,909 commits; three backends carrying the repo's own unverified-live flags; a notify path that is a payload-hack button rather than an entity. None is a reason to adopt; they are the scope discipline the roadmap must respect. The verdict — improve — holds because the maintenance asymmetry only pays off when the differentiating layer is genuinely unbuildable upstream, true here precisely for the launcher select model and the server backends, and because the bespoke path's worst defects are already audited to the line, which is more than can be said for inheriting a split-brain and gluing around it.

## 5. NixOS Fleet Architecture: From Kiosk-Only to Every Host in jupiterOS

A NixOS host runs services in two shapes: system services, managed by the system manager and ordered against the network and each other, and user services, managed per-user and unable to order against system units "by design" [[what-is-the-difference-between-systemdservices-and-systemduserservices-help-nixo]] [[restart-oneshot-systemd-service-on-every-rebuild-help-nixos-discourse]]. The agent ships as a user service with linger (the mechanism keeping a user's manager alive without a login). In 2026 that boundary moved, and the fleet's design sits on the wrong side of it.

### A. The boundary redraw

The old reason to retire user units was staleness — switches did not restart them. PR #517768, merged May 2026, made it worse: switch-to-configuration-ng now runs a full per-user switch for any user with an active manager — enumerate via `logind.list_users()`, stat `/run/user/{uid}` as the liveness check (linger included), spawn a setuid child per live manager running daemon-reload plus stop/reload/restart passes with literal `restart_unit` calls [[switch-to-configuration-ng-harden-user-unit-migration-second-pass-by-r-vdp-pull]] [[mainrs]]. The regression fired on real fleets within days: users kicked out to GDM mid-switch as user-manager restarts collapsed `graphical-session.target` — a one-way teardown, the target declaring `RefuseManualStart=yes` — one reporter hitting seven occurrences in 57 switches, session units stopping 150–730 ms after the daemon-reload and never returning [[anyone-seeing-nixos-rebuild-switch-kick-you-out-to-gdm-andor-log-gpf-errors-spec]]. The user-unit shape now combines both failure modes: lingered-but-not-logged-in users wait for a reboot; active users get sessions torn down mid-switch. For an appliance fleet, retire the shape entirely.

### B. The system-service design

One `systemd.services.ha-linux-agent` per host, `User=io`, `Restart=on-failure`, `RestartSec=5s`, `After=network-online.target`, plus a `role` option — `kiosk | server | minimal` — driving mkIf branches (NixOS's conditional-configuration idiom). Why this exact shape and not a dynamic or dedicated user: `DynamicUser=` is ruled out on upstream authority — it is "currently incompatible with D-Bus policies" (a service using it may not allocate a D-Bus service name, though calling into other buses still works) and implies `ProtectSystem=strict`, which would block the agent's sysfs/probe surface — so a static `User=io` is the canonical minimal shape, not a preference. And the existing launcher grants survive by mechanism, not luck: the polkitUnitRule grants key on `subject.user == `io``, which a `User=io` system service satisfies unchanged, so the launcher's system-scope commands transfer with zero new grants. The two facts that were supposed to force the user/system split both dissolved. 

**Session-bus reachability:** a `User=io` system service reaches the per-user bus at `/run/user/1000/bus` with two `Environment=` lines (`XDG_RUNTIME_DIR` + `DBUS_SESSION_BUS_ADDRESS`), because access control on the per-user bus is purely the socket's filesystem mode — jupiter-os's own `mkSessionLauncher` proves the pattern from the system side for cage sessions [[d-bus]]. Headless boxes without a session bus produce the "Failed to connect to bus: No medium found" ladder, which is why the generic backend already degrades to warn-and-disable where no session exists — correct behaviour on europa and pallene [[systemduser-archwiki]] [[openclaw-gateway-status-fails-on-ec2headless-servers-due-to-missing-user-level-s]]. Declarative linger (NixOS 23.11, closing a nine-year gap) stays useful for the cage sessions, not the agent — and its habit of disabling undeclared users' managers is a footgun when enabled [[enabling-persistent-user-instance-systemd-issue-3702-nixosnixpkgs-github]] [[nixosusers-groups-add-user-option-to-enable-lingering-by-toxicfrog-pull-request]].

### C. The zero-capability privilege ladder — the design, not the fallback

The audited evidence contains one direct internal disagreement: one position holds `AmbientCapabilities=CAP_SYS_ADMIN CAP_SYS_RAWIO` where SMART is enabled; the live-proven finding is that every subsystem has an unprivileged channel, so the capability grant becomes the named, explicitly-rejected alternative [[systemdexec]] [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]]. The kernel matrix makes the stakes concrete: NVME_IOCTL_ADMIN_CMD requires CAP_SYS_ADMIN, and as the Scrutiny maintainer puts it, "there is nothing you can do except grant that" — the de facto new-root catch-all, to displace a daemon that already runs [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]]. The ladder:

- **SMART:** smartd `-M exec` hooks. smartd already runs privileged on europa at the fleet's chosen interval with scheduled self-tests; the hook receives the full event context via `SMARTD_MESSAGE`/`SMARTD_FAILTYPE`/`SMARTD_DEVICE` environment variables and hands it to the agent, which never touches the ioctl (the direct device-control syscall) — inheriting smartd's scheduling and self-test logic free. The man-page caveat dictates the hook's shape: "smartd will block until the executable PATH returns", so the hook must be a fast hand-off — write the SMARTD_* event to the agent's channel and exit immediately (a detached spawn or socket write), never an inline MQTT publish that would stall smartd's monitoring loop. The channel has two audited designs — the hook (a root-owned script, the smartd-warning.d convention, wired via a `jupiter.storage.smartMonitoring.hook` option or a fixed `/usr/share/smartmontools/smartd_warning.d/` entry) either drops a JSON line into `/var/lib/ha-linux-agent/smartd/` for the agent to pick up, or publishes directly to the agent's MQTT user as a low-privilege client [[smart-archwiki]] [[smartdconf5-smartmontools-debian-testing-debian-manpages]]. The capability-rejection holds a fortiori on this hardware: europa's audited inventory (Marvell 88SE9230 SATA HBA, WD 18TB drives plus one OS SSD) is all-SATA, so even the rejected alternative would need only CAP_SYS_RAWIO, not the "new root" CAP_SYS_ADMIN the Scrutiny quote warns about. The exporter shape — smartctl_exporter, root by design, 60-second polls — remains a per-host opt-in for sub-minute freshness no current host needs [[github-prometheus-communitysmartctl_exporter-export-smartctl-statistics-to-prome]].
- **ZFS:** `/proc/spl/kstat/zfs/<pool>/state` procfs reads — the node_exporter-proven unprivileged path, plain file opens, no ioctl, no privilege — for state polling, plus a zedlet as the push channel: ZED (the ZFS event daemon) is root-only and already auto-enabled on ZFS hosts, so it publishes *into* the agent's channel. The mechanics mirror the smartd hook exactly: zevents arrive as `ZEVENT_`-prefixed environment variables, zedlet registration is filename-prefix-based — as a special case, the prefix all matches all zevents [[zed8in]] — and zedlets must be root-owned with no group/other write. The deployment cost is near zero because `zfs-zed.service` ships inside the zfs package and is wanted by `zfs.target` unconditionally when ZFS is enabled — jupiterOS defines no unit for ZED, only zed.rc values via `services.zfs.zed.settings` plus one custom zedlet [[zed8in]] [[zfsnix]]. The current backend's shell-outs to `zpool list` are root-equivalent today; the rewrite removes an avoidable root requirement. Thresholds from the monitoring literature: capacity warn 80 %, critical 90 %; fragmentation 30/50; any non-ONLINE state as the binary_sensor problem [[how-to-monitor-zfs-pool-health-and-status-on-ubuntu]].
- **systemd unit health:** system-bus D-Bus match rules, live-proven on callisto — a logrotate timer's `JobRemoved` signal was delivered to an unprivileged io subscriber with zero polkit grants, alongside 27 PropertiesChanged signals in the same window, while unprivileged job *creation* remains correctly gated. The proof has a negative half that pins the design: the more obvious observability API, BecomeMonitor (`busctl --system monitor`), was tried live and polkit-denied for io, so the design commits to match-rule subscription (zbus receive_signal / MessageStream with a match rule) specifically, never BecomeMonitor. Two subtleties: Manager signals require an explicit `Subscribe()` call at startup (PropertiesChanged does not — a lazy-signals design), and the daemon shape has a production precedent in systemd_mon, which has subscribed "no polling, and no busy-loops" since the v204 era, queuing rapid intermediate transitions into one notified change [[github-joontysystemd_mon-monitor-for-systemd-to-alert-failed-services-github]]. The rejected alternative is the OnFailure drop-in pattern, which needs root-owned writes into `/etc/systemd/system/` [[see-also-3]].
- **Backlight:** raw sysfs writes (the ABI contract: `brightness` 0..max_brightness, `actual_brightness`, `bl_power` 0/4) with the broken chmod replaced by one udev `GROUP=`video`` rule plus io-in-video membership — the fleet's own existing pattern for the customer-display hidraw nodes. One write-path subtlety from the fleet audit: kiosks run the hardware backend's backlight disabled, so the deployed brightness entity is the launcher's screen-power light profile (backlight = "") whose writes go through the same raw sysfs path — the udev rule must therefore cover the *launcher* backend's write path, which is the consumer the kiosks actually use, not only the backend-hardware surface the Section 1 audit names [[sysfs-class-backlight]] [[backlight-support-the-linux-kernel-documentation]]. The read side upgrades to push for free: the kernel emits a `KOBJ_CHANGE` uevent and a `sysfs_notify` on `actual_brightness` after every store attempt, hotkey path included, so the 1-second poll-everything default becomes event-driven plus a slow heartbeat [[backlightc]].

Summed: no AmbientCapabilities, no sudo, no root anywhere in the fleet. The complete privilege surface is system-bus socket access, optionally the session bus via the Environment block, the existing polkit rule pattern for the specific units the launcher may start/stop, and one designation leg: backend-headscale's `tailscale status --json` shell-out needs `tailscale set --operator=io` (unprivileged operation of tailscaled is a designation, not a default) with `--socket=<path>` for NixOS's socket location [[tailscale-cli-tailscale-docs]]. Delete `ha-linux-agent-sysfs-perms` entirely — it grants group-root write that the only intended consumer cannot use.

### D. The rollout, and the one open decision

The module moves from the kiosk profile to common, role-switched:

| Host | Class | Agent today | Target role |
|---|---|---|---|
| amalthea, adrastea, metis, thebe | TCxWave kiosks — screen-power profile fused to `tcxwave-screen-power.service` (touch-wake, polkit-gated for io per `tcxwave-touch-wake.nix:287`), session mutual-exclusion select, customer-display switch; 1-second polling, broken backlight writes | running, the surfaces the Phase 2 rewrite must preserve | kiosk |
| callisto | broker + arcade host | deliberately absent | kiosk/minimal — the broker host finally runs its own agent |
| europa | ZFS NAS, syncthing, headscale | absent despite the purpose-built backends | server (SMART hook, procfs ZFS, zed bridge) |
| pallene | Kamatera VPS, ZFS-less | hard opt-out (no sops-nix, no disko, no ha-linux-agent) | minimal — pending the secrets decision |

Secrets wiring is unchanged: sops-nix (the fleet's secrets-decryption module) decrypts to `/run/secrets` with per-secret owner and `restartUnits`, so `sops.secrets.mqtt_ha_linux_agent.owner = `io`` works identically for a system service — per-secret owner and restartUnits are the system-module semantics, while the home-manager path a user unit would have depended on runs as a user service into `$XDG_RUNTIME_DIR/secrets.d` with ordering requirements, so the system-service move lands on the simpler of the two documented shapes [[github-mic92sops-nix-atomic-secret-provisioning-for-nixos-based-on-sops-github]]. Pallene is the one decision only the user can make — a sops bootstrap or a minimal profile with inline credentials — because its configuration explicitly refuses sops-nix, and no agent choice changes that. 

**One residual risk is named rather than hedged:** notification delivery from a system service into a session (the Environment block's untested leg, estimated at 20–25 % risk) — and its shape is conditional, not kiosk-shaped: an audited grep of the fleet checkout (mako, dunst, swaync, fnott, notify-send across `modules/` and `hosts/*/`) returns zero matches, so no notification daemon ships anywhere and the session-bus last mile is dead code on every host today, while the kiosks' real last mile is the customer-display VFD overlay, whose daemon already renders anything published to its MQTT topic [[jupiteros-notification-ground-truth]]. The residual therefore stands only for a future desktop host class, with the Environment block conditional likewise — dead code today, a live question the day a desktop host appears. The verification item: one busctl check for an `org.freedesktop.Notifications` owner on a kiosk comes first, because with no daemon to receive, a delivery test as scoped cannot exercise the last mile it is meant to retire.

## 6. JupiterOS-Specific Feature Gaps

The gap list is jupiterOS-shaped, not generic: each item maps to a host class in the fleet's configurations, and each closes through a channel either unprivileged by design or pushed from a privileged incumbent the host already runs. The feature design and the privilege design are the same document.

**systemd unit health (callisto, europa, kiosks).** The fleet's service inventory — mqtt, postgres, syncthing, headscale, the iscsi target, model-router, the kiosk power services — has no HA-side health surface at all. The D-Bus Subscribe() design delivers per-unit binary sensors with push semantics, and the watched-unit list generates from the same jupiterOS configuration that defines the launcher profiles. The launcher backend's 1-second `systemctl is-active` polls move to the same channel — the push design eliminates the poll rather than tuning its interval.

**SMART/NVMe (europa; opt-in elsewhere).** The smartd hook keeps smartd as the privileged detector and the agent as consumer, surviving smartd's scheduling and self-test logic for free — displacing it would cost a capability grant and a polling loop to replace a daemon that already runs the fleet's chosen tests [[smart-archwiki]]. Three caveats the hook design carries:

- **Device self-test support is optional per drive** (an Intel 600p reports "Device Self-test Not Supported" via the oacs bit while still reading healthy), so the inherited scheduling needs a capability check, not an assumption [[how-to-check-nvme-ssd-health-newbie-corner-arch-linux-forums]].
- **The surface decision** — separate entities versus attributes on a disk entity — has an incumbent cautionary precedent in go-hass-agent exposing SMART as attributes that template sensors must individually surface [[how-to-see-your-ssdhdd-health-directly-in-home-assistant-diy-ideas]].
- **The bridge should expose wear and vendor product-EOL as distinct sensors**, since a drive at ~1 % of rated TBW can already be flagged EOL [[whats-the-best-way-to-monitor-nvme-health-applications-endeavouros]]. Callisto, which has repeatedly destroyed local NVMe drives and keeps none, has no customer for even the opt-in.

**Verified ZFS status (europa only).** The procfs-state plus zedlet two-channel design, with the premise correction that scopes it: pallene is ZFS-less and callisto's only ZFS exposure is the iSCSI zvol with no local pool, where the backend's `detect()` already returns false — correct today [[repo-map-ha-linux-agent]].

**Mesh/exit-node health (europa, fleet visibility).** The tailscale `ipnstate` schema is the surface for peer and exit-node state — PeerStatus with HostName, Online, and ExitNodeStatus for the current exit node's liveness [[ipnstate-package-tailscalecomipnipnstate-go-packages]]. The backend's current mechanism is already audited: backend-headscale shells out to `tailscale status --json` today, so the schema work is verification and version-tolerance of an existing channel, not new parsing — and the unverified backend maps onto europa, the host where the mesh hub (headscale) runs, with callisto's and the kiosks' agents reporting peer/exit-node state as tailnet members. Unprivileged operation of the channel is a designation, not a default — `tailscale set --operator=io` is the sanctioned grant for a non-root user to operate tailscaled, with `--socket=<path>` covering NixOS's customised socket location [[tailscale-cli-tailscale-docs]]. The schema is authoritative but explicitly unstable-by-policy across versions ("WARNING: format subject to change"), so the parser is version-tolerant [[tailscale-cli-tailscale-docs]]; the operational surface around it — `tailscale wait` / tailscale-online.target as the readiness gate where mesh reachability orders the agent, `BackendState` as the reliable running-indicator [[how-to-check-if-tailscale-is-running-alexwlchan]], and the frozen-by-policy `--json` contract that makes version-tolerance a schema check rather than a re-parse [[cmdtailscalecli-build-a-mechanism-to-change-the-output-from-json-logs-in-the-fut]] — completes the feature the same way SMART and ZFS get their mechanisms named.

**Power/UPS (absent today; NUT is the shape when it appears).** The audited absence first: a search of `modules/` and `hosts/*/` for ups, nut, and apc declarations returns zero matches — no jupiterOS host declares a UPS, so power monitoring maps to no host class in today's fleet. The corpus still fixes the design for the day one is attached, because the HA-native shape is NUT and its ceilings are the agent-side consumer's requirements:

- The integration cannot talk to a UPS directly (a NUT server is required, port 3493, 60-second default polling).
- It can retrieve but not set NUT variables and supports no parameterised commands.
- Device actions (instcmds such as beeper.disable, test.battery.start.quick, power-cycle outlet) require credentialled upsd.users grants.
- It cannot auto-detect a server IP change (DNS-name resolution, never baked IPs).
- Most diagnostic sensors are disabled by default as a deliberate recorder-cost trim; `upsc`/`upscmd` enumerate the raw surface an agent-side consumer reads directly [[network-ups-tools-nut-home-assistant]].

With switches now restarting user units disruptively, a booted-vs-current-generation sensor converts the new switch behaviour from a surprise into an observable — telling HA which hosts run a stale generation after a switch, cheap to read, fleet-relevant for the first time [[anyone-seeing-nixos-rebuild-switch-kick-you-out-to-gdm-andor-log-gpf-errors-spec]].

**Remote reboot/poweroff.** Not in the audited command surface today: launcher unit start/stop plus the generic backend's lock, suspend, and notify; no crate carries a reboot or poweroff handler [[repo-map-ha-linux-agent]]. What is missing is the capability plus the idempotency contract — an audit of the fleet's command handlers for non-idempotent semantics (reboot/power among them) is the named next step, because whether any launcher-style command is non-idempotent calibrates how much the clean-session rejection depends on it: if none are, a replayed stale message damages nothing, and the persistence question becomes lower-stakes than the lifecycle design argues.

**Notifications, end to end.** notify.mqtt replaces the payload-hack button (HA 2024.5+; callisto's HA qualifies), one-way [[add-mqtt-notify-platform-by-jbouwh-pull-request-115653-home-assistantcore-github]] [[mqtt-notify-home-assistant]]. The kiosk last mile is the customer-display VFD overlay — the display daemon already renders anything published to its MQTT topic as a notification overlay, verified against the fleet checkout — not session-bus notifications, of which zero daemons ship fleet-wide [[jupiteros-notification-ground-truth]]. Actionable notifications have no MQTT-transport implementation anywhere (the one Linux round-trip, halinuxcompanion's, rides the native API with a local HTTP server — the class whose own sensor-stranding problem §3 documents), so they stop being priced into the decision; what little interactivity is needed is recoverable in-pattern — expose notification actions as buttons on the device, automations listening on those command topics.

**CPU performance knobs (kiosks).** The global boost switch lives at `/sys/devices/system/cpu/cpufreq/boost` (values 0/1, the recommended interface over the legacy per-policy AMD knob) — a natural governor/EPP sibling for the hardware backend's existing write path, gated by the same udev video-group pattern [[cpu-performance-scaling-the-linux-kernel-documentation]].

**The future desktop host class.** A niri-based desktop host is speculative (niri, a Wayland compositor, appears in zero jupiterOS host configurations), but its boundary is solved from source: the compositor's IPC socket is created as `niri.{wayland_socket_name}.{pid}.sock` under the user's runtime directory — filesystem-permission-gated, so a same-UID `User=io` system service reaches it by globbing, no session unit required (the niri-ipc client library's explicit-path `connect_to()` / `NIRI_SOCKET` being the cleaner reach than globbing) — and the event-stream contract delivers complete state up-front followed by updates, so "your state can never 'desync'" [[serverrs]] [[ipc-niri-msg-niri]] [[niriniri-ipcsrcsocketrs-at-main-niri-wmniri-github]]. The convenience carries a security cost that belongs in the same threat model as the polkit grants: niri's own model warns that IPC-socket access can "Spawn a Wayland client which can do everything in the list above" — screen recording, input emulation, clipboard reading, password-dialog spoofing via the layer-shell protocols, so the agent's socket reach is a privileged capability in practice, not a free convenience [[security-model-niri-wmniri-wiki-github]]. The system-service design covers a desktop host class without a shape change.

## 7. Testing a Hardware-Touching Daemon

A hardware-touching daemon resists testing because its inputs live in `/sys`, on D-Bus, and on the network; a gate is only a gate if it runs in CI, fails loudly, and cannot hang. The testing verdict rests on one general principle: web consensus optimises the generic case, and fleet ground truth overrides it. The web's consensus names mosquitto-in-testcontainers as the right harness — `Mosquitto::default().start()`, broker URL from the mapped port, no authentication [[testcontainers-mosquitto-module]] [[mosquitto-in-testcontainers_modulesmosquitto-rust]]. The audited fleet facts refute it on arrival: no docker or podman on any jupiterOS host, no container runtime in any host configuration, and the Nix remote builders cannot expose container sockets inside build sandboxes at all — a testcontainers gate would be dead on arrival, not merely awkward. The harness therefore borrows testcontainers' hard-won lessons (URL always derived from the harness, never hardcoded; ready-probe before assertions; per-test exclusive broker) and swaps the spawn primitive for a subprocess.

**The sandbox-legality proof, from the Nix source itself.** Can a build-sandbox derivation even open a TCP socket pair? The Nix source answers at the syscall level: the builder performs `ioctl(SIOCSIFFLAGS)` on `lo` with `IFF_UP | IFF_LOOPBACK | IFF_RUNNING` inside a network namespace cloned for every non-fixed-output derivation, and the design comment states the builder "only has a private loopback interface" by intent — in-sandbox client-server pairs are upstream-blessed by construction [[local-derivation-goalcc]]. 

**Practice confirms the mechanism on both sides:** merged nixpkgs PR #283878 ran a localhost server-client pair inside checkPhase, the build log showing "Serving HTTP on 127.0.0.1 port 8000" serving requests from the test client [[single-file-cli-init-at-1149-by-n8henrie-pull-request-283878-nixosnixpkgs-github]], while the same author's Discourse thread shows the cross-boundary shape failing — a server started outside the build is unreachable from checkPhase because "there are different loopback interfaces in different namespaces", which is precisely why the harness spawns mosquitto inside the test rather than reusing a host broker [[local-networking-in-checkphase-help-nixos-discourse]]. So the mosquitto-subprocess harness inside the test hook — bind a `TcpListener` to `127.0.0.1:0`, read the port, hand it to `mosquitto -p <port>` (the no-config default is anonymous [[mosquittoconf-man-page-eclipse-mosquitto]] and loopback-only), TCP-probe with a fail-fast, kill on Drop — needs no sandbox escape and no VM [[mosquitto8-mosquitto-debian-unstable-debian-manpages]].

**The seven-step ladder, in dependency order**:

1. **Fix the clippy lint** (`map_or` → `is_some_and` at `backend-hardware:117`) so the check can go green at all — the gate currently cannot gate.
2. **Wire the test hook** — this runs the existing eight pure tests for zero new code, the single cheapest reliability win available, and the moment the *8 tests, none running* posture ends.
3. **sysfs-root injection** — parameterise backend-hardware on a `PathBuf` root, build tempfile fixtures as synthetic `/sys` trees (std::fs is a module, not a mockable trait, so injection is the canonical path), and unit-test parsing plus warn-not-panic behaviour on unwritable nodes.
4. **Extract the `Agent::run()` seam** — config-injectable jitter bound and shutdown channel, so the lifecycle is testable in-process — the same refactor the supervisor requires, so ladder and reliability phase are one work item.
5. **The mosquitto-subprocess harness plus five defect-named regression tests**, with rumqttc itself as the observer client (the production stack, not a mock): the harness needs zero new flake ingredients — mosquitto already ships in the devShell, `pkgs.dbus` already rides commonArgs' buildInputs, and crane's derivation attributes pass straight through so the broker rides cargoTest's nativeBuildInputs with no preCheck hook, the per-test guard spawning and killing the broker itself.    - `broker_restart_resubscribes_and_reasserts_availability` (kill -9 the broker, restart on the same port, publish a command, assert the agent handles it — the exact event `agent.rs:190` currently swallows — then assert a fresh subscriber reads retained `online`)
   - `birth_message_triggers_discovery_republish` (jitter injectable to 0)
   - `sigterm_publishes_offline_then_disconnects`
   - `hung_backend_doesnt_starve_sensors` (one backend whose poll never returns plus one healthy; assert the healthy one still publishes)
   - `decommission_zero_payload` The five names follow the repo's own house style — the eight existing tests are named regression guards with explanatory comment blocks (*Regression guard: … See commit e28ca83*) — so the new tests read as natives, not imports. Every await wrapped in `tokio::time::timeout(5 s)` — a reliability gate that can hang is not a gate.
6. **A private dbus-daemon harness** (`--session --print-address` into a tempdir, exercising the zbus plumbing with the `pkgs.dbus` buildInput) — bounded honestly to plumbing tests, because a private bus hosts no `org.freedesktop.systemd1`.
7. **`runNixOSTest` for the module** — the out-of-tree invocation the NixOS manual documents, headless in QEMU where a full system bus and real systemd exist, cribbed from nixpkgs' own mosquitto test with a single node (the kiosk failure mode is local): enable the module, wait for the agent unit, assert retained `online`, restart the broker service mid-test, and assert re-subscribe and availability return — the module-level replay of the two root defects, and the gate that pins the fleet unit shape in one stroke [[nixos-manual]] [[mosquittonix]].

Two boundaries are settled: real systemd signal tests belong to the NixOS test, because build sandboxes do not provide systemd; and a KVM (kernel-VM acceleration) availability check on the remote builders decides whether the VM gate runs per-check or nightly. The testcontainers notes stay filed for the day the project gains hosted CI with Docker — the test bodies are deliberately harness-agnostic below the spawn primitive.

## 8. Ordered Improvement Roadmap

The order is the argument, and each phase's exit criteria feed the next gate.

**Phase 0 — unblock the gate (days, no behaviour change).** Fix `backend-hardware:117`; wire the test hook; the check goes green with all eight tests executing for the first time. Remove or wire the dead `tls` knob at `config.rs:88`; document backend-hardware in the README; land the notify.mqtt discovery entity — strictly better than the payload-hack button, and independent of everything else [[test_notifypy]].

**Phase 1 — the ConnAck supervisor (one to two weeks, on rumqttc 0.24.0, no dependency churn).** ConnAck-driven re-subscribe and retained-availability re-assert on every connect; birth subscription with 0–30 s jitter (config-injectable to 0 for tests); channel capacity 0 with per-tick publish timeouts; per-backend and per-command task isolation with 5 s HTTP timeouts in backend-syncthing; SIGTERM offline-then-`disconnect()`; exponential reconnect backoff 1→60 s with ±20 % jitter so a broker restart cannot synchronise the fleet; `--decommission` zero-payload mode. Broker pairing on callisto: `persistence true` plus `persistence_location`, and a `$SYS` drop-counter check — hygiene at current scale, load-bearing the day entity counts grow. Ladder steps 4 and 5 land here as the definition of done, with `broker_restart_resubscribes_and_reasserts_availability` as the named acceptance test.

**Exit criteria:** the five regression tests green in the check; a live kiosk survives `systemctl restart mosquitto` on callisto with entities recovering inside the keepalive window; the live presenting symptom is gone. Beyond the one-shot restart test, a standing publish/subscribe round-trip self-probe (the blackbox-exporter pattern, where message loss is a published-minus-received counter delta and a hang is started-minus-completed) turns deafness from an incident into an alarm — implementable inside the agent or as an HA automation with no extra exporter [[github-inovexmqtt_blackbox_exporter-prometheus-exporter-for-mqtt-monitoring-gith]].

**Phase 2 — the fleet service model (one week, mostly Nix).** Rewrite the module to ship `systemd.services.ha-linux-agent` with `User=io`, `Restart=on-failure`, and the role switch; delete the user unit and the broken sysfs-chmod oneshot (fixing the false comment either way); the udev `GROUP=`video`` rule plus io-in-video for backlight writes; the Environment block on lingered hosts only; sops wiring unchanged; rollout to europa (server role) and callisto (kiosk/minimal — the broker host runs its own agent deliberately rather than by omission, closing the 4-of-7 gap to 6-of-7); the runNixOSTest gating the module in both roles; the pallene secrets decision surfaced to the user as the phase's one open question.

**Exit criteria:** `nixos-rebuild switch` restarts the agent on every host every time (the property the current fleet lacks); brightness writes succeed on a kiosk with no chmod oneshot; the busctl check for an `org.freedesktop.Notifications` owner on amalthea settles the fleet section's residual risk question (no owner, and the session-bus Environment block is retired for today's host classes).

**Phase 3 — features, each with its privilege design settled (two to three weeks, severable).** The smartd-hook SMART bridge on europa; backend-zfs rewritten onto procfs state plus the zedlet bridge; the D-Bus Subscribe() unit-health backend replacing the launcher's 1-second is-active polls; KOBJ_CHANGE-driven backlight sync; version-tolerant headscale parsing; the nix generation/boot-health sensor; notify-to-VFD on the kiosks; the boost switch. Explicitly out of scope: the mobile_app actionable-notification contract (the one Linux implementation rides the native API with a local HTTP server, not MQTT — nothing for an MQTT agent to inherit) and the incumbents' sensor long tail that the fleet does not consume.

**Exit criteria:** each feature carries at least one ladder-level test; none adds a capability, a sudo, or a root-owned write.

**Forward-looking.** Six to twelve months out, the agent stops being a kiosk accessory and becomes jupiterOS's observation plane: every host emitting unit health, storage health, and session state over one supervised MQTT lifecycle, with the module's role switch absorbing new host classes without code changes. The first named consumer is the ROADMAP's ganymede-successor, an always-on headless host planned for mosquitto, the HA VM, and n8n with no host configuration yet — absorbed by the `server`/`minimal` role switch the day it exists. Three developments would legitimately reopen settled questions and deserve standing watch:

- **A merged-and-released upstream reconnect signal** — which would let the raw ConnAck match become an event variant and trigger the version bump, but would not change the design, since subscriptions stay application-owned.
- **An incumbent shipping native select controls with state sync or a NixOS service module** — go-hass-agent's zero-occurrence record through v14.15.1 is the current evidence against [[changelogmd]].
- **An end-to-end MQTT v5 decision** — which loosens the clean-session reasoning and makes message expiry the stale-command cure; the v5 module already ships inside the pinned version. The deeper strategic point stands behind all of them: the fleet's deciding feature — declarative mutual-exclusion session control fused to systemd units — is one fleet's idiom, and no general-purpose agent will ever prioritise it. Owning twelve small crates whose worst defects are file:line-diagnosed is a better maintenance position than gluing that idiom onto an agent that cannot express it.

## Opinionated Synthesis

**ha-linux-agent is two bugs away from reliable, and the fix is fully specified; the rest is order.** The "never reliable" complaint decomposes into two bugs — subscribe-once plus a swallowed ConnAck, and availability-published-once — both located to lines and mechanically explained in §2, with the supervisor fixing all of it without dependency churn, with named regression tests, on the pinned version. The strongest objection — adopt go-hass-agent, express the launcher as configuration around it — fails on packaging and expressibility (§4), but it stays live as named flip conditions: an incumbent NixOS service module plus select controls with state sync would reopen the generic-host arithmetic (not the launcher layer, inexpressible in a commands-file vocabulary); an end-to-end MQTT v5 decision would loosen the clean-session reasoning; a desktop host class is already covered by the same-UID socket boundary. Until one of those fires, the evidence points one way.

The committed plan, then, is reliability first (Phase 0–1, days to weeks, because a deaf agent makes every feature a lie and every new sensor a ghost), fleet second (Phase 2, because a 4-of-7 deployment contradicts the stated ambition and the 2026 switch-to-configuration change makes the user-service shape actively harmful), features third (Phase 3, scoped to jupiterOS consumption through unprivileged event-driven channels — smartd hooks, procfs plus zed, live-proven D-Bus match rules, udev video-group backlight). The residual risks are named, not hedged: the busctl check for a notification-daemon owner on amalthea (20–25 % until run, and conditional on a desktop host class ever existing), the one procfs readability check on europa (a single command away), and the pallene secrets decision (the user's, not the agent's). The flip conditions standing watch in §8 need no restatement here; should one fire, the verdict recalculates and the phases re-order around it. Beyond them sits the payoff: the launcher select — the one thing no general-purpose agent will ever prioritise — stays homegrown, declarative, and regression-tested, and the fleet buys an observation plane it owns end to end.
