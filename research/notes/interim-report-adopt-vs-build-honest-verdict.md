# Interim report: adopt-vs-build-honest-verdict

**Locus question:** Given go-hass-agent v14.15.1 is already in nixpkgs and lnxlink is community-endorsed with ~50 modules, is improving ha-linux-agent the right call at all — and if yes, exactly which jupiterOS-native capabilities (launcher mutual-exclusion groups, kiosk session switching, ZFS/headscale backends, declarative NixOS module, single-device MQTT-only identity) justify the maintenance burden of a 12-crate workspace with 3 tests — including the notification-transport fork (MQTT-only vs native-API for actionable notifications) that decides the feature table?

**Flavor:** dialectical
**Register:** advocate, deep inference

## What the corpus already said

The width sweep established the incumbent case strongly. go-hass-agent ([[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]], 7,022 words of architectural reference) is a dual-transport agent: mobile_app registration via the Native App Integration API (mandatory — "Go Hass Agent cannot run in an MQTT-only credentials [mode]. It makes use of the Native App Integration API that is not MQTT only") plus an optional MQTT v5 side that exposes controls. It ships a very large sensor catalogue (D-Bus/ProcFS/SysFS/Netlink-sourced: active app, desktop settings, MPRIS, webcam/mic-in-use, battery, memory, disk usage + rates + SMART, per-connection network state, per-core CPU frequency, power profile, screen lock, user sessions, OOM events, fwupd firmware security, hwmon), script sensors (cron-scheduled JSON/YAML/TOML), arbitrary-D-Bus MQTT controls, and a commands.toml vocabulary (button/switch/number). It is in nixpkgs proper at v14.15.1, current with upstream, building for all 24 Linux platforms ([[go-hass-agent-mynixos]]), with ~monthly cosign-signed releases and a data-race fix in v14.15.1 that exemplifies ongoing maintenance quality [[releases-joshuargo-hass-agent-github]]. lnxlink ([[lnxlink]], [[github-bkbillylnxlink-effortlessly-manage-your-linux-machine-using-mqtt-github]]) is the ~50-module MQTT-only community favourite: notify.send_message, idle, keep-alive, media, brightness, screen on/off, fullscreen, screenshot, audio-select, hotkeys, mouse, send-keys, Steam launcher, clipboard, current users, systemd unit management, GPU, restart-required, updates, disk IO, mounts, network speed, Bluetooth, WOL, BeaconDB location, camera/mic/gamepad in-use, webcam switch, docker, bash commands, LNXlink self-update, logging level — plus the canonical alternatives table. The post-mortem context: HASS.Agent (Windows, 1.3k stars) is the project whose Linux absence created this niche, forked after the original author's disappearance [[github-hass-agenthassagent-unofficial-development-project-for-the-hassagent-plat]]; its actionable notifications "work the same way as the companion apps do" — later confirmed as the `hass_agent_notifications` event round-trip [[actionable-notifications-hassagent]]. The community demand signal (WTH thread, Dec 2024) shows users want a macOS-app-like experience and name go-hass-agent/lnxlink/glances as the options [[wth-there-is-no-windows-and-linux-ha-app-similar-to-macos-month-of-what-the-heck]]. The corpus had already flagged go-hass-agent's documented split-brain: with MQTT on, "Go Hass Agent will appear in two places in your Home Assistant… under the Mobile App integration, which will show all the sensors… Secondly, under the MQTT integration… Unfortunately, due to limitations with the Home Assistant architecture, these cannot be combined in a single place." Ground truth on our side: [[repo-map-ha-linux-agent]] maps the 12-crate workspace (backend-hardware centrality 1.00, core/config.rs 0.96, backend-launcher 682 lines with 46 symbols) and the README declares the entity surface.

## What the new sources say

**1. HA's `notify.mqtt` entity platform exists and is the resolution of the notification-transport fork — for one-way notifications.** [[mqtt-notify-home-assistant]] (introduced HA 2024.5, "used by 48.6% of the active installations"): "The MQTT notify integration lets you send an MQTT message when the send_message action is called. This can be used to expose a action of a remote device that allows processing a message, such as showing it on a screen." An MQTT device can expose a notify entity via discovery with a `command_topic` (and optional `command_template` to shape the payload). Crucially, the config vocabulary contains ONLY: availability, command_template, command_topic, encoding, qos, retain, name, unique_id, device metadata. There is no actions schema and no event round-trip defined by the platform. So ha-linux-agent CAN get a first-class `notify.<device>` entity in HA — HA-side UX parity with the mobile_app notify service — without abandoning MQTT. But action buttons do not exist in this platform; any actionable-notification scheme over MQTT must be invented by the agent (publish actions as separate entities, e.g. buttons/selects, and have automations listen on those command topics rather than on a notification-action event).

**2. The actionable-notification round-trip is a native-API contract that no MQTT agent implements — and go-hass-agent doesn't either.** The canonical spec [[actionable-notifications-home-assistant-companion-docs]]: "When the notification action is performed, the mobile_app_notification_action event fires with the following data: { "event_type": "mobile_app_notification_action", "data": { "action": …, "reply_text": …, "action_data": …, "tag": … }}" — consumed via `wait_for_trigger` on the event. HASS.Agent (Windows) implements this pattern via its `hass_agent_notifications` event [[actionable-notifications-hassagent]]. go-hass-agent: issue #667 "[FEATURE REQUEST] Smart notifications with action buttons" (flaper87, opened Dec 2 2025, still OPEN, no assignee, no milestone, no linked PR): "The goal is to be notified on my laptop and be able to confirm/deny the notification so HA will take actions based on that… We should see the buttons to confirm / dismiss the notification just like for mobile devices" — and the buttons don't render [[feature-request-smart-notifications-with-action-buttons-issue-667-joshuargo-hass]]. Issue #926 "[FEATURE REQUEST] Add support for clear_notification" (LinqLover, Aug 2 2026, OPEN, no maintainer reply): "On my phone this works nice using clear_notification, but using go-hass-agent, clear_notification simply sends a second notification instead" [[feature-request-add-support-for-clear_notification-issue-926-joshuargo-hass-agen]]. So even the native-transport incumbent lags the companion-app notification contract, and both open feature requests have zero maintainer engagement. ha-linux-agent's current notify button (payload-becomes-body via mqtt.publish) is roughly feature-equivalent to lnxlink's `commands/notify` JSON ("Send rich desktop notifications via notify.send_message" [[lnxlink-pypi]]), which is one-way only.

**3. Headless/server deployment: both incumbents work headless, with documented friction.** go-hass-agent's maintainer, verbatim in discussion #387 (Jan 2025): "The systemctl service is primarily for 'headless' usage (i.e., servers) not running any desktop environment. If you run the agent both as a systemctl service and in your desktop, you'll have two instances sending duplicate data, which might not be desired" [[running-the-agent-as-a-service-and-tray-icon-joshuargo-hass-agent-discussion-387]]. A practitioner blog ([[how-to-see-your-ssdhdd-health-directly-in-home-assistant-diy-ideas]], provenance: hobbyist blog, Dec 2025) walks a working headless install on a Raspberry Pi: register with a long-lived token, `systemctl --user enable/start`, appears under the Mobile App integration — but SMART sensors materialise on x86 and NOT on Raspberry Pi OS, requiring a smartctl+jq+cron+command_line-sensor workaround. The older community record has a Proxmox user whose .deb "fails because of dependencies related to the GUI" asking for a core/GUI package split [[go-hass-agent-a-native-app-integration-for-desktop-laptop-devices-share-your-proj]] — the modern v14 packaging no longer has that problem (the DIY blog's ARM64 .deb installed cleanly headless). lnxlink ships an explicit headless mode: "The headless installation is used for linux environments that don't use a Graphical Interface like servers… When asked, it's recommended to answer false on install as a user service. sudo lnxlink -c config.yaml" — with the documented tax that "Some modules depend on graphical interface, so… you will have to find which ones stop lnxlink from starting and remove them from the config file" [[lnxlink-pypi]].

**4. No NixOS service module exists for either incumbent — audited absence, verified against the pinned nixpkgs tree.** Direct local verification against the flake-locked nixpkgs source (`nix eval nixpkgs#go-hass-agent.version` → "14.15.1"; grep of `nixos/modules/` for go-hass-agent and lnxlink → zero hits; lnxlink has no nixpkgs package at all — `nix eval nixpkgs#lnxlink.version` errors). The only HA-agent-adjacent NixOS module in the tree is glances ([[go-hass-agent-mynixos]] confirms the package; my grep confirms the module gap). Community NixOS users hand-roll buildGoModule derivations with explicit X11/mesa/glfw buildInputs (Azelphur's v13.2.7 derivation shared in the community thread [[go-hass-agent-a-native-app-integration-for-desktop-laptop-devices-share-your-proj]]). ha-linux-agent already ships a flake with a `nixosModules.default` exposing `services.ha-linux-agent.{enable,settings}` (README), and jupiter-os layers a `jupiter.services.haAgent` abstraction over it with per-app launcher profiles — including the `backlight` light-profile reshaping that produced the 2026-07-25 regression fix commits ("grouped profiles must yield exactly one entity" test in [[repo-map-ha-linux-agent]]'s backend-launcher). That declarative-fleet-module layer is genuinely absent upstream for both incumbents.

**5. Fleet ground truth: jupiterOS exercises exactly the features the incumbents don't have — and the "every host" ambition currently touches 4 of 6 hosts.** Read directly from /home/io/projects/jupiter-os: the agent is wired exclusively through `modules/services/ha-agent.nix` and `modules/desktop/tcxwave-kiosk.nix`, which enables it on the four TCx Wave kiosks (amalthea, adrastea, metis, thebe) with `pollIntervalSecs = 1` ("i want updates every second" — io), a launcher `screen-power` profile with `backlight = ""` (one dimmable HA light whose brightness writes go "straight to the backlight ha-linux-agent already has 0666 permission on"), a `customer-display` switch, and the dashboard-gaming module's session `select` (cage-tty1 + jupiter-arcade, mutual-exclusion group "session"). callisto (arcade-console + MQTT broker) deliberately does NOT run the agent ("cage + polkit + ha-agent wiring for a dashboard this host doesn't have" — arcade-console.nix comment); europa (ZFS NAS + headscale server + syncthing) doesn't run it despite backend-zfs/backend-syncthing/backend-headscale existing for exactly that host. The kiosk fleet's actual usage is: launcher mutual-exclusion groups + backlight-as-light + notify + the generic hardware sensors. No kiosk runs KDE (backend-kde has zero fleet consumers), only callisto's arcade session runs gamescope (kiosks' arcade mode does, via the shared dashboard-gaming modeSpecs), Lutris is installed via `jupiter.gaming.console` appCatalog but no kiosk configuration exercises backend-lutris buttons, and no host is running niri (backend-niri is speculative for a future desktop).

## Evidence synthesis

The feature-delta table resolves surprisingly favourably to ha-linux-agent *on the axes the fleet actually uses*, and unfavourably on nearly every axis it doesn't. Sensor coverage: go-hass-agent's catalogue is roughly 3-4× ha-linux-agent's generic backend (sysinfo CPU/memory/disk/load/uptime + logind idle/locked + UPower battery vs the incumbent's per-core frequencies, SMART, network per-link rates, OOM events, firmware security, etc.), and lnxlink adds ~50 modules including restart-required detection, pending-updates tracking, GPU usage, and systemd unit management — none of which ha-linux-agent has. Reliability/maturity: 3,909 commits and monthly cosign-signed releases vs 11 commits, 12 crates, and 8 test functions (5 launcher, 3 discovery — zero tests on backend-generic, backend-hardware, backend-zfs, backend-syncthing, backend-headscale, and the MQTT lifecycle itself; the sibling interim notes [[interim-report-mqtt-lifecycle-supervisor-spec]] and [[interim-report-fleet-service-model-by-host-class]] document verified lifecycle defects — permanent deafness after reconnect, hung-syncthing stalls, a false comment in ha-agent.nix:112 — that are the concrete substance of the user's "never reliable" complaint). Transport: go-hass-agent's dual-transport design forces the split-brain it documents itself (device appears under BOTH Mobile App and MQTT integrations, "cannot be combined in a single place"); ha-linux-agent's MQTT-only single-device identity is architecturally cleaner and the fleet's HA instance already depends on MQTT discovery. NixOS: neither incumbent has a nixpkgs service module, a community flake module, or even (lnxlink) a package; ha-linux-agent's flake module + jupiter-os's `jupiter.services.haAgent` abstraction is real, working, declarative fleet infrastructure today. Headless: both incumbents run headless (go-hass-agent natively as a user service with linger; lnxlink via sudo-install + manual module pruning) — so "works on servers" is NOT a differentiator, though "installs cleanly without pip/sudo/GUI-dep archaeology, declaratively, on a NixOS server" is.

The notification-transport fork resolves as follows: HA's notify.mqtt entity platform (HA 2024.5+) gives an MQTT-only agent a real `notify.<device>` service in HA — strictly better than ha-linux-agent's current raw button-with-empty-payload workaround. But actionable notifications — the mobile_app_notification_action event contract, the one thing HASS.Agent's fanbase cites as irreplaceable — are NOT implementable through the notify.mqtt platform's vocabulary, and go-hass-agent itself hasn't implemented them either (two open, maintainer-silent feature requests, #667 Dec 2025 and #926 Aug 2026). The only Linux-side implementations of the action round-trip are: (a) native-API agents (HASS.Agent is Windows-only; halinuxcompanion implements mobile_app with an HTTP server for the notify round-trip but is a 90-star Python project that itself lists "Move sensors to MQTT" as a to-do because "the limitations of the API" leave sensors "stuck" when the host goes offline — the LWT problem [[github-muniterhalinuxcompanion-homeassistant-linux-companion-github]]), or (b) an MQTT agent inventing its own action vocabulary (buttons/selects per notification, automations listening on command topics). Option (b) is fully in-pattern for ha-linux-agent's existing entity model and is what I'd commit to.

### Position A: Adopt go-hass-agent / lnxlink — mature, packaged, sensor-complete

The strongest version: go-hass-agent v14.15.1 is one `environment.systemPackages` line away on every host, is maintained at ~monthly cadence with signed releases, has 3,909 commits of sensor polish ha-linux-agent will spend months replicating (SMART with capability handling, per-core CPU frequency, network link rates, OOM events, session events), and its maintainer explicitly designs the systemd path for servers ("The systemctl service is primarily for 'headless' usage (i.e., servers)"). It refuses to run as root — matching NixOS's user-service-plus-linger pattern, and jupiter-os already runs ha-linux-agent exactly that way, so the deployment model transfers 1:1. lnxlink covers the desktop-feature long tail (~50 modules incl. idle, media, brightness, screenshot, audio-select, systemd unit management, restart-required) that neither go-hass-agent nor ha-linux-agent has, is MQTT-only like ha-linux-agent (single integration, no split-brain), and has an explicit headless install path. A 12-crate workspace with 8 test functions, 11 commits, verified reconnect deafness, and three backends explicitly flagged "Unverified in a live environment" (zfs, syncthing REST fields, lutris JSON field names — README's own words) is not a foundation; it's a prototype that the fleet's only four consumers use for one backend's mutual-exclusion select and a backlight light. The honest adopter's path: contribute a NixOS module + launcher-exclusion select upstream (go-hass-agent takes feature requests; the audio-select gap shows its control vocabulary CAN be extended), or wrap lnxlink.

### Position B: Build/fix ha-linux-agent — the jupiterOS-native layer is real and load-bearing

The strongest version: the fleet's actual deployed feature set is not "sensors + commands", it is the launcher mutual-exclusion session select (dashboard ↔ arcade on one tty1, HA-side select), the backlight-as-dimmable-light profile fused to tcxwave-screen-power.service, the customer-display switch, and 1-second polling — a control-plane surface expressing jupiterOS's own systemd session model, where the allowlist is declaratively generated from `jupiter.services.haAgent.launcherApps` in the host config. Neither incumbent can express this: go-hass-agent's commands.toml has button/switch/number only — its own user documented in Jan 2026 that a PipeWire output-device selector "can't be expressed" because "I can't see a means to do a drop-down selector box with multiple text items" [[go-hass-agent-a-native-app-integration-for-desktop-laptop-devices-share-your-proj]]; states are explicitly "not kept in sync" for non-button controls; and its group concept doesn't exist. lnxlink has a Steam launcher dropdown and systemd unit control but no mutual-exclusion semantics and no backlight-fused light entities tied to a fleet's power services. The single-device identity question is not cosmetic: go-hass-agent documents that its sensors (Mobile App) and controls (MQTT) land as TWO devices that "cannot be combined in a single place" — every HA dashboard/automation targeting a kiosk would see split state. And the ZFS/headscale/syncthing backends map 1:1 onto europa/callisto — the exact hosts the "run on EVERY host" ambition targets — where backend-zfs's pool-health binary_sensor ("the thing you'd actually want an HA alert on", per ROADMAP) has no incumbent equivalent (go-hass-agent has SMART-per-disk but not ZFS pool health; lnxlink neither). The maintenance-burden premise is also softer than it looks: 12 crates, but each backend is 100-330 lines and self-contained behind two small traits; the true debt is concentrated in core (agent.rs/discovery/config) and the unverified-CLIs, which is exactly what the sibling loci have already audited into a concrete fix list.

## Committed position

Improve, don't adopt — but with the honest concession table on the record, and with a scope discipline the current repo violates. The load-bearing reason: the deciding features for this fleet are not sensor breadth, they are the declarative launcher mutual-exclusion select + backlight-light session model, single-device MQTT identity, and the ZFS/headscale/syncthing backends for the server hosts — and the incumbents demonstrably cannot express the first (go-hass-agent's own users hit the missing-select wall in Jan 2026; its commands.toml vocabulary is button/switch/number with explicitly unsynced state), suffer the second by their own documentation (two HA devices, "cannot be combined"), and lack the third outright. Adopting would mean inheriting the split-brain and then building the missing launcher/session layer as configuration glued around an agent that doesn't natively model it — a worse maintenance position than owning 12 small crates whose worst defects are already audited. The concession table adopters can rightly press: ha-linux-agent's sensor coverage is ~25% of go-hass-agent's, its test suite is 8 functions vs 3,909 commits of maturity, three backends carry its own "unverified in a live environment" flags, the notification story is currently a payload-hack button rather than a notify entity, and lnxlink's 50-module long tail (idle time, media, keep-alive, screenshot, systemd units) shows how far "desktop companion" extends beyond jupiterOS's needs — none of which the fleet uses today, which is precisely why the build path is affordable. The improvement roadmap the evidence forces: (1) fix the audited MQTT lifecycle/supervisor defects first — no feature matters while the agent is intermittently deaf; (2) replace the notify button with a notify.mqtt discovery entity (HA 2024.5+, command_topic + command_template → title/message JSON) and, for actionable notifications, do NOT chase the native mobile_app contract — go-hass-agent hasn't either (#667/#926 open, maintainer-silent) — instead expose per-notification action buttons/selects over MQTT command topics, which is the only implementable round-trip on this transport; (3) prove backend-zfs/syncthing/headscale against europa/callisto and turn the "unverified" flags into test or at least live-verified status, because the every-host ambition currently runs on 4 of 6 hosts and the server hosts are where the remaining backends earn their keep; (4) freeze scope at the fleet's real entity surface — mutual-exclusion groups, backlight lights, notify, hardware sensors, ZFS/mesh/syncthing health — and let go-hass-agent remain the answer for sensor-breadth-desktop use-cases the fleet doesn't have.

- **Position:** ha-linux-agent should be improved rather than replaced, because the fleet's deciding capabilities (declarative launcher mutual-exclusion session select, backlight-light fusion, single-device MQTT identity, ZFS/headscale/syncthing server backends) are architecturally inexpressible in the incumbents, while the incumbents' advantages (sensor breadth, module long-tail) are in the fleet's unused 75%.
- **Confidence:** medium-high (~70%). The launcher-select and split-brain findings are verified against primary sources (maintainer docs, Jan 2026 user report, my own nixpkgs-tree grep); the counterfactual "adopt and extend upstream" path is plausible and would flip a maintainer-responsive upstream — but go-hass-agent's two open notification feature requests with zero maintainer engagement weakens that escape hatch.
- **Boundary conditions:** This verdict holds for a jupiterOS-internal agent whose consumers are 4 kiosks + (prospectively) 2-3 servers with a fixed, declaratively-generated entity surface. If the goal were a general-purpose Linux HA companion for desktops the family doesn't control, or if sensor breadth (SMART, per-core frequencies, network rates) became a fleet requirement, adopt would win — the maintenance asymmetry (11 commits vs 3,909) only pays off when the differentiating layer is genuinely unbuildable upstream, which is true for the launcher model only because go-hass-agent's control vocabulary lacks select/entities-with-synced-state.
- **What would change this position:** (a) go-hass-agent landing native select/dropdown controls with state sync or a NixOS service module with launcher-app semantics (its issue tracker shows demand); (b) evidence that the notify.mqtt platform cannot carry per-device notify entities cleanly in discovery (the page's discovery support is confirmed, so unlikely); (c) a maintained lnxlink NixOS module appearing; (d) the fleet's actual automations growing to need the desktop long-tail (idle/media/screenshot) that lnxlink already ships — at that point the build-vs-buy arithmetic shifts to adopting lnxlink for kiosks and keeping only the launcher layer bespoke.
- **Evidence weight:** 4 primary-source clusters support build (maintainer headless statement + commands.toml vocabulary + split-brain doc + my nixpkgs module-absence grep + the launcher-usage ground truth in jupiter-os); 2 clusters support adopt (sensor/release maturity from the README + releases note; lnxlink's 50-module catalogue); 2 clusters are neutral-but-constraining (notify.mqtt exists → MQTT-only is not notification-second-class for one-way; mobile_app actionable round-trip documented → the one native-API feature that matters has no Linux implementation at all, so MQTT-only loses little).

## Open questions

- Does HA's MQTT discovery support the notify component end-to-end from a device (the notify.mqtt page says "Alternatively, you can set it up via MQTT discovery" — I verified the claim, but ha-linux-agent publishing a working notify discovery payload is untested)?
- go-hass-agent's sensor behaviour on an impermanent, cage-kiosk NixOS host (no DE, no XDG portal) — how much of its catalogue silently degrades vs ha-linux-agent's deliberately-minimal generic backend? Untestable without a trial install on a kiosk; the DIY blog's Raspberry Pi SMART gap suggests platform-conditional degradation is real.
- lnxlink's real-world reliability on Wayland-only kiosks (its keyboard-hotkey module is X11-only; active-window on Wayland is a community module) — never assessed because no jupiterOS host needs those modules.
