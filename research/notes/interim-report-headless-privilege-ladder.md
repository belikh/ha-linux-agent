# Interim report: headless-privilege-ladder

**Locus question:** For the server hosts (europa, callisto), which monitoring channel + privilege design per subsystem — SMART via smartd -M exec hooks vs CAP_SYS_ADMIN/CAP_SYS_RAWIO ioctls, ZFS via zed events vs zpool polling, systemd unit health via D-Bus signals vs OnFailure= drop-in, backlight via udev uevents vs sysfs polling — and what capability set does the resulting unit need?
**Flavor:** technical (convergent)
**Register:** advocate, deep inference

## What the corpus already said

The width sweep established the capability matrix for SMART: [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]] is the kernel-source evidence — "if you read the source code for NVME_IOCTL_ADMIN_CMD it requires CAP_SYS_ADMIN, so there is nothing you can do except grant that" (nvme_user_cmd check in drivers/nvme/host/pci.c), with mrhotio's live Docker repro: `--cap-add SYS_RAWIO` gives "Read NVMe Identify Controller failed: NVME_IOCTL_ADMIN_CMD: Permission denied", while SYS_ADMIN suffices; CAP_SYS_RAWIO covers SATA/SCSI only. [[smart-archwiki]] documents smartd's `-M exec` hook channel (scripts receive `SMARTD_MESSAGE/SMARTD_FAILTYPE/SMARTD_ADDRESS` env vars) plus `-n standby,15,q` power-mode protection and `-s (S/../.././02|L/../../6/03)` self-test scheduling. [[smartdconf5-smartmontools-debian-testing-debian-manpages]] confirms the full `SMARTD_*` env-var surface. [[answers]] (superuser) settles the node choice: `/dev/nvme0` control node preferred for health ioctls, both nodes work on current kernels. [[best-nvme-ssd-health-monitoring-tools-9-options-ranked]] surveys the incumbent tooling (netdata 10s, zabbix 6h, smartctl_exporter 60s-scrape root-privileged) — everything the agent displaces is poll-based and root. [[indexhtml]] (Oracle ZFS states) defines the canonical health vocabulary: ONLINE/DEGRADED/FAULTED/OFFLINE/UNAVAIL/REMOVED with the roll-up rule (any DEGRADED/UNAVAIL top-level vdev ⇒ pool DEGRADED). [[how-to-monitor-zfs-pool-health-and-status-on-ubuntu]] gives the threshold bands (capacity warn 80%/crit 90%, frag 30%/50%, ARC hit <80%) and names zed as the event-driven channel. [[see-also-3]] (systemd.unit(5) DocBook source) documents the global drop-in pattern verbatim: `/etc/systemd/system/service.d/10-all.conf` with `[Unit] OnFailure=failure-handler@%N.service`, "systemd auto-removes the recursive self-dependency the template would otherwise create". [[how-to-get-notifications-if-a-systemd-unit-fails-help-kde-discuss]] shows the polling alternative and its drift traps (timestamped output always-differs). [[ipc-niri-msg-niri]] documents the niri event-stream protocol ("complete current state up-front, then follow up with updates") for kiosk state. [[sysfs-class-backlight]] + [[backlight-support-the-linux-kernel-documentation]] define brightness (requested, R/W) vs actual_brightness (readback truth, R/O), the uevents on actual_brightness, `backlight_force_update()` for hotkey re-sync, and the bl_power 0/4 rail-cut semantics. The claims tables for these notes (claims-*.json) carry 25 supporting claims, all directional-consistent, none contested — the open question was never *whether* these mechanisms exist but which channel+privilege combination each subsystem should use and what capability set the resulting unit needs.

## What the new sources say

**zed(8) man page** [[zed8in]] — ZED "monitors events generated by the ZFS kernel module. When a zevent (ZFS Event) is posted, the [ZED] will run any ZEDLETs... that have been enabled for the corresponding zevent class." Zedlet matching is filename-prefix-based ("the prefix all matches all zevents"), zevent nvpars arrive as `ZEVENT_`-prefixed environment variables, and — decisive for the privilege design — "The ZED requires root privileges" and "ZEDLETs must be owned by root. They must have execute permissions for the user, but they must not have write permissions for group or other." ZED is the push channel, but it is a root-owned one; an unprivileged agent cannot consume zevents directly (the zevent socket/nvlist is via /dev/zfs, root-only).

**NixOS services.zfs module source** [[zfsnix]] — the exact option surface jupiterOS can enable tomorrow: `services.zfs.zed.enableMail` (requires `services.mail.sendmailSetuidWrapper.enable` — an assertion the module enforces) and `services.zfs.zed.settings` (attrsOf str|int|bool|list str rendered into `/etc/zfs/zed.d/zed.rc`), plus stock zedlets installed via `environment.etc` (`statechange-notify.sh`, `resilver_finish-notify.sh`, `scrub_finish-notify.sh`, `all-syslog.sh`, ...). Critically, the zfs-zed.service unit ships inside the zfs package (`systemd.packages = [ cfgZfs.package ]`) and is wanted by zfs.target *unconditionally when ZFS is enabled* — jupiterOS does not need to define any unit for ZED, only to populate zed.rc and drop a custom zedlet. `services.zfs.autoScrub` exists with `interval` (systemd.time calendar, default monthly), `randomizedDelaySec`, and `pools` — europa's zfs-nas.nix already sets `services.zfs.autoScrub.enable = true`.

**Kernel backlight.c source** [[backlightc]] — the load-bearing code: `brightness_store()` → `backlight_device_set_brightness()`, which unconditionally calls `backlight_generate_event(bd, BACKLIGHT_UPDATE_SYSFS)` after every store attempt, and that helper ends with `sysfs_notify(&bd->dev.kobj, NULL, "actual_brightness")` plus a `KOBJ_CHANGE` uevent with `SOURCE=sysfs|hotkey|unknown`. So BOTH event channels are kernel-supported and free: (a) poll(2)/POLLPRI on the `actual_brightness` sysfs attribute, (b) a KOBJ_CHANGE uevent on the backlight kobject — and the hotkey path (`backlight_force_update()`) feeds the same generator, so platform-initiated brightness changes are signalled identically. The kernel emits the uevent even on failed stores, and its DOC comment states intent: "When the backlight changes this is reported to user-space using an uevent connected to the actual_brightness attribute."

**logind D-Bus API (docbook source of org.freedesktop.login1)** [[see-also-4]] — `org.freedesktop.login1.Session` has `SetBrightness(in s subsystem, in s name, in u brightness)` ("either backlight or leds"; "intended to be used by the desktop environment and allows unprivileged programs to access hardware settings in a controlled way"). But it's a *Session* method — there is no Manager-level SetBrightness — so a headless host with no active seat session has no logind path, and the doc names no polkit action for it. This is real but unsuitable as the fleet's primary write channel; it is a desktop-session nicety only.

**ArchWiki ZFS page** [[zfs-archwiki]] — the audited absence, confirmed: the page documents NO unprivileged zpool//dev/zfs read path. Zero occurrences of "unprivileged", "non-root", or "/dev/zfs"; every zfs/zpool command shown at a `#` root prompt; no `zfs` group recipe; no chmod/chgrp on ZFS device nodes. The page's ZED section defers email wiring to zed.rc and nothing else. Combined with zed(8)'s "ZED requires root privileges", the audit concludes: **on Linux there is no documented, supported unprivileged zpool read path** — `zpool list/status` requires opening /dev/zfs, which is root-only by default.

**node_exporter zfs_linux.go source** [[zfs_linuxgo]] — the workaround path, precisely: pool state comes from `/proc/spl/kstat/zfs/<pool>/state` (`linuxZpoolStatePath = "/*/state"`), parsed as the first-line state word and mapped onto the fixed enum `{"online","degraded","faulted","offline","removed","unavail","suspended"}`. Per-subsystem stats (`abdstats`, `arcstats`, `dbufstats`, `dmu_tx`, `dnodestats`, `fm`, `vdev_cache_stats`, `vdev_mirror_stats`, `xuio_stats`, `zfetchstats`, `zil`), per-pool `/*/io`, and per-dataset `/*/objset-*` are all plain `os.Open()` procfs reads — no /dev/zfs, no ioctl, no privilege mechanism anywhere. All ZFS telemetry node_exporter exposes — including per-pool state — is readable unprivileged from procfs (subject to distro procfs modes; NixOS defaults leave /proc/spl/kstat/zfs world-readable 0444).

## Ground truth from the two repos and a live fleet host (highest-tier evidence)

**Live ground truth from callisto (10.1.1.3, the actual hardware class):** I ran the D-Bus experiments on this dev box, which IS callisto. (1) `busctl --system monitor` (BecomeMonitor) is polkit-denied for io — but that is only the *eavesdropping* API. (2) The normal match-rule subscription works unprivileged: `mgr.Subscribe()` succeeded as io, and a `JobRemoved` signal for logrotate.service (fired by the 22:00 logrotate.timer) was **delivered to an unprivileged subscriber** — "JobRemoved: 1 | PropertiesChanged: 27 | job: unit=logrotate.service result=done | RESULT: DELIVERY TO UNPRIVILEGED SUBSCRIBER CONFIRMED". Note the systemd lazy-signals subtlety this exposed: Manager signals like JobRemoved/UnitNew are NOT emitted until the client calls `Subscribe()` — the D-Bus design must call Subscribe() at startup (it's a plain method call, not polkit-gated). PropertiesChanged (org.freedesktop.DBus.Properties) fires without Subscribe. (3) Unprivileged job *creation* is polkit-gated (`systemd-run`/`systemctl restart` denied for io) — but jupiterOS already ships the exact fix: `polkitUnitRule user unit` in modules/lib.nix:194 (action `org.freedesktop.systemd1.manage-units`, scoped to one unit + one user), applied for `tcxwave-screen-power.service` and `tcxwave-cdp-anim.service`. (4) `udevadm monitor` (kernel uevent netlink socket, CTLNL group 1) works unprivileged — io receives `KERNEL - the kernel uevent` events with no root and no group membership. This is the fourth confirmed-unprivileged channel.

**Fleet reality (hosts audited):** europa is the only true ZFS server (HPE MicroServer Gen10, rpool + hand-built 16.4T two-disk-mirror `tank`, `services.zfs.autoScrub.enable = true`, smartd via `jupiter.storage.smartMonitoring.enable = true` at 1800s interval, `-a (S/../.././02|L/../../7/03)`); its SATA HBA (Marvell 88SE9230) and WD 18TB drives + one OS SSD are all SATA (no NVMe) — but callisto has "repeatedly destroyed local NVMe drives, so it has none", its own root is ext4-over-iSCSI from europa's zvol, and it runs mqtt (the broker), postgres, headscale-target, syncthing-hub (europa), arcade, model-router, dsh, opencode-web, open-design, procurement-mcp, nom-web. The server set is europa (ZFS NAS + iscsi target + syncthing + headscale + harmonia) and callisto (iSCSI-root compute + broker + postgres + tunnel host). **Kiosks** (amalthea/adrastea/metis/thebe) are the TCx Wave units with backlight + cage + MSR.

**Agent reality (crates audited):** backend-zfs polls `zpool list -H -p -o cap <pool>` + `zpool list -H -o health <pool>` per pool per tick (requires zpool on PATH + /dev/zfs access ⇒ root-equivalent today); backend-hardware does raw sysfs writes for brightness/governor/EPP; backend-launcher drives `systemctl is-active/start/stop` and raw sysfs brightness for its backlight profiles; backend-generic already has zbus (workspace-pinned **zbus 4**, tokio feature) for login1/UPower/Notifications on the system bus; backend-headscale shells to `tailscale status --json`; backend-syncthing uses the REST API with X-API-Key. The agent already runs as a *user* service (`systemd.user.services.ha-linux-agent`, `ConditionUser = "io"`, linger) per ha-agent.nix:104, with the root-owned sysfs-chmod oneshot at ha-agent.nix:117-124 as its privilege crutch — and the sibling investigator proved that crutch broken (chmod 0664 sets group-root write; io's groups are users+wheel only; no host adds io to video) so brightness/governor/EPP writes silently fail EACCES today, with only a `warn!` in write_sys_file (backend-hardware/src/lib.rs:108-111) and tcxwave-kiosk.nix:199 still claiming "0666 permission" (ha-agent.nix actually ships 0664 — the comment drift itself evidences the fragility).

## Evidence synthesis

### SMART (disks): smartd -M exec hook, not agent-side ioctls

The capability matrix from [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]] is kernel-source-confirmed: NVMe SMART requires CAP_SYS_ADMIN (NVME_IOCTL_ADMIN_CMD), SATA/SCSI requires CAP_SYS_RAWIO, and mixed fleets need both — two of the most powerful capabilities in the set (SYS_ADMIN is the "new root" catch-all). Against that, smartd already runs as a root daemon on europa (`jupiter.storage.smartMonitoring.enable = true`, 30-min interval, scheduled self-tests) and [[smart-archwiki]] documents its `-M exec` channel: the hook script receives the full event context via SMARTD_MESSAGE/SMARTD_FAILTYPE/SMARTD_DEVICE/SMARTD_TFIRSTEPOCH env vars. The smartd path needs ZERO additional privilege on the agent: smartd (root) detects the failure event, the exec hook (a tiny root-owned script, the smartd-warning.d convention) writes into a world-writable spool or publishes straight to MQTT as a low-priv user, and the agent picks it up. The agent-side-ioctl alternative would require AmbientCapabilities=CAP_SYS_ADMIN on the agent unit for NVMe hosts — a capability grant that the evidence (Scrutiny's own maintainer conceding "there is nothing you can do except grant that") marks as a last resort. For the fleet's actual disks (europa: 3× SATA; callisto: none; kiosks: SATA), even the raw capability need is CAP_SYS_RAWIO-only — but the event-driven smartd design wins regardless because europa ALREADY runs smartd; wiring its output costs one script, while displacing it costs a capability grant and a polling loop. Design: keep smartd as the detector; add a `jupiter.storage.smartMonitoring.hook` option (or a fixed /usr/share/smartmontools/smartd_warning.d/ entry) that either (a) drops a JSON line into /var/lib/ha-linux-agent/smartd/ for the agent to pick up, or (b) publishes directly to the ha-linux-agent MQTT user. Agent-side smartctl polling (the smartctl_exporter shape, 60s [[github-prometheus-communitysmartctl_exporter-export-smartctl-statistics-to-prome]]) remains a kiosk option needing CAP_SYS_RAWIO via AmbientCapabilities — but the kiosks' SanDisk Z400s are already covered if kiosks enable smartMonitoring too. Prescriptive detail: smartd.conf `-n standby,15,q` guards against waking spun-down disks (power events on europa's WD18T), and the hook must be executable, root-owned, no group/other write ([[smart-archwiki]]).

### ZFS: two-channel — procfs state for the agent, zed for the push alerts

[[zfs-archwiki]] + [[zed8in]] establish that zpool CLI and ZED are both root-only channels on Linux (audited absence: no unprivileged /dev/zfs path documented anywhere; "The ZED requires root privileges"). But [[zfs_linuxgo]] shows the unprivileged path node_exporter already uses: `/proc/spl/kstat/zfs/<pool>/state` (first-line state word), `/*/io` for I/O, `arcstats` for ARC hit ratio, all plain procfs reads. The current backend-zfs (zpool list -H polling) therefore embeds an avoidable root requirement. Design: (a) REWRITE backend-zfs to read `/proc/spl/kstat/zfs/<pool>/state` + capacity from `zfs list` (or better, `/*/io` + dataset space via procfs/objset) — the agent needs NO capability, NO group, NO sudo for pool state; (b) make ZED the push channel for transitions (statechange-notify.sh zedlet is already installed by nixpkgs' zfs module into /etc/zfs/zed.d) with a custom zedlet that hands the zevent to the agent (same spool/MQTT trick as smartd — a root-owned zedlet writing a line the unprivileged agent reads). This gives event-driven alerts (zed) + unprivileged state polling (procfs) with no CAP_SYS_ADMIN anywhere. Thresholds from [[how-to-monitor-zfs-pool-health-and-status-on-ubuntu]]: capacity warn 80%/crit 90%, fragmentation 30%/50%, ARC hit <80%, any non-zero CKSUM delta, and `zpool status -x`-equivalent state != ONLINE as binary_sensor problem. NixOS surface: `services.zfs.zed.settings` for zed.rc values + a custom zedlet via environment.etc (the module installs stock zedlets already); zfs-zed.service is already wanted by zfs.target on europa automatically. EUOPA-ONLY (and any future ZFS host); callisto's ZFS exposure is only the iSCSI zvol (no local pool — backend-zfs detects() returns false there, correct today).

### systemd unit health: D-Bus signals with Subscribe(), not OnFailure drop-ins

The live experiment on callisto PROVED the unprivileged path: `Subscribe()` + match-rule on JobRemoved/UnitNew works for io with zero polkit grants, and a real timer-fired job was delivered in seconds. The OnFailure= global drop-in alternative ([[see-also-3]], the `failure-handler@%N` template pattern) is systemd-native but writes root-owned files into /etc/systemd/system/service.d/ — the agent would need root (or a root-owned activation script) to install it, and every unit then depends on the template being present. The D-Bus channel needs NO privilege, NO file writes, and is already expressible: backend-generic uses zbus 4 today and the systemd Manager proxy needs only `Subscribe()` (a plain method call, polkit-free) plus a JobRemoved receiver. The kiosk's launcher backend already has the polkitUnitRule precedent for the one gap (unprivileged start/stop of SPECIFIC units — polkitUnitRule user unit in modules/lib.nix:194, the exact mechanism the launcher backend needs for scope=system apps). Design: a new backend-systemd (or extend backend-generic) with Subscribe() + JobRemoved/UnitNew/PropertiesChanged receivers mapping unit state transitions to HA binary_sensors per watched unit (mqtt, postgres, syncthing, headscale, iscsi-target, llama-server, model-router, nom-web, cloudflare-tunnel, dsh — the module inventory), plus Subscribe-driven UnitPropertiesChanged for substates (activating, deactivating, failed). PropertiesChanged needs no Subscribe call and covers the "watch state changes" case even more directly than JobRemoved for fine-grained state. Caveat from the probes: `busctl --system monitor` is denied — the agent must use match-rule subscription (zbus receive_signal / MessageStream with a match), never BecomeMonitor.

### Backlight: sysfs writes + POLLPRI/uevent reads, no logind, no chmod hack

[[backlightc]] proves the kernel emits BOTH a KOBJ_CHANGE uevent (SOURCE=sysfs|hotkey) AND sysfs_notify on actual_brightness on EVERY store attempt, and the hotkey path feeds the same generator — so hotkey changes are signalled too. The write channel stays raw sysfs brightness (1-line fs::write, already in backend-hardware/launcher) — the fix for the broken 0664 chmod is NOT another chmod but AmbientCapabilities: the write needs CAP_SYS_ADMIN-equivalent privilege... actually no — sysfs node permissions are ordinary DAC; a group write or a tiny polkit-gated helper is enough. Three options evidenced: (1) **udev rule GROUP="video" + add io to video** (matching the kiosk MSR rules in tcxwave-power-tuning.nix:176-180 — the fleet's own existing pattern for exactly this problem class, video-group hidraw access for the MSR): one udev rule for SUBSYSTEM=="backlight" RUN/GROUP + one extraGroups entry; this is the minimal-change, kernel-idiomatic fix. (2) logind SetBrightness — real API [[see-also-4]] but Session-scoped (no headless path, no polkit action named, TakeControl prerequisite unclear) — rejected for kiosks too because the kiosk agent is a user service whose session the compositor owns, and SetBrightness gives no benefit over sysfs when io can just be in video. (3) systemd backend with AmbientCapabilities — overkill for a DAC problem. For the READ side (brightness state sync with hotkeys), the agent should listen to the KOBJ_CHANGE uevent via the kernel netlink socket (udev backend crate or the same socket udevadm monitor uses — confirmed unprivileged on callisto) or inotify/POLLPRI on actual_brightness, replacing the 1s-poll-everything kiosk default (tcxwave-kiosk.nix:207-209, "i want updates every second") with push — the exact niri-IPC lesson from [[ipc-niri-msg-niri]] ("complete current state up-front, then follow up with updates... no polling is needed").

### The capability set the resulting unit needs: NONE (system-bus D-Bus + procfs + spool files + polkit-scoped systemctl)

Summing the four subsystems under the event-driven design: SMART events arrive via the smartd hook's spool file (readable) or direct MQTT publish; ZFS state via /proc/spl/kstat/zfs (world-readable) + zedlet spool/MQTT; unit health via system-bus D-Bus signals (unprivileged, proven live); backlight via sysfs (group video, udev-set) + uevent netlink (unprivileged). The agent unit needs: **no AmbientCapabilities, no sudo, no root** — the complete privilege surface is (a) system-bus socket access (any user), (b) /run/user/1000/bus reachability for session-bus features (notifications) on hosts with an active session — the user-service model's own requirement — and (c) the polkitUnitRule pattern for the specific units the launcher may start/stop. If a future NVMe host wants agent-side SMART polling, THAT host's unit alone adds AmbientCapabilities=CAP_SYS_ADMIN CAP_SYS_RAWIO per the Scrutiny evidence — and that grant should be opt-in per host class, not fleet-wide. This directly replaces the broken sysfs-chmod workaround (delete ha-linux-agent-sysfs-perms entirely; it grants group-root write to nodes whose only group is wheel-not-root... precisely: chmod 0664 makes them group-writable by group `root`, which io is not in — the writes fail EACCES today) with a working udev GROUP + membership design. On server hosts (europa/callisto) where nothing ever writes sysfs, the same agent binary needs nothing at all.

## Committed position

The four subsystems resolve cleanly onto a **zero-capability, event-driven design** where the monitoring channel is always the push one and the privilege is always the least the kernel exposes: SMART = smartd `-M exec` hook (smartd is already the privileged detector on europa — the agent merely consumes its events, no CAP_SYS_ADMIN/CAP_SYS_RAWIO anywhere); ZFS = `/proc/spl/kstat/zfs/<pool>/state` procfs polling (unprivileged, node_exporter-proven) for state plus a custom zedlet via `services.zfs.zed.settings` as the push channel for transitions (ZED is root-only and already auto-enabled on ZFS hosts — it publishes INTO the agent's channel rather than the agent gaining privilege); systemd unit health = system-bus D-Bus `Subscribe()` + JobRemoved/UnitNew/PropertiesChanged match-rule subscription (live-proven unprivileged on callisto — logrotate.timer's job was delivered to io with zero grants, and note the Subscribe() prerequisite for Manager signals that PropertiesChanged doesn't need); backlight = raw sysfs brightness writes with the privilege fixed by a udev `GROUP="video"` rule + io-in-video membership (the fleet's own MSR-rule pattern), with state sync via the kernel's own KOBJ_CHANGE uevent + sysfs_notify on actual_brightness (backlight.c-proven on every store attempt, hotkey path included) replacing the 1s poll-everything default. The load-bearing reason: every alternative channel that surfaced in the evidence (agent-side NVMe ioctls, zpool CLI, OnFailure drop-ins, logind SetBrightness) requires either CAP_SYS_ADMIN (the Scrutiny "nothing you can do except grant that" capability), root-owned filesystem writes, or a Session-scoped API with no headless path — while the chosen four channels all demonstrably work for an unprivileged user, three of them proven live on fleet hardware or kernel-source-verified within this investigation. The scoping premise: the ZFS/zed design is europa-only (callisto has no local pool), so nothing here needs to be host-general to be fleet-safe.

**Position:** For europa/callisto/kiosks adopt the event-driven, zero-capability matrix — smartd -M exec hooks (agent consumes), ZFS via /proc/spl/kstat/zfs state + zedlet push (agent stays unprivileged), unit health via system-bus Subscribe()+match rules (unprivileged, live-proven), backlight via udev video-group sysfs + uevent sync — and delete the broken sysfs-chmod oneshot; agent-side ioctls (CAP_SYS_ADMIN for NVMe) only ever as a per-host opt-in for hosts with local NVMe and only if agent-side SMART polling is genuinely wanted over smartd's existing coverage.

- **Confidence:** high (75–85%). The kernel-source evidence (backlight.c, NVME_IOCTL_ADMIN_CMD), the live D-Bus/uevent proofs on callisto, the audited absence of an unprivileged /dev/zfs path across ArchWiki + zed(8), and the direct repo audit (smartd already on europa, backend-zfs's zpool CLI, the ha-agent.nix chmod) are all primary-source or measured; what keeps it from >85% is the two unfetched upstream docs (ArchWiki ZED page, zed.rc itself) and no live ZFS host to verify /proc/spl/kstat/zfs readability on this exact NixOS config (the procfs mode claim is node_exporter-source + NixOS-default inference, not measured on europa).
- **Boundary conditions:** This matrix is for jupiterOS's actual host classes — europa (SATA ZFS NAS with smartd running), callisto (no local disks, broker+postgres host), TCx kiosks (SATA + backlight + cage). A future host with local NVMe + no smartd flips the SMART row to AmbientCapabilities=CAP_SYS_ADMIN (per-host opt-in); a future Wayland-desktop host with an active seat session makes logind SetBrightness viable as a nicety but not the primary; a ZFS host whose /proc/spl/kstat/zfs is mode-restricted (NixOS default is world-readable but it's not an ABI promise) flips the ZFS state row to the zedlet-push-only design. The D-Bus row assumes systemd ≥ v252 with Subscribe() (all NixOS 26.05 hosts qualify) and match-rule subscription (not BecomeMonitor, which is polkit-denied — measured).
- **What would change this position:** (1) A live europa test showing /proc/spl/kstat/zfs/<pool>/state is NOT world-readable under this NixOS config (then the zedlet push channel becomes the sole ZFS path and procfs polling drops). (2) Evidence that smartd's -M exec environment loses the device/failure context on NixOS specifically (then a smartd_warning.d consumer or a direct smartctl --json interval poll with CAP_SYS_RAWIO on SATA-only hosts becomes the fallback). (3) Discovery of an unprivileged /dev/zfs read path in newer OpenZFS (e.g. a zfs group + ACL change) — then zpool CLI could replace procfs parsing, though the event design would still prefer zed. (4) The udev GROUP="video" route failing on the kiosks' acpi_video0 device (driver-specific permission quirks) — then the launcher backend's sysfs write moves behind a tiny polkit-gated helper or the touch-wake unit's own root ExecStart.
