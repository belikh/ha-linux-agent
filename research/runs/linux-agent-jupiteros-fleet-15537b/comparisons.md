# Cross-locus comparisons

The six investigators' committed positions, side-by-side:

- **Service model** ([[interim-report-fleet-service-model-by-host-class]]): ONE system service per host, User=io, host-class-parametrised AmbientCapabilities (CAP_SYS_ADMIN+CAP_SYS_RAWIO for SMART on europa), explicit DBUS_SESSION_BUS_ADDRESS Environment on lingered hosts; retire the user-unit shape entirely. The two facts that were supposed to force the user/system split both dissolved (session bus reachable from User= system service via jupiterOS's own mkSessionLauncher pattern; the user-unit restart gap confirmed current as of Oct 2025).
- **MQTT lifecycle** ([[interim-report-mqtt-lifecycle-supervisor-spec]]): ConnAck-driven supervisor — re-subscribe + re-assert availability on every ConnAck, birth-triggered republish with 0-30s jitter, SIGTERM offline-then-disconnect, cap-0/timeout-bounded publishes, per-backend isolation, empty-payload decommission, paired callisto mosquitto changes (max_queued_messages ≥ 4× fleet inventory, persistence true). Commits AGAINST clean_session=false (stale command replay has no TTL).
- **Adopt vs build** ([[interim-report-adopt-vs-build-honest-verdict]]): Improve, don't adopt — the deciding features (launcher mutual-exclusion select, backlight-light session model, single-device MQTT identity, ZFS/headscale/syncthing server backends) are architecturally inexpressible in the incumbents (go-hass-agent's control vocabulary is button/switch/number with unsynced state; split-brain device identity self-documented). Concession table on record: ~25% sensor coverage vs go-hass-agent, 8 tests vs 3,909 commits, three unverified-live backends, notify-as-payload-hack. Notifications resolved: notify.mqtt (HA 2024.5+) for one-way parity; actionable notifications have no Linux implementation anywhere (go-hass-agent #667/#926 open, zero maintainer engagement) so MQTT-only loses almost nothing.
- **Privilege ladder** ([[interim-report-headless-privilege-ladder]]): ZERO-capability, event-driven matrix — smartd -M exec hooks (smartd already privileged on europa), ZFS procfs + zedlet bridge, system-bus D-Bus match-rule subscription (live-proven unprivileged on callisto), backlight via udev GROUP="video" + io-in-video with KOBJ_CHANGE sync. No AmbientCapabilities, no sudo, no root — and delete the broken sysfs-chmod workaround. The ZFS design is europa-only (callisto has no local pool).
- **rumqttc fitness** ([[interim-report-rumqttc-dependency-fitness]]): KEEP rumqttc 0.24.0 (measured: Cargo.lock pins exactly 0.24.0). Re-subscription will never come from the library (PR #1052 open/unreviewed/v5-scoped; Paho also leaves re-subscription application-owned). The "v3.1.1-only" locus premise is factually wrong — 0.24.0 ships a full v5 module with message/session expiry. 0.24→0.25.1 upgrade measured painless (check/test/clippy exit 0) but zero relevant delta — don't churn. Endorses the clean_session=true ConnAck supervisor without reservation.
- **Testing gate** ([[interim-report-testing-gate-for-hardware-daemon]]): 7-step ladder — clippy fix (backend-hardware:117) → craneLib.cargoTest (flake check currently runs ZERO tests; the real count is 8, not 3) → sysfs-root injection + tempfile fixtures → Agent::run seam extraction → mosquitto-SUBPROCESS harness (testcontainers REJECTED on measured fleet ground truth: no container runtime anywhere) with 5 defect-named regression tests → private dbus-daemon harness → runNixOSTest cribbed from nixpkgs' own mosquitto test.

## Tension 1: AmbientCapabilities vs the zero-capability ladder

- **Service model** ([[interim-report-fleet-service-model-by-host-class]]) commits: system service with `AmbientCapabilities=CAP_SYS_ADMIN CAP_SYS_RAWIO` where SMART is enabled (europa).
- **Privilege ladder** ([[interim-report-headless-privilege-ladder]]) commits: zero capabilities anywhere — SMART via smartd `-M exec` hooks (smartd already runs privileged; the agent only consumes SMARTD_* env-var events), backlight via udev `GROUP="video"` + group membership, unit health via unprivileged system-bus D-Bus.
- **The cross-locus dynamic:** Direct conflict on the same design point. Both converged on the system-service/User=io shape, but the service-model investigator assumed SMART requires in-process ioctls while the privilege-ladder investigator proved (kernel source + live busctl experiments on callisto) that every subsystem has an unprivileged channel — and that the chmod workaround the service model would replace is not just ugly but *broken today* (it grants group-root write; io's only group is wheel, so brightness writes fail EACCES silently).
- **How the draft should engage:** The reliability/fleet section must present the privilege ladder's zero-capability matrix as the design, and the service-model's AmbientCapabilities clause as the explicitly-rejected alternative (with the Scrutiny "grant CAP_SYS_ADMIN or use the hook" fork named). Privilege-ladder evidence is live-proven; the draft weights accordingly.
- **Calibration:** Service model: ~20-25% residual risk on notification-from-system-service live test (unrelated to capabilities). Privilege ladder: high confidence, three of four channels proven live or kernel-source-verified; the one inference leg (procfs ZFS state readability on europa) is a single SSH command away.

## Tension 2: The v3.1.1 foreclosure — corrected by measurement

- **MQTT lifecycle** ([[interim-report-mqtt-lifecycle-supervisor-spec]]) commits: empty-payload decommission "since v3.1.1 forecloses message expiry" — treating the v4-only surface as a design constraint.
- **rumqttc fitness** ([[interim-report-rumqttc-dependency-fitness]]) commits: the foreclosure claim is factually wrong for 0.24.0 — the v5 module (message_expiry_interval, session_expiry_interval) ships inside the pinned version; the workaround is optional hardening, not forced.
- **The cross-locus dynamic:** A factual correction that strengthens rather than undermines the core convergence: both commit to the identical ConnAck-driven supervisor on clean_session=true. The rumqttc investigator explicitly endorses the spec "without reservation" and strengthens it — the raw ConnAck match is the *permanent* shape of rumqttc's design, not a version workaround.
- **How the draft should engage:** The MQTT-lifecycle section presents the ConnAck supervisor as mandatory and unconditional; the v5 module appears as a named future option (with the spike test the fitness investigator prescribed) rather than as the reason for the workaround. Never present "rumqttc is v3.1.1-only" as fact — it is false for the pinned version.
- **Calibration:** Fitness verdict is measurement-backed (Cargo.lock pin verified; the 0.25.1 upgrade test was run and reverted). The supervisor spec is high-confidence on the two root-cause bugs (file:line + rumqtt #250) — both investigators name the same flip condition: upstream shipping reconnect signalling.

## Tension 4: Corpus consensus vs fleet ground truth on the test harness

- **Testing gate** ([[interim-report-testing-gate-for-hardware-daemon]]) commits: REJECT testcontainers — no container runtime exists on any jupiterOS host or Nix remote builder (audited `/etc/nix/machines`, host configs); use a mosquitto-subprocess harness instead.
- **The width corpus** (4-source consensus claim): Mosquitto testcontainers is the right primitive for reliable, parallel-safe MQTT broker tests.
- **The cross-locus dynamic:** A meta-level tension the draft itself should model: web consensus optimises for the generic case; fleet ground truth overrides it. The consensus claim is correct for Docker-equipped CI; it is dead on arrival for this fleet and this flake. The testing investigator also corrected the run's own premise: the workspace has 8 tests (not 3 — the original audit missed feature-gated `#[cfg(test)]` modules), and `nix flake check` runs ZERO of them because cargoTest was never wired.
- **How the draft should engage:** The testing section presents the 7-step ladder with the subprocess harness, names the testcontainers consensus and the specific ground-truth fact that rejects it, and corrects the 3-tests figure to 8 (while noting the deeper truth: the count matters less than the fact that none of them run in CI).
- **Calibration:** High confidence — the container-runtime absence is directly audited, and the craneLib.cargoTest gap is visible in flake.nix.

## Tension 5: The notification session-bus residual risk vs the notify.mqtt resolution

- **Service model** ([[interim-report-fleet-service-model-by-host-class]]) commits: DBUS_SESSION_BUS_ADDRESS Environment on lingered hosts, flagging notification-delivery-from-a-system-service as the single ~20-25% residual risk of the whole position.
- **Adopt vs build** ([[interim-report-adopt-vs-build-honest-verdict]]) commits: replace the notify button with a notify.mqtt discovery entity (HA 2024.5+, command_topic + command_template) — solving the HA→agent delivery leg entirely over MQTT.
- **The cross-locus dynamic:** Partial complication, easy to misread as full resolution: notify.mqtt fixes the *transport into the agent* (no native API needed), but the agent's *last mile* — calling org.freedesktop.Notifications on the session bus — still needs the Environment block the service model prescribes. The adopt-vs-build resolution reduces the risk surface (one documented MQTT path instead of an undocumented payload hack) without eliminating the session-bus dependency; the residual risk stands for hosts with desktops, and vanishes for headless hosts where the notification backend should simply not enable.
- **How the draft should engage:** The roadmap's notify.mqtt item must be presented together with (not instead of) the service model's Environment block, and the one live test that would retire the residual risk (send a notification from HA to a User=io system service on a kiosk) belongs in the roadmap's verification checklist.
- **Calibration:** Service model flags it medium-confidence-untested; adopt-vs-build's notify.mqtt is documentation-backed (HA 2024.5+). Both name the same final arbiter: a live test on amalthea.
