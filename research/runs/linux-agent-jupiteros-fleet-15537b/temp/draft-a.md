# Fix the Lifecycle, Then Fleet It: Why "Never Reliable" Is Two Located Bugs, Not a Lost Cause

**Executive summary — the answer first.** ha-linux-agent's reputation for being "never reliable" is not a vague aura of sloppiness; it resolves to a small set of precisely-diagnosed, file:line-located MQTT lifecycle defects, and the presenting symptom is live right now: the four TCxWave kiosks' entities read UNAVAILABLE on callisto's Home Assistant instance at this moment — the exact "never reliable" complaint, observed live [[interim-report-mqtt-lifecycle-supervisor-spec]]. The agent subscribes to its command topics exactly once in a fire-and-forget setup task (`crates/core/src/agent.rs:134-138`) and swallows every ConnAck event in its poll loop (`Ok(_) => {}` at `agent.rs:190`) — so after the first broker restart or network blip, the client library reconnects forever but never re-establishes subscriptions [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]], leaving every agent fleet-wide permanently deaf. A second, mirror-image bug publishes retained availability "online" exactly once (`agent.rs:139-144`), so after the same blip every host looks dead in HA while its telemetry still flows — sensors that lie rather than sensors that vanish. The fix is a ConnAck-driven supervisor (re-subscribe + re-assert availability + birth-triggered rediscovery on every connect), it is implementable on the pinned rumqttc 0.24.0 without any dependency churn, and it is the same bug the incumbent Windows agent shipped and fixed (HASS.Agent 2.1.1: "MQTT autodiscovery messages were not republished after connection was lost and recovered" #230) [[releases-hass-agenthassagent-github]]. The correct course is therefore ordered and non-negotiable: fix reliability first, deploy fleet-wide second via one system service per host with a role-driven NixOS module, and add features third — the exact ordering the investigations converged on independently [[interim-report-fleet-service-model-by-host-class]]. Adoption is the wrong move — the incumbents cannot express the fleet's deciding features (a launcher mutual-exclusion select with synced state, a single-device MQTT identity, ZFS/headscale/syncthing server backends), a verdict their own documentation seals [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]].

## 1. Current State: A Verified Reliability Audit

The audit ground truth comes from the codebase itself, observed directly rather than inferred: 12 crates, 11 commits, a 198-line `Agent::run()` in `crates/core/src/agent.rs` that is a test-unfriendly monolith, and a `repo-map` centrality analysis that puts `backend-hardware/src/lib.rs`, `core/src/config.rs`, and `backend-gamescope/src/lib.rs` at the top of the reference graph [[repo-map-ha-linux-agent]]. Three structural findings define "sloppy state" precisely.

**Finding one: the reliability defects are located, not diffuse.** The defect audit names nine, each with file:line evidence [[interim-report-mqtt-lifecycle-supervisor-spec]]:

| Defect | Location | Failure mode |
|---|---|---|
| D1 Deafness after reconnect | `agent.rs:134-138` subscribe-once; `agent.rs:190` ConnAck swallowed | Agent reconnects but never re-subscribes; commands never arrive again |
| D2 Availability stuck offline | `agent.rs:139-144` "online" published once; LWT at `agent.rs:55-60` retained "offline" | Host reads dead in HA while telemetry flows |
| D3 No birth republish | absent | HA restart strands entities until manual re-send |
| D4 Unbounded stale queue | `AsyncClient::new(opts, 64)` at `agent.rs:62` | Stale state burst replays on reconnect |
| D5 Hung-backend starvation | `backend-syncthing/src/lib.rs:75,98` — reqwest client with **no timeout** (reqwest has none by default); all backends polled sequentially at `agent.rs:154-157` | One hung syncthing daemon freezes every sensor on the host; commands awaited inline at `agent.rs:185` block the poll loop, stop keepalives, and flap the LWT [[interim-report-mqtt-lifecycle-supervisor-spec]] |
| D6 No graceful shutdown | zero signal-handling grep hits across `crates/`; unit has only `ConditionUser` | A clean DISCONNECT silently discards the LWT, leaving availability stuck "online" forever |
| D7 No decommission path | absent | Ghost entities resurrect on every HA restart |
| D8 Session semantics unexamined | defaults | See §2 — the fleet needs `clean_session=true` explicitly |
| D9 Broker defaults unpaired | callisto `mqtt.nix` sets neither `max_queued_messages` nor `persistence` | See §2 — broker amnesia compounds D1 |

**Finding two: the privilege workaround is not just ugly, it is broken today.** `jupiter-os/modules/services/ha-agent.nix:117-124` ships a root-owned oneshot that `chmod 0664`s backlight and cpufreq sysfs nodes, with a comment claiming "io is in the groups that own the nodes (video for backlight…)" at line 112. That comment is false: sysfs attributes default `root:root 0644`, so `0664` grants group-write to group *root*, and io's only group anywhere in the fleet is `wheel` (`modules/common.nix:139` — no host adds io to `video`). The agent's brightness, governor, and EPP writes therefore fail EACCES with nothing but a `warn!` in `write_sys_file` (`crates/backend-hardware/src/lib.rs:108-111`) — silent failure at the HA layer [[interim-report-fleet-service-model-by-host-class]]. The deployed shape is a user service carrying a system-level privilege crutch that does not even work; that is the definition of hand-waving infrastructure.

**Finding three: the test and CI posture is worse than it looks, and the numbers needed correcting.** The workspace has **8 test functions, not 3** (3 in `core/src/discovery.rs`, 5 in `backend-launcher/src/lib.rs` — all pure shape/regression guards, zero on the ten other crates), but the flake's `checks` contain only `buildPackage` and `cargoClippy --all-targets -- --deny warnings`: **no `craneLib.cargoTest` entry exists, so zero of the 8 tests ever run in any gate**. Worse, clippy is red today — the `unnecessary_map_or` family at `backend-hardware/src/lib.rs:117` fails `--deny warnings`, so `nix flake check` cannot go green before a one-line fix [[interim-report-testing-gate-for-hardware-daemon]]. There is no `.github/` directory; there is no CI at all. A hardware-touching daemon with zero executed tests and a red lint gate is the pipeline fact behind the felt unreliability.

**The fleet coverage fact:** the agent runs on 4 of 6 hosts — the four TCxWave kiosks (amalthea, adrastea, metis, thebe) via `tcxwave-kiosk.nix` — while callisto deliberately opts out (its arcade-console config strips the agent wiring), europa runs nothing despite backend-zfs/backend-syncthing/backend-headscale existing for exactly that host, and [[interim-report-adopt-vs-build-honest-verdict]]. "Every host" is an ambition the fleet's own configuration currently contradicts; §5 closes that gap.

## 2. The MQTT Lifecycle Problem: Why It Is Never Reliable

This section carries the thesis. The claim is not that the agent has many small flaws; it is that **the connection lifecycle is driven from the wrong place** — a fire-and-forget setup task instead of the poll loop's ConnAck event — and that this one structural error, plus two default-shaped traps, produces every reliability symptom the fleet has felt.

**The library contract that decides everything.** rumqttc's poll loop reconnects unconditionally: "Continuing to poll will reconnect to the broker if there is a disconnection" [[eventloop-in-rumqttc-rust]], and the crate advertises exactly that — "Automatic reconnections by just continuing the eventloop.poll()/connection.iter() loop" plus "Natural backpressure to client APIs during bad network" — with re-subscription conspicuously absent from its own feature list [[rumqttc-rust]]. Its defaults are clean_session=true, keep_alive 60 s, inflight 100 [[librs]]. But reconnection is not re-subscription. Issue #250 (open since February 2021, still open, labelled in-pipeline) documents the footgun precisely: after a reconnect with a clean session, "I'm not seeing any data coming in from subscribed topics" — because subscriptions live only in broker-side session state, which a clean session destroys on every reconnect [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]]. The in-pipeline fix, PR #1052, is open, unreviewed, v5-scoped, and — decisively — only emits a reconnect *signal*; its own caller pattern re-subscribes in application code, so subscription ownership stays with the application even if it merges [[interim-report-rumqttc-dependency-fitness]]. Waiting for upstream saves nothing. The same holds for issue #211 (open since December 2020, labelled stale/blocked): there is no disconnect callback and no TTL on pending messages, so stale telemetry can replay on reconnect by design [[rumqttc-reconnection-to-mqtt-broker-and-pending-messages-ttl-issue-211-bytebeami]].

**D1, mechanically.** The agent's setup task subscribes once and the poll loop ignores the connect event. Compounding this, callisto's `mqtt.nix` sets no `persistence`, so mosquitto defaults `persistence false` — connection, subscription, and message data "stored in memory only" [[mosquitto8-mosquitto-debian-unstable-debian-manpages]] — meaning **every broker restart wipes all sessions fleet-wide** [[interim-report-mqtt-lifecycle-supervisor-spec]]. The result today: the first mosquitto restart, HA restart with a broker drop, or network blip permanently deafens every agent. It keeps publishing state (the poll task is independent) but can never receive a command again. This alone explains "never reliable."

**D2, the mirror image.** On any ungraceful disconnect the broker correctly fires the retained "offline" LWT. But the agent never re-publishes "online" after reconnecting, so the retained availability topic permanently says "offline" while state telemetry flows normally — and per HA's own availability semantics, an entity with an `availability_topic` stays unavailable until a payload actually arrives on that topic; state alone does not suffice [[mqtt-discovery-availability-home-assistant-os-home-assistant-community]] — the exact trap the community thread demonstrates step by step (publish state, sensor stays unavailable; publish availability, sensor appears) [[mqtt-discovery-availability-home-assistant-os-home-assistant-community]]. Hosts look dead in HA while working. Users read D1 and D2 together as "the agent is broken."

**D3, the HA-side contract the agent does not honour.** HA's MQTT integration is explicit: "A device or service that exposes the MQTT discovery should subscribe to the Birth message and use this as a trigger to send the discovery payload. To avoid high IO loads on the MQTT broker, adding some random delay in sending the discovery payload is recommended" — HA publishes `online` to `homeassistant/status` on startup, and all discovered entities sit unavailable until a discovery message is processed [[mqtt-home-assistant]]. Retained discovery is necessary but not sufficient: the HA #135266 maintainer thread shows retained configs present on the broker and fresh state arriving, yet devices still stranded unavailable — at 5,374 entities the broker's per-client queue overflowed during HA's startup retained replay and *silently dropped* retained messages (56 of 112 affected topics arrived empty; MQTT Explorer showed them present while HA's own logs showed nothing; the user's cure was "I have raised the allowed maximum number of queued messages on my broker") [[some-mqtt-devices-unavailable-after-ha-restart-issue-135266-home-assistantcore-g]] [[comments]]. The older issue #38661 shows the same stranded-entity class ending in manual delete-and-rediscover — "A lot of my MQTT sensors are unavailable after a restart. The solution to get them back is to delete the entity, and resend the discovery message" [[mqtt-sensors-unavailable-in-01140bx-others-stay-unknown-issue-38661-home-assista]]. The hand-built-devices community thread independently converged on the same discipline: retained config + state + availability, re-published on reconnect — the Zigbee2MQTT devices survive HA restarts because their add-on already does this [[my-hand-built-mqtt-devices-are-unavailable-after-hassio-restart-but-zigbee2mqtt]].

**D4 and D5, the lying-telemetry failure modes.** The channel capacity of 64 (`agent.rs:62`) contradicts rumqttc's own recommendation to set it to 0 when managing pending state [[rumqttrumqttcsrceventlooprs-at-main-bytebeamiorumqtt-github]] — during an outage, up to 64 stale state messages queue and then replay as a burst. And D5 is the worst class in the fleet: `backend-syncthing` builds its reqwest client with no timeout (reqwest has no default timeout — an audited absence in the crate's own API), and because `Agent::run` polls all backends sequentially in one task, a single hung syncthing daemon freezes **every** sensor on the host while availability still reads "online" — sensors that lie rather than sensors that vanish [[interim-report-mqtt-lifecycle-supervisor-spec]].

**D6, the shutdown trap.** The broker discards the stored LWT on a graceful DISCONNECT. Today the agent's SIGTERM path "works" only by accident: the process dies ungracefully, TCP closes, the LWT fires. The day anyone adds a clean shutdown that sends DISCONNECT without first explicitly publishing "offline," the retained availability sticks at "online" forever — the exact trap ESPHome solves with a dedicated `shutdown_message` distinct from the will [[mqtt-client-component-esphome-smart-home-made-simple]]. rumqttc 0.24.0 ships the primitive needed: `AsyncClient::disconnect()` [[interim-report-rumqttc-dependency-fitness]].

**The supervisor spec, and the one structural change it hangs on.** The fix set is a ConnAck-driven supervisor: on every `Ok(Event::Incoming(Packet::ConnAck(_)))` — first connect or reconnect, either `session_present` value — re-issue all command-topic subscribes (idempotent; subscribe-before-connect is proven safe because requests buffer in the bounded channel until post-ConnAck [[rumqttrumqttcsrceventlooprs-at-main-bytebeamiorumqtt-github]]) and re-assert retained availability "online"; subscribe to `homeassistant/status` and republish all discovery configs with 0–30 s per-host random jitter on HA's birth (the production reference: Z2M's availability machinery applies `Math.random() * max_jitter` with a 30 s default and ×1.5/×3/×6/×12 backoff, publishing retained QoS 1 availability and deduping consecutive states) [[device-availability-zigbee2mqtt]]; set channel capacity 0 with per-tick publish timeouts so staleness is bounded to one poll interval; wrap every backend `poll()` and every command handler in `tokio::time::timeout` and dispatch commands via `tokio::spawn` — rumqtt's standing rule is "Don't block this while iterating"; handle SIGTERM by publishing retained "offline," awaiting it, then `disconnect()`; add a `--decommission` mode publishing zero-length payloads to every owned topic (HA's official removal semantic); and pair callisto's mosquitto with sizing and persistence [[interim-report-mqtt-lifecycle-supervisor-spec]].

**Two calibrations that keep the argument honest.** First, on broker sizing: the silent-drop mechanism is real and five-source-confirmed — queue admission is per-client, counts against `max_queued_messages` (default 1000, and 0 means no maximum, explicitly not recommended), and for a disconnected client the in-flight adjustment zeroes (`adjust_count = 0` when `!net__is_connected`) so the full queue depth is available to offline replay ([[databasec]], [[mosquitto8-mosquitto-debian-unstable-debian-manpages]]) — but at the fleet's measured ~25 agent entities the default 1000 never binds; the binding quantity is HA's own `#`-wildcard client queue against broker-wide retained replay. So D9 lands as cheap hygiene plus a `$SYS` confirmation check on `$SYS/broker/publish/messages/dropped` — not the never-published `$SYS/broker/mqtt/*` variants that mosquitto 2.1.2's `sys_tree.c` explicitly excludes — with `persistence true` as the load-bearing half (every broker restart still wipes sessions, which is why the ConnAck re-subscribe is mandatory regardless of queue sizing). Second, on the client dependency: keep rumqttc pinned at exactly 0.24.0 (Cargo.lock measured). The upgrade to 0.25.1 was actually run — `cargo check`, `cargo test` (3 passed), and `cargo clippy` all exit 0 with zero code changes — and reverted, because it buys nothing the supervisor needs; the method-for-method-identical public AsyncClient API across 0.24.0→0.25.1 is itself the evidence that the bump is cosmetic for this codebase [[interim-report-rumqttc-dependency-fitness]] [[eventloop-in-rumqttc-rust]]. And one premise-correction that strengthens rather than weakens the spec: 0.24.0 is *not* MQTT v3.1.1-only — `src/lib.rs:113` declares `pub mod v5;` with full v5 property support inside the pinned version, so the v5 escape hatch is a module switch away, a named future option, never the reason for the workaround. The ConnAck supervisor is mandatory and unconditional either way, because the raw ConnAck match is the *permanent* shape of this client's design, not a version workaround.

**On `clean_session` — committed against the persistent-session instinct.** A persistent session's only unique deliverable for this fleet is broker-side queueing of QoS 1 messages for an offline agent — which here means *commands*, queued while kiosks are powered off overnight, replayed at morning boot with no TTL available in v3.1.1 (#211, blocked since 2020) and no timestamp in the payload. A week-old launcher toggle or reboot command replaying as fresh is a real, fleet-specific hazard; no source in the corpus states this, but the kiosk overnight-off pattern (jupiter-os enables the agent fleet-wide on hosts that power off) and rumqtt's documented lack of any pending-message TTL jointly imply it. Keep `clean_session=true` (explicitly, for intent), stable client_id, and take all reliability from the ConnAck-driven design. The production references point the same way — Z2M's client defaults clean sessions and relies on birth/LWT re-announce rather than session state [[interim-report-mqtt-lifecycle-supervisor-spec]].

**The precedent that makes this credible rather than speculative:** the incumbent Windows companion shipped exactly this bug class and fixed it in a patch release — HASS.Agent 2.1.1's changelog: "MQTT autodiscovery messages were not republished after connection was lost and recovered" (#230), alongside rename-triggered discovery-removal failures (#376, #388) and an entire sensor class stopping on a WMI restart (#205); 2.2.0 even removed its hardware-monitor library outright on security grounds, leaving the GPU sensor permanently returning 0 [[releases-hass-agenthassagent-github]]. Reconnect-deafness is the generic companion-agent disease; the difference is that ha-linux-agent's instance of it is now diagnosed to the line and has a spec.

## 3. What a Proper Linux Agent Looks Like: The Comparison Set

To argue the improvement plan, the bar must be defined by the 2026 companion-agent ecosystem, not by ha-linux-agent's current self.

**The sensor bar.** go-hass-agent (the actively maintained incumbent, v14.15.1 of 2026-08-09, packaged in nixpkgs for all 24 Linux platforms, ~monthly cosign-signed releases) sources its Linux sensor surface from D-Bus (logind sessions, power state, screen lock, NetworkManager, XDG portal, UPower, MPRIS, fwupd), ProcFS (memory, disk, load, CPU usage/frequency, uptime, kernel, CPU vulnerabilities), SysFS (disk I/O rates, hwmon), and Netlink (link states/rates) — roughly 3–4× ha-linux-agent's generic backend, which offers sysinfo CPU/memory/disk/load/uptime plus logind idle/locked and UPower battery [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[go-hass-agent-mynixos]]. lnxlink defines the fullest desktop envelope of any Linux agent: ~50 modules spanning idle-time, keep-alive, media control with metadata, brightness, screen on/off, fullscreen detection, screenshot streaming, audio device selection, systemd unit management, GPU usage, restart-required and pending-updates tracking, WOL, BeaconDB location, and in-use sensors for mic/speaker/camera/gamepad [[lnxlink]]. Even the HA Glances integration — a polling scraper, single integration owner, 1.3% of active installations — catalogues the de-facto host-monitoring scope: per-mount disk use, per-disk I/O rates, memory and swap, processor load, process counts, CPU, temperatures, Docker containers, per-NIC rx/tx, GPU, uptime. A "proper Linux Agent" in 2026 is measured against that aggregate surface; by sensor count alone, ha-linux-agent today is roughly a quarter of go-hass-agent.

**The control bar — where the comparison inverts.** The companion-agent contract that matters for kiosks is not sensor breadth; it is **controls whose state is genuinely synchronised** and **entity shapes richer than buttons**. Here the incumbents fail on their own documentation: go-hass-agent's commands.toml vocabulary is button/switch/number only, and its README states plainly, "States are not kept in sync. This is most important for all controls besides buttons. For example, if you configure a switch, any changes to the state you make outside of Home Assistant will not be reflected in Home Assistant automatically" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. Its complete changelog from v4.3.1 through v14.15.1 contains zero occurrences of select entities, MQTT control state synchronisation, or NixOS support — the gaps persist through the current era [[interim-report-adopt-vs-build-honest-verdict]]. jupiterOS's kiosk session-switching *requires* a select whose options reflect real systemd unit state — that is the launcher backend's whole design (grouped profiles become one mutually exclusive select, with the shared state topic reshaping through discovery `value_template`) — a control vocabulary the incumbent architecturally lacks. lnxlink has dropdowns and systemd unit control but no mutual-exclusion semantics and no backlight-fused light entities tied to fleet power services [[lnxlink]].

**The identity bar.** go-hass-agent is dual-transport by mandate — it registers via the mobile_app Native App Integration API ("Go Hass Agent cannot run in an MQTT-only credentials [mode]") with an optional MQTT v5 side — and documents the split-brain consequence itself: sensors and controls land as *two* HA devices that "cannot be combined in a single place" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. ha-linux-agent's single-device MQTT-only identity is architecturally cleaner, and it is not a cosmetic preference: every dashboard and automation targeting a kiosk sees one coherent device.

**The transport bar — resolved for this fleet.** A senior HA contributor's objection on the record — "Could you clarify your reasoning behind going through MQTT for influxdb injection? Seems an unnecessary point of failure to me. I go directly from telegraf to influxdb, then use the influxdb integration inside HA" — is correct for a DB-centric time-series pipeline and irrelevant to this fleet: jupiterOS runs no InfluxDB and wants HA automations, dashboards, and kiosk *control*, which need the bidirectionality MQTT natively provides; halinuxcompanion is migrating *toward* MQTT precisely because the native API cannot reflect a host going offline while an LWT can. (This disagreement is engaged in full in the Opinionated Synthesis.)

**The notification bar — and the one thing MQTT cannot do.** HA 2024.5 shipped a native MQTT notify entity platform (PR #115653, Quality Scale gold, has-tests; "notify" sits in mqtt/const.py's SUPPORTED_COMPONENTS; the upstream test suite publishes the working discovery payload `{"name": "test", "command_topic": "test-topic"}`) [[add-mqtt-notify-platform-by-jbouwh-pull-request-115653-home-assistantcore-github]] [[corehomeassistantcomponentsmqttconstpy-at-dev-home-assistantcore-github]] [[test_notifypy]]. This gives an MQTT-only agent a first-class `notify.<device>` service — strictly better than ha-linux-agent's current raw-button payload hack, and implementable today. What it cannot carry is *actionable* notifications: the platform's vocabulary is command_topic + command_template, one-way outbound, with no actions schema and no event round-trip. But the honest comparison shows no Linux agent implements the action round-trip anywhere — go-hass-agent's requests #667 (Dec 2025) and #926 (Aug 2026) sit open with zero maintainer engagement — so going MQTT-only sacrifices almost nothing the ecosystem actually delivers [[interim-report-adopt-vs-build-honest-verdict]] [[corehomeassistantcomponentsmqttconstpy-at-dev-home-assistantcore-github]].

**The bar, summarised:** a proper Linux agent = production MQTT lifecycle (birth/LWT/ConnAck-driven, retained discipline) + a sensor surface at incumbent scale + controls with synced state and select-level vocabulary + single-device identity + a notify entity + hardware coverage (SMART, ZFS, unit health) via event-driven, unprivileged channels [[mqtt-home-assistant]] [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. ha-linux-agent currently meets none of the first and parts of the rest; the argument of this report is that the first is small, precisely scoped, and prerequisite to everything else.

## 4. The Build-vs-Buy Dialectic: Custom Rust Agent vs Telegraf, Glances, and Netdata

The strongest case for adoption, stated at full strength: go-hass-agent v14.15.1 is one `environment.systemPackages` line away on every host (verified in nixpkgs proper, not broken, not unfree, building for all 24 Linux platforms) [[go-hass-agent-mynixos]]; it has 3,909 commits of sensor polish, ~monthly signed releases through 2026, SMART with capability handling, per-core CPU frequency, network link rates, OOM events, fwupd firmware security [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]; its maintainer explicitly designs the systemd path for servers ("The systemctl service is primarily for 'headless' usage (i.e., servers)"); and a 12-crate workspace with 8 test functions, 11 commits, verified reconnect deafness, and three backends self-flagged "Unverified in a live environment" (zfs, syncthing REST fields, lutris JSON field names) is not a foundation but a prototype. lnxlink covers the desktop long tail — its ~50 modules are the credible proof that "desktop companion" extends far beyond anything jupiterOS consumes [[lnxlink]]. Telegraf→DB pipelines are the observability standard; Netdata agents need "1%-5% of a single core" with default settings.

**Why the evidence refutes it.** First, the deciding features are inexpressible upstream. The fleet's actual deployed feature set is not "sensors + commands" — it is the launcher mutual-exclusion session select (dashboard ↔ arcade on one tty1, HA-side select generated declaratively from `jupiter.services.haAgent.launcherApps`), the backlight-as-dimmable-light profile fused to `tcxwave-screen-power.service`, the customer-display switch, and 1-second polling — a control plane expressing jupiterOS's own systemd session model [[interim-report-adopt-vs-build-honest-verdict]]. go-hass-agent's own users hit the missing-select wall (a January 2026 report: a PipeWire output-device selector "can't be expressed" because commands.toml has no drop-down), its states are explicitly unsynced — "States are not kept in sync. This is most important for all controls besides buttons" — and its group concept does not exist [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. Second, the deployment story inverts at the module layer: neither incumbent has a NixOS service module — module-list.nix's full text contains zero occurrences of go-hass or lnxlink, and lnxlink is not packaged in nixpkgs at all (its Python dependency surface is heavy and GUI/X11-coupled, which is why no one has upstreamed a module) [[lnxlink]] — while ha-linux-agent already ships a flake `nixosModules.default` with a working `jupiter.services.haAgent` abstraction layered above it; adopting would mean inheriting the split-brain and then building the launcher/session layer as configuration glued around an agent that does not natively model it. Third, the alternatives fail on fleet-specific axes: Netdata's marketed 100–200 MB default meets 250–350 MB in typical production and 200–1000+ MB in community reports, with the maintainer-endorsed production recipe disabling most of the product to fit edge hosts — at which point a purpose-built agent is the lighter choice for TCxWave-class kiosks; Glances is a polling REST scraper with 1.3% adoption; Telegraf's MQTT output modes address metrics pipelines, not kiosk control, and HA's built-in Prometheus integration exposes only entity-level metrics, not host/OS metrics. Fourth, the escape hatch is closed: contributing the missing features upstream requires a maintainer-responsive project, and the two open notification feature requests with zero maintainer engagement are the evidence against that [[interim-report-adopt-vs-build-honest-verdict]].

**The concession table, on the record.** Improve-don't-adopt is only honest with the costs named: ~25% sensor coverage vs go-hass-agent; 8 test functions vs 3,909 commits of maturity; three backends carrying the repo's own unverified-live flags; the notify path is currently a payload-hack button rather than an entity; lnxlink's 50-module long tail shows how far "desktop companion" extends beyond jupiterOS's needs. None of these is a reason to adopt — they are the *scope discipline* the improvement roadmap must respect: fix the lifecycle, keep the sensor surface deliberately minimal per host class, and spend features only where jupiterOS actually consumes them.

**The verdict:** improve, don't adopt — because the maintenance asymmetry only pays off when the differentiating layer is genuinely unbuildable upstream, which is true here precisely for the launcher select model, and because the worst defects of the bespoke path are already audited to the line, which is more than can be said for inheriting a split-brain architecture and gluing around it.

## 5. NixOS Fleet Architecture: From Kiosk-Only to Every Host in jupiterOS

**Start from the honest coverage table.** 6 hosts: 4 TCxWave kiosks (agent on, `pollIntervalSecs = 1` — the user's own "I want updates every second"), callisto (broker + arcade host, agent deliberately absent), europa (ZFS NAS + syncthing + headscale, agent absent despite the purpose-built backends), . The user's "EVERY host" and the fleet's configs disagree, and the disagreement is the work item: callisto and europa are the gap to close by design;  [[interim-report-adopt-vs-build-honest-verdict]] [[interim-report-headless-privilege-ladder]]. (This is the "every host vs the fleet's own opt-outs" disagreement; the fleet section opens with the 4/6 table and surfaces** The earlier case for the user-service shape was that `nixos-rebuild switch` did not restart user units [[what-is-the-difference-between-systemdservices-and-systemduserservices-help-nixo]]; the later case was that it did, disruptively. The current truth is the second, and it is worse for an appliance fleet: PR #517768 (merged 2026-05-26) made switch-to-configuration-ng run a full per-user switch with `restart_unit` calls for any user with an active manager — the regression fired on real fleets as `niri.service` and session monitors restarting mid-switch, one-way session teardowns via `graphical-session.target`, and half-applied generations when a session died mid-switch [[switch-to-configuration-ng-harden-user-unit-migration-second-pass-by-r-vdp-pull]] [[mainrs]]. So the user-unit shape now combines *both* failure modes: for lingered-but-not-logged-in users, changes wait for a reboot; for active users, switches tear sessions down. The verdict survives with the stronger mechanism: retire the user-unit shape entirely. The module ships `systemd.services.ha-linux-agent` with `User=io`, `After=network-online.target`, `Restart=on-failure`, `RestartSec=5s`, plus a `role` option (`kiosk | server | minimal`) driving mkIf branches [[interim-report-fleet-service-model-by-host-class]].

**The two facts that were supposed to force the user/system split both dissolved.** Session-bus reachability: a `User=io` system service reaches `/run/user/1000/bus` with two `Environment=` lines (`XDG_RUNTIME_DIR` + `DBUS_SESSION_BUS_ADDRESS`) — access control on the per-user bus is purely the socket's filesystem mode, and jupiter-os's own `mkSessionLauncher` (modules/lib.nix:60–67) already proves the pattern from the system side for cage sessions; the agent's generic backend already degrades gracefully to warn-and-disable where no session exists, which is the correct behaviour on europa [[interim-report-fleet-service-model-by-host-class]] [[systemduser-archwiki]]. Ordering: system units order after `network-online.target` and mosquitto on callisto; user units cannot order against system units at all — "you cannot have user services depend on system ones or vice versa, by design" [[what-is-the-difference-between-systemdservices-and-systemduserservices-help-nixo]]. The declared-prerequisite history matters for honesty: the older NixOS threads and the 9-year linger gap (issue #3702, closed by declarative linger in 23.11) built the user-service habit [[enabling-persistent-user-instance-systemd-issue-3702-nixosnixpkgs-github]] [[nixosusers-groups-add-user-option-to-enable-lingering-by-toxicfrog-pull-request]] [[systemduser-archwiki]]; the stc-ng era retires it.

**The zero-capability privilege ladder — the design, not the fallback.** The sharpest internal disagreement the investigations produced is direct: one committed to `AmbientCapabilities=CAP_SYS_ADMIN CAP_SYS_RAWIO` where SMART is enabled; the privilege-ladder investigation proved every subsystem has an unprivileged channel, live on fleet hardware [[interim-report-headless-privilege-ladder]]. The ladder wins on evidence weight, and the AmbientCapabilities clause becomes the named, explicitly-rejected alternative [[interim-report-fleet-service-model-by-host-class]]:

- **SMART:** smartd `-M exec` hooks. smartd already runs privileged on europa (1800 s interval, scheduled self-tests); the hook script receives the full event context via `SMARTD_MESSAGE`/`SMARTD_FAILTYPE`/`SMARTD_DEVICE` env vars and hands it to the agent — the agent never touches the ioctl. The kernel-source capability matrix makes the alternative concrete: NVME_IOCTL_ADMIN_CMD requires CAP_SYS_ADMIN ("there is nothing you can do except grant that"), CAP_SYS_RAWIO covers SATA only [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]] [[smart-archwiki]] — a grant of the "new root" catch-all to displace a daemon that already runs. (A sibling lesson in broker defaults applies while we are touching mosquitto's config: even with `max_keepalive` set, clients could CONNECT with keepalive 0 and receive no Server Keep Alive in the CONNACK — closed only in the 2.0.9 milestone — which is one more reason the supervisor sets its client keepalive explicitly rather than relying on broker-side correction [[no-keepalive-0-still-allowed-with-max_keepalive-set-issue-2117-eclipse-mosquitto]].)
- **ZFS:** `/proc/spl/kstat/zfs/<pool>/state` procfs reads (the node_exporter-proven unprivileged path — plain `os.Open()`, no /dev/zfs, no ioctl) for state polling, plus a custom zedlet as the push channel for transitions (ZED is root-only and already auto-enabled on ZFS hosts; it publishes *into* the agent's channel). The current backend-zfs shells to `zpool list` (root-equivalent today) — the rewrite removes an avoidable root requirement [[interim-report-headless-privilege-ladder]]. Thresholds: capacity warn 80%/crit 90%, fragmentation 30%/50%, any non-ONLINE state as the binary_sensor problem [[how-to-monitor-zfs-pool-health-and-status-on-ubuntu]].
- **systemd unit health:** system-bus D-Bus `Subscribe()` + JobRemoved/PropertiesChanged match-rule subscription — **live-proven on callisto**: a logrotate.timer job's JobRemoved signal was delivered to an unprivileged io subscriber with zero polkit grants (note the systemd lazy-signals subtlety: Manager signals require an explicit `Subscribe()` call at startup; PropertiesChanged does not) [[interim-report-headless-privilege-ladder]]. The rejected alternative is the OnFailure drop-in pattern, which needs root-owned file writes into `/etc/systemd/system/service.d/` [[see-also-3]]. The design precedent for the daemon shape is systemd_mon: "subscribing to DBus notifications from Systemd… no polling, and no busy-loops," queuing rapid intermediate states into one notified transition [[github-joontysystemd_mon-monitor-for-systemd-to-alert-failed-services-github]].
- **Backlight:** raw sysfs writes (the ABI contract: `brightness` 0..max_brightness, `actual_brightness`, `bl_power` 0/4 [[sysfs-class-backlight]]) with the broken chmod replaced by a udev `GROUP="video"` rule + io-in-video membership — the fleet's own existing pattern for exactly this problem class — and state sync via the kernel's own KOBJ_CHANGE uevent + `sysfs_notify(actual_brightness)`, which backlight.c emits on every store attempt including the hotkey path, replacing the 1-second poll-everything default with push.

Summing the four subsystems: **no AmbientCapabilities, no sudo, no root** — the complete privilege surface is system-bus socket access, optionally the session bus via the Environment block, and the existing polkitUnitRule pattern for the specific units the launcher may start/stop. Delete `ha-linux-agent-sysfs-perms` entirely. The NVMe ioctl path remains a per-host opt-in if sub-minute SMART freshness ever matters — it is worth noting that callisto has repeatedly destroyed local NVMe drives and keeps none, so even that opt-in has no current customer.

**Secrets and the module contract.** sops-nix's system module decrypts to `/run/secrets` with per-secret owner/group and `restartUnits` — the existing credential path (`sops.secrets.mqtt_ha_linux_agent.owner = "io"`) works identically for a system service; no home-manager indirection is needed.

## 6. JupiterOS-Specific Feature Gaps

The gap list is jupiterOS-shaped, not generic — each item maps to a host class that exists in the fleet's configs.

**systemd unit health (callisto, europa, kiosks).** The fleet's service inventory — mqtt, postgres, syncthing, headscale, iscsi-target, model-router, dsh, nom-web, cloudflare-tunnel — currently has no HA-side health surface at all. The D-Bus Subscribe() design from §5 delivers per-unit binary_sensors with push semantics [[interim-report-headless-privilege-ladder]]; the 1-second `systemctl is-active` polls inside the launcher backend should move to the same channel (the poll is part of the current "sloppy state" complaint, and the push design eliminates it rather than tuning its interval) [[repo-map-ha-linux-agent]].

**SMART/NVMe (europa; opt-in elsewhere).** The smartd `-M exec` hook design: smartd stays the privileged detector, the hook writes the event (or publishes directly as the low-priv MQTT user), the agent consumes [[interim-report-headless-privilege-ladder]]. This survives smartd's own scheduling and self-test logic for free — displacing it would cost a capability grant and a polling loop to replace a daemon that already runs the scheduled tests the fleet configured [[smart-archwiki]].

**Verified ZFS status (europa only).** The procfs-state + zedlet two-channel design [[interim-report-headless-privilege-ladder]]; callisto's ZFS exposure is only the iSCSI zvol with no local pool, where backend-zfs's `detect()` already returns false — correct today [[repo-map-ha-linux-agent]].

**Mesh/exit-node (callisto, fleet-wide visibility).** backend-headscale shells to `tailscale status --json`; the ipnstate schema is the stable surface for peer/exit-node state (PeerStatus with HostName, Online, ExitNodeStatus for the current exit node's liveness and IPs) [[ipnstate-package-tailscalecomipnipnstate-go-packages]] [[repo-map-ha-linux-agent]]. The gap is not the schema but the lifecycle: an unverified-live backend on a host where the mesh hub runs.

**Nix generation/boot health.** With stc-ng restarting user units disruptively [[switch-to-configuration-ng-harden-user-unit-migration-second-pass-by-r-vdp-pull]], a booted-vs-current-generation sensor becomes fleet-relevant: it tells HA (and the user) which hosts are running a stale generation after a switch — cheap to read, and it converts the new switch behaviour from a surprise into an observable.

**Remote reboot/poweroff.** Present via the launcher/systemd backends [[repo-map-ha-linux-agent]]; what is missing is the idempotency contract noted in §2's clean_session argument — non-idempotent commands are exactly the class a replayed stale message would damage, which is part of why the persistent session is rejected.

**Notifications, end to end.** notify.mqtt replaces the payload-hack button (HA 2024.5+; callisto's HA qualifies), one-way [[add-mqtt-notify-platform-by-jbouwh-pull-request-115653-home-assistantcore-github]]. The kiosk last mile is *not* session-bus notifications — an audited absence: no mako/dunst/swaync ships anywhere in jupiter-os, so org.freedesktop.Notifications is dead code on the fleet today. The real last mile on kiosks is the customer-display VFD overlay; the session-bus Environment block is conditional on a future desktop host class, and the one live test that would retire the residual risk (send a notification from HA to a User=io system service on a kiosk) belongs in the roadmap's verification checklist.

**CPU performance knobs (kiosks).** The global boost switch lives at `/sys/devices/system/cpu/cpufreq/boost` (0/1, the recommended interface over the legacy per-policy AMD cpb knob) — a natural governor/EPP sibling for the hardware backend's existing write path, gated by the same udev video-group pattern.

## 7. Testing a Hardware-Touching Daemon

The testing verdict rests on a general principle worth stating once, explicitly: **web consensus optimises the generic case; fleet ground truth overrides it.** The corpus's four-source consensus names Mosquitto-in-testcontainers as the right harness for parallel-safe broker tests. The audited fleet facts refute it on arrival: no docker or podman on any jupiterOS host, no container runtime in any host config, and Nix remote builders (`/etc/nix/machines`: callisto plus the four kiosks) cannot expose container sockets inside build sandboxes anyway — a testcontainers gate would be dead on arrival, not merely awkward [[interim-report-testing-gate-for-hardware-daemon]]. Yet the harness still borrows testcontainers' hard-won lessons (derive the broker URL from the harness, never hardcode; ready-probe before assertions; per-test exclusive broker to avoid cross-test interference).

The concrete gate is a seven-step, dependency-ordered ladder where step 1 is minutes and the reliability phase gets its definition of done at step 2 [[interim-report-testing-gate-for-hardware-daemon]]:

1. **Fix the clippy lint** (`map_or` → `is_some_and` at `backend-hardware:117`) so `nix flake check` can go green at all — the gate currently cannot gate.
2. **Wire `craneLib.cargoTest`** into the flake checks — this runs the *existing* 8 pure tests for zero new code, the single cheapest reliability win available, and corrects the record: 8 tests, not 3, though the deeper truth is that none of them run today.
3. **sysfs-root injection** — parameterise backend-hardware on a `PathBuf` root (std::fs is a module, not a trait; tempdir + abstraction is the canonical path), add `tempfile` fixtures, and unit-test parsing plus the warn-not-panic behaviour on unwritable nodes, in the repo's existing named-regression-guard house style [[interim-report-testing-gate-for-hardware-daemon]].
4. **Extract the `Agent::run()` seam** — config-injectable jitter bound + shutdown channel, so the lifecycle is testable in-process rather than as a black box with real signals.
5. **The mosquitto-subprocess harness + five defect-named regression tests** [[interim-report-testing-gate-for-hardware-daemon]] [[mosquitto8-mosquitto-debian-unstable-debian-manpages]]: bind a `TcpListener` to `127.0.0.1:0`, hand the port to `mosquitto -p <port>` (the no-config default is anonymous, local-only — the `mosquitto -p` loopback-only binding that 2.0 introduced), Drop-guard kill, URL always derived from the harness. The tests, named per defect: `broker_restart_resubscribes_and_reasserts_availability` (kill -9 the broker, restart on the same port, publish a command, assert the agent *handles* it — the exact line `agent.rs:190` currently swallows — then assert a fresh subscriber reads retained "online"), `birth_message_triggers_discovery_republish`, `sigterm_publishes_offline_then_disconnects`, `hung_backend_doesnt_starve_sensors`, `decommission_zero_payload`. The observer client is rumqttc itself — the same client stack as production, not a mock. Every await wrapped in `tokio::time::timeout(5s)`: a reliability gate that can hang is not a gate. The Nix sandbox brings up `lo` (upstream-blessed since Nix 1.1), so in-sandbox client-server pairs are legitimate.
6. **Private dbus-daemon harness** for zbus plumbing (`dbus-daemon --session --print-address` into a tempdir; the `pkgs.dbus` buildInput already ships the binary) — accepting honestly that a private bus has no `org.freedesktop.systemd1`.
7. **`runNixOSTest`** for the module — cribbed from nixpkgs' own three-node mosquitto test (single node suffices here; the kiosk failure mode is local): enable the module, `wait_for_unit("ha-linux-agent.service")`, assert retained "online", then `machine.systemctl("restart mosquitto.service")` mid-test and assert re-subscribe + availability return — the module-level replay of D1/D2, and the gate that pins the system-service unit shape from §5.

One boundary worth committing to: the D-Bus private-bus layer is bounded to plumbing tests only; real systemd signal tests belong to the NixOS test, because Nix build sandboxes do not provide systemd. And the corpus's testcontainers notes stay in the vault flagged unused — load-bearing only if the fleet ever gains a container runtime, so the synthesis should not cite them as if the design uses them.

## 8. Ordered Improvement Roadmap

The order is the argument: **reliability first, fleet second, features third** — because no feature matters while the agent is intermittently deaf, and because the reliability phase's test ladder (§7) is the gate the fleet phase's module test plugs into.

**Phase 0 — unblock the gate (minutes).** Fix `backend-hardware:117`; add `craneLib.cargoTest`; `nix flake check` green with all 8 tests executing for the first time.

**Phase 1 — the ConnAck supervisor (days, on rumqttc 0.24.0, no dependency churn).** (a) ConnAck-driven re-subscribe of all command topics + retained availability "online" re-assert; (b) subscribe `homeassistant/status`, republish discovery on birth with 0–30 s jitter (config-injectable to 0 for tests) — the HA-documented birth contract [[mqtt-home-assistant]] and the Z2M jitter reference [[device-availability-zigbee2mqtt]]; (c) channel capacity 0 + per-tick publish timeouts (the rumqttc-recommended rendezvous posture [[eventloop-in-rumqttc-rust]]); (d) per-backend `poll()` and per-command `tokio::spawn` + timeout isolation, 5 s HTTP timeouts in backend-syncthing; (e) SIGTERM offline-then-`disconnect()` — the ESPHome `shutdown_message` pattern [[mqtt-client-component-esphome-smart-home-made-simple]]; (f) `--decommission` zero-payload mode; (g) exponential reconnect backoff 1→60 s with ±20 % jitter (a broker restart must not synchronise N hosts into a reconnect stampede — Z2M's jitter rationale, fleet-sized); (h) `Restart=on-failure` + `RestartSec=5s` (+ sd_notify watchdog as the ESPHome `reboot_timeout` analogue). Steps 4–5 of the test ladder land here as the definition of done, with `broker_restart_resubscribes_and_reasserts_availability` as the named acceptance test [[interim-report-testing-gate-for-hardware-daemon]]. Broker pairing on callisto: `persistence true` + `persistence_location`, `max_queued_messages` sized ≥ 4× retained inventory (hygiene at current scale, urgent only if entity counts grow — the HA #135266 silent-drop mechanism is the reason it stays on the list at all [[some-mqtt-devices-unavailable-after-ha-restart-issue-135266-home-assistantcore-g]]), and a `$SYS` drop-counter check.

**Phase 2 — fleet architecture (the module rewrite).** One `systemd.services.ha-linux-agent`, `User=io`, role-driven mkIf (`kiosk | server | minimal`); delete the user unit and the sysfs-chmod oneshot (fixing the false comment either way); udev `GROUP="video"` + io-in-video for backlight writes; Environment block on lingered hosts; sops unchanged; rollout to europa (server role: SMART hook + procfs ZFS + zedlet) and callisto (kiosk/minimal role — the broker host finally runs its own agent, closing the "dashboard this host doesn't have" gap deliberately rather than by omission); the runNixOSTest from step 7 gating the module;** notify.mqtt discovery entity (transport leg over MQTT; kiosk last mile = VFD overlay, not session-bus) [[test_notifypy]]; the smartd-hook SMART bridge on europa; the backend-zfs procfs rewrite; the D-Bus Subscribe() unit-health backend (replacing the launcher's 1 s `is-active` polls); KOBJ_CHANGE-driven backlight sync replacing poll; the niri socket glob for the future desktop host class (the resolved socket pattern `$XDG_RUNTIME_DIR/niri.{wayland_socket_name}.{pid}.sock` is filesystem-permission-gated, so a same-UID service reaches it without a session unit). Explicitly *not* in scope: chasing the mobile_app actionable-notification contract (no Linux implementation exists anywhere — the incumbents' open, maintainer-silent requests are the evidence) [[interim-report-adopt-vs-build-honest-verdict]], and replicating the incumbents' sensor long tail that the fleet does not consume.

**Verification checklist (per phase).** Phase 1: the five regression tests green in `nix flake check`; a live kiosk survives `systemctl restart mosquitto` on callisto with entities recovering within the keepalive window. Phase 2: runNixOSTest green in both roles; a `nixos-rebuild switch` on a kiosk restarts the agent and the new binary takes effect *that switch*, not next reboot; the one live notification test on amalthea (HA → User=io system service) retiring the §5 residual risk. Phase 3: SMART event from a forced smartd notification lands as an HA entity; a `zpool` DEGRADED drill on europa surfaces within one poll; a unit failure on callisto appears in HA within seconds of `Subscribe()` delivery.

**Forward-looking.** The 6–12 month horizon reshapes the agent from a kiosk accessory into jupiterOS's observation plane: every host emitting unit health, storage health, and session state over one supervised MQTT lifecycle, with the module's role switch absorbing new host classes (a desktop host class; additional VPSes via the minimal role) without code changes. Two contingencies would legitimately reopen settled questions and deserve standing watch: a merged-and-released #1052 (which would let the raw ConnAck match be replaced by an `Event::Reconnect` signal and would trigger the 0.25.x bump — but would not change the design, since subscriptions stay application-owned), and go-hass-agent landing native select controls with state sync or a NixOS service module (which would reopen the adopt-vs-buy arithmetic; its changelog's zero-occurrence record through v14.15.1 is the current evidence against). The deeper strategic point: the fleet's deciding features — declarative mutual-exclusion session control fused to systemd units — are exactly the layer no general-purpose agent will ever prioritise, because they are one fleet's idiom. Owning twelve small crates whose worst defects are already file:line-diagnosed is a better maintenance position than gluing that idiom onto an agent that cannot express it.

## Opinionated Synthesis

The thesis, restated with maximal commitment: **ha-linux-agent is two bugs away from reliable, and the fix is fully specified.** The "never reliable" complaint decomposes into D1 (subscribe-once + swallowed ConnAck) and D2 (availability published once) — both located to lines, both mechanically explained by rumqttc's documented reconnect-without-resubscribe contract (#250, open five-plus years, with even the in-pipeline fix leaving subscription ownership application-side) — amplified by three default-shaped traps (callisto's amnesiac mosquitto defaults, the capacity-64 stale queue, the timeout-less reqwest client that turns one hung daemon into a fleet-wide lying-telemetry event). The presenting symptom is live on the fleet today. The supervisor spec fixes all of it without dependency churn, on the pinned version, with named regression tests. Then — and only then — the fleet phase converts a 4-of-6 kiosk-only deployment into the every-host ambition via one system service per host, with the zero-capability event-driven privilege ladder whose channels were live-proven on fleet hardware. Then features, scoped to what jupiterOS actually consumes.

### The Six Expert Disagreements, Engaged

**Disagreement 1 — MQTT hop vs direct database injection.** koying's "unnecessary point of failure" objection is correct for a Telegraf→InfluxDB metrics pipeline and wrong for this fleet, which runs no InfluxDB and needs bidirectional kiosk control and automations [[mqtt-home-assistant]]. Resolution: MQTT for this fleet's scope; a fleet that later wants long-horizon metric history should add Telegraf→DB *alongside* the agent, not instead of it. The objection is scoped, not answered away.

**Disagreement 2 — go-hass-agent's MQTT v5 hard requirement vs rumqttc's v4 default path.** The load-bearing fact is not the protocol version [[interim-report-rumqttc-dependency-fitness]]; it is the state-sync admission: kiosk session-switching requires switches that reflect real unit state, and the incumbent's own README disclaims exactly that. The v5 requirement is adoptable if the broker is upgraded; the unsynced-control admission is architectural. This disagreement feeds the adopt-vs-build verdict rather than standing alone. (And the mirror-image correction stands: rumqttc 0.24.0 is not v3.1.1-locked — the v5 module ships inside the pinned version, so the supervisor's workarounds are optional hardening, never forced.)

**Disagreement 3 — Netdata's marketed footprint vs its community-documented blowups.** Both sides are right in scope: 100–200 MB describes the empty-system default; 250–1000+ MB describes metric-heavy reality, and the vendor's own optimisation guide concedes the defaults are too heavy for edge hosts — the stripped configuration is the only one a kiosk-class host can carry. For TCxWave-class kiosks, the effective Netdata configuration is the stripped one — at which point the purpose-built agent wins on weight before any feature argument begins.

**Disagreement 4 — In-process SMART polling vs smartd's privileged event hooks.** Zero new privilege and free scheduling logic (smartd already runs on europa with the fleet's chosen self-test cadence) beats in-process freshness purchased with CAP_SYS_ADMIN — the capability the kernel-source evidence marks as the "nothing you can do except grant that" last resort [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]] [[smart-archwiki]]. The ioctl path survives as a per-host opt-in only, and no current host qualifies.

**Disagreement 5 — Testcontainers consensus vs the fleet's containerless ground truth.** The consensus is correct for Docker-equipped CI and dead on arrival for a fleet and builder set with no container runtime anywhere [[interim-report-testing-gate-for-hardware-daemon]]. The general principle — web consensus optimises the generic case; fleet ground truth overrides it — is the transferable lesson, and the subprocess harness deliberately keeps the consensus's anti-flake properties.

**Disagreement 6 — Retained-everything discipline vs selective retention with expiry.** The rare fully-resolved disagreement, and the reliability contract itself: retain everything (config, state, availability — the Z2M/ESPHome posture [[mqtt-client-component-esphome-smart-home-made-simple]] [[device-availability-zigbee2mqtt]]) AND republish on birth/ConnAck with jitter (HA's own mandate [[mqtt-home-assistant]], backed by the #135266 silent-drop evidence [[comments]]) AND size/persist the broker. Retention without republish strands entities when replay drops; republish without retention strands them when the broker forgets. The agent needs both halves; the supervisor spec is the synthesis.

One residual risk is named rather than hedged: the notification-delivery-from-a-system-service path (the session-bus Environment block) is the design's single untested leg — estimated at 20–25 % risk by the service-model investigation [[interim-report-fleet-service-model-by-host-class]], with the notification-daemon dead-code finding reducing its blast radius and one live kiosk test retiring it outright. Everything else in this draft is either measured (exit codes, file:line, live D-Bus delivery), source-verified (kernel, man pages, HA docs, maintainer threads), or an inference whose provenance is stated in exactly the shape the evidence supports.
