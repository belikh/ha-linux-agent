# Draft B — The adoption sceptic's case: do not improve ha-linux-agent

**Executive summary.** The direct answer to this research question is uncomfortable for anyone who has invested in the current codebase: improving ha-linux-agent is the wrong call. The repo is not a foundation awaiting polish — it is a prototype whose two headline defects (permanent deafness after any broker reconnect, availability permanently stuck "offline" after the first network blip) mean it has never once been reliable, and whose test, build, and deployment infrastructure is presently non-functional: eight tests of which zero run in any gate, a clippy failure that keeps `nix flake check` red, no CI directory at all, and three of its ten backends flagged "unverified in a live environment" by its own README [[interim-report-testing-gate-for-hardware-daemon]] [[interim-report-adopt-vs-build-honest-verdict]]. Against this stands an incumbent — go-hass-agent — that is packaged in nixpkgs proper at v14.15.1, building for all 24 Linux platforms nixpkgs supports, maintained by two nixpkgs maintainers on a roughly monthly cosign-signed release cadence, with 3,909 commits of sensor and hardware polish [[go-hass-agent-mynixos]] [[releases-joshuargo-hass-agent-github]] [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] — and a community-endorsed alternative, lnxlink, whose ~50-module catalogue covers nearly every desktop-companion feature the fleet could want [[lnxlink]] [[github-bkbillylnxlink-effortlessly-manage-your-linux-machine-using-mqtt-github]]. The "every host in jupiterOS" ambition is better served by adopting go-hass-agent everywhere, keeping boring mature tooling (smartd, Telegraf, NUT) for server depth, and confining bespoke code to a thin fleet-specific control layer — systemd units, polkit rules, and at most a handful of script sensors — rather than maintaining a twelve-crate Rust daemon solo.

This draft defends that minority position at full strength, and concedes where the evidence forces: Glances carries its own six-year record of unreliability inside Home Assistant [[glances-integration-loses-connection-and-doesnt-automatically-recover-issue-1105]] [[glances-integration-sometimes-stops-reporting-current-data-issue-170384-home-ass]] [[glances-sensors-are-renamed-after-a-restart-issue-32328-home-assistantcore-githu]]; Telegraf can publish to MQTT but cannot discover entities into Home Assistant at all [[telegrafpluginsoutputsmqttreadmemd-at-master-influxdatatelegraf-github]]; Netdata's real footprint is too heavy for the fleet's kiosk hardware class [[resource-utilization-netdata-agent-learn-netdata]] [[insane-netdata-memory-usage-help-netdata-community-forums]] [[agent-performance-optimization-guide-configuration]]; go-hass-agent documents its own split-brain device identity and unsynchronised control states as permanent architecture [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]; and lnxlink is not in nixpkgs, with a Python dependency surface that makes NixOS packaging genuinely painful [[python-packaging-error-needs-specific-setuptools-version-nixos-discourse]]. A steelman that hid these would be a strawman. The honest claim is narrower and stronger: every option is imperfect, but only the adoption path gets better without this project's owner doing the work — and the incumbent's imperfections are cosmetic for this fleet where the custom agent's are load-bearing.

## 1. Current State: A Verified Reliability Audit

The audit facts are not in dispute, and the improvement camp has done the codebase a service by establishing them precisely. The workspace is twelve crates with eleven commits and eight test functions — three in `core/src/discovery.rs` and five in `backend-launcher/src/lib.rs`, all pure shape-and-parsing tests, zero on any hardware, D-Bus, or MQTT-touching path [[repo-map-ha-linux-agent]] [[interim-report-testing-gate-for-hardware-daemon]]. The original audit's "3 tests" figure was stale; the corrected count is 8, but the correction deepens rather than softens the problem: `nix flake check` runs none of them, because `craneLib.cargoTest` was never wired into the flake's checks, and clippy is red today at `backend-hardware/src/lib.rs:117` (the `unnecessary_map_or` family), so the gate cannot go green even if it were [[interim-report-testing-gate-for-hardware-daemon]]. There is no `.github/` directory; there is no CI of any kind. The two verified lifecycle defects are textbook: `crates/core/src/agent.rs:134-138` subscribes to command topics exactly once inside a fire-and-forget setup task, the poll loop swallows every ConnAck with `Ok(_) => {}` at line 190, and `agent.rs:139-144` publishes the retained availability "online" exactly once — so after any reconnect the agent never re-subscribes, and after any ungraceful disconnect the retained availability topic permanently reads "offline" while state telemetry keeps flowing [[interim-report-mqtt-lifecycle-supervisor-spec]]. The fleet's live presenting symptom matches the code exactly: the four kiosks' entities read unavailable in Home Assistant on callisto right now, which is the user's "never reliable" complaint observed live, not recalled [[interim-report-mqtt-lifecycle-supervisor-spec]] [[interim-report-adopt-vs-build-honest-verdict]].

Beyond the lifecycle, the audit found: `backend-syncthing` builds its reqwest client with no timeout (`lib.rs:75,98`), and because `agent.rs:154-157` polls all sensor backends sequentially in one task, a single hung daemon on europa starves every sensor on the host while availability still says "online" — telemetry that lies rather than telemetry that vanishes [[interim-report-mqtt-lifecycle-supervisor-spec]]. No signal handling exists anywhere in `crates/` (verified by grep), so systemd's default `Restart=no` on the deployed user unit means a panicked agent stays dead until reboot [[interim-report-mqtt-lifecycle-supervisor-spec]] [[interim-report-fleet-service-model-by-host-class]]. The deployed NixOS module's own comment is false: `ha-agent.nix:112` claims "io is in the groups that own the nodes (video for backlight...)" but io's only group is wheel, so the root-owned sysfs-chmod oneshot grants group-root write on nodes io cannot write — the brightness and governor writes the kiosk fleet depends on fail EACCES, silently, behind a `warn!` in `write_sys_file` [[interim-report-fleet-service-model-by-host-class]] [[repo-map-ha-linux-agent]]. Three backends (zfs, syncthing, lutris) are flagged in the README's own words as "Unverified in a live environment" [[interim-report-adopt-vs-build-honest-verdict]].

The improvement camp reads this list as "a concrete fix specification, already audited." The sceptic reads it differently, and the difference is the whole argument: this is not the audit of a mature system entering maintenance — it is the audit of a prototype that has never had a single reliable day in production. The four kiosks have run this agent with one-second polling and mutual-exclusion session selects, and the observable result in Home Assistant is unavailability [[interim-report-adopt-vs-build-honest-verdict]]. When a system's verified defect list includes "cannot hear commands after a broker restart" and "reports offline forever after one blip" — and the broker on callisto defaults to `persistence false`, wiping all sessions on every restart, guaranteeing both defects fire routinely [[interim-report-mqtt-lifecycle-supervisor-spec]] — the system is not under-maintained; it is unstarted. Prototypes are cheap to rewrite and expensive to institutionalise. The eleven commits of history here do not represent sunk value that adoption discards; they represent a design exploration whose useful outputs — the launcher profile model, the entity-shape tests — port to any successor as configuration and as test cases, not as a daemon.

## 2. The MQTT Lifecycle Problem: Why It Is Never Reliable

The lifecycle analysis is the strongest work the improvement camp produced, and it argues against them more than they admit. The root cause chain: rumqttc reconnects automatically but never re-establishes subscriptions — issue #250, opened February 2021, still open, labelled "in-pipeline" pointing at PR #1052 which is itself open, unreviewed by maintainers, and scoped to MQTT v5 only, and which even if merged tomorrow would only add a reconnect *signal*, leaving subscription ownership with the application by design [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]] [[interim-report-rumqttc-dependency-fitness]]. The crate's own advertised feature list on docs.rs says "Automatic reconnections by just continuing the eventloop.poll()/connection.iter() loop" — with re-subscription conspicuously absent, and only 35.34% of the crate documented [[rumqttc-rust]]. The companion defect, rumqtt #211 (open since December 2020, labelled stale/blocked), means there is no disconnect callback and no TTL on pending messages [[interim-report-rumqttc-dependency-fitness]]. The prescribed fix — a ConnAck-driven supervisor that re-subscribes, re-asserts availability, listens for HA's birth message, and republishes discovery with jitter — is correct, well-specified, and a faithful reimplementation of things the ecosystem solved in public years ago [[interim-report-mqtt-lifecycle-supervisor-spec]].

That last clause is the argument. Home Assistant's own MQTT contract has mandated birth-triggered discovery republish with random delay for years: "A device or service that exposes the MQTT discovery should subscribe to the Birth message and use this as a trigger to send the discovery payload. To avoid high IO loads on the MQTT broker, adding some random delay in sending the discovery payload is recommended" [[mqtt-home-assistant]]. go-hass-agent's changelog shows it paying exactly these dues in public: a 2024 entry reading "reconnect to MQTT on disconnect and fix issue with MQTT commands not working" (commit cfce533), followed by "gracefully shutdown mqtt message channel", "keep device id constant for MQTT", "ensure sensors have appropriate icon, device class and state class", and a major MQTT refactor whose breaking-change note promises easier future control additions [[changelogmd]]. HASS.Agent — the Windows agent whose Linux absence created this niche [[github-hass-agenthassagent-unofficial-development-project-for-the-hassagent-plat]] — has the same scar tissue, and its fix history is the reliability curriculum: "MQTT autodiscovery messages were not republished after connection was lost and recovered (#230)", "Fixed MQTT entities changing ID after device rename (#388)", discovery messages not removed on rename (#376), and "Restarting Windows Management Instrumentation (WMI) while HASS.Agent is running causes all WMI based sensors to stop functioning (#205)" [[github-hass-agenthassagent-unofficial-development-project-for-the-hassagent-plat]]. Zigbee2MQTT's availability machinery — retained QoS 1 availability publishes, x1.5/x3/x6/x12 backoff, 30-second max jitter, persisted timeout state — is the production reference, published and copyable [[interim-report-mqtt-lifecycle-supervisor-spec]].

The inference, stated as an inference because no source says it directly: the joint facts that (a) every mature agent in this space has publicly shipped the identical reconnect/republish fixes the supervisor spec prescribes [[changelogmd]] [[github-hass-agenthassagent-unofficial-development-project-for-the-hassagent-plat]], and (b) the dependency underneath this codebase has left its own reconnect bug open for more than five years [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]] [[interim-report-rumqttc-dependency-fitness]], together imply that "improving ha-linux-agent" means one solo maintainer re-deriving, from scratch, on a single-machine budget, a reliability curriculum that incumbent projects burned years of multi-contributor production reports to learn — while continuing to stand on a library whose maintainers have not answered the core reconnect question since before this repository existed. The maintenance-trap framing is not rhetoric; it is this arithmetic. And the trap has a second wall: even the alternative client (Paho) leaves re-subscription application-owned, so a client switch buys nothing and costs a C toolchain dependency on NixOS fleet builds [[interim-report-rumqttc-dependency-fitness]]. The improvement path is a dead end in both directions — the library will never deliver the fix, and the fix the library cannot deliver is the one the incumbents already have [[interim-report-rumqttc-dependency-fitness]] [[changelogmd]].

There is also the minority position on the transport itself, which deserves full strength. koying, a long-time Home Assistant contributor, on routing host metrics through MQTT: "Could you clarify your reasoning behind going through MQTT for influxdb injection? Seems an unnecessary point of failure to me. I go directly from telegraf to influxdb, then use the influxdb integration inside HA" [[system-design-architecting-ha-data-flows-with-telegraf-mqtt-influxdb-and-grafana]]. The counter-architects agree from the other side: HA_Desktop_Companion exists because its author "don't like existing implementations using MQTT" and reimplemented ESPHome's native protocol instead [[github-gamerclassn7ha_desktop_companion-app-which-is-using-native-ha-api-to-comu]]. The concession that cuts both ways: halinuxcompanion — the native-API Linux agent — lists "Move sensors to MQTT" as a to-do, with the reasoning that "the limitations of the API" leave sensor values "stuck" when a host goes offline, because only MQTT's last-will mechanism can reflect an offline host [[github-muniterhalinuxcompanion-homeassistant-linux-companion-github]]. And the native-API-only camp loses its best exhibit on the notification front: HA core's MQTT const.py carries notify among the discovery-supported components, so even one-way notifications are expressible over MQTT without any native API [[corehomeassistantcomponentsmqttconstpy-at-dev-home-assistantcore-github]]. The honest reading for jupiterOS: MQTT is the right transport for the bidirectional kiosk control plane (every mature agent converged on it [[wth-there-is-no-windows-and-linux-ha-app-similar-to-macos-month-of-what-the-heck]]), and koying is right that it is the wrong transport for server metrics history — which argues for splitting the problem: a maintained agent for control and presence, boring tooling for metric depth. It does not argue for a bespoke daemon trying to be both.

## 3. What a Proper Linux Agent Looks Like: The Comparison Set

The canonical vocabulary for "companion agent" is the mobile companion documentation: sensor.battery_level, battery_state, connection_type, geocoded_location, ssid, storage, activity, frontmost_app, active_camera, active_audio_input/output, camera_in_use, audio_input_in_use, displays, media session, last_update_trigger — an 8,000-word catalogue of what a device companion is expected to expose, with per-platform enablement and update semantics [[sensors-home-assistant-companion-docs]]. Against that vocabulary, the incumbents are overwhelming. go-hass-agent's Linux surface sources from D-Bus (logind sessions and power state, screen lock, NetworkManager connections and Wi-Fi details, XDG portal active app and desktop settings, UPower battery, MPRIS, fwupd firmware security), ProcFS (memory, disk usage, load, per-core CPU usage and frequency, uptime, kernel, distro, CPU vulnerabilities), SysFS (disk IO rates, hwmon hardware sensors), Netlink (link states and rates), and geoclue (location), each with its own update cadence from ~5 seconds to ~15 minutes — plus controls (volume, webcam, power off/reboot/suspend/hibernate, screen lock, inhibit locks, arbitrary D-Bus invocation via the `gohassagent/HOSTNAME/dbuscommand` topic), events (user sessions, OOM), and a script-sensor mechanism accepting any shebang program emitting JSON/YAML/TOML on Quartz cron or `@every` schedules [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. Its recent cadence is the depth-of-maintenance evidence: v14.15.1 (2026-08-09) fixed a concurrent map-read data race in the CPU usage worker; v14.15.0 added NVIDIA and AMD GPU memory sensors; v14.13.0 improved webcam streaming; v14.11.0 fixed PipeWire volume control; v14.10.3 fixed ddcutil backlight detection on Gnome [[releases-joshuargo-hass-agent-github]] [[changelogmd]]. That is a maintainer actively polishing exactly the hardware-adjacent surface — backlight, audio, GPU, disks — a fleet of kiosks and servers lives on [[releases-joshuargo-hass-agent-github]].

lnxlink's module catalogue is the fullest feature envelope of any Linux Home Assistant agent: rich desktop notifications via notify.send_message, URL/file opening, keep-alive, idle-time sensing, media control with metadata, brightness, screen on/off, fullscreen detection, desktop screenshot streaming to an HA image entity, audio-device selection, keyboard hotkey capture, mouse simulation, a Steam game-launcher dropdown, active-window monitoring, clipboard view/update, current-user monitoring, boot-select, power-profile toggling, per-unit systemd service management ("Manage Linux services; check status, start, or stop specific units"), NVIDIA/AMD GPU usage, restart-required and system-update tracking, disk IO/usage/mounts, Bluetooth with device battery, Wi-Fi strength, WOL toggle, BeaconDB Wi-Fi-triangulation location, mic/speaker/camera/gamepad in-use sensors, webcam switch and feed, fingerprint, speech, GPIO, IR remote, bash-command custom entities ("Create custom sensors, binary_sensors, buttons, or switches using shell scripts"), docker management, in-Home-Assistant self-update, and even a sensor-collection-latency probe [[lnxlink]] [[github-bkbillylnxlink-effortlessly-manage-your-linux-machine-using-mqtt-github]]. HASS.Agent remains the notification gold standard on any platform: actionable notifications that "work the same way as the companion apps do", with buttons that fire the `hass_agent_notifications` event back into Home Assistant — the complete action round-trip [[home-hassagent-documentation]] — and its sensor/command setup docs show how far the polish goes: per-sensor update intervals, availability checks, and the telling guidance that "only certain commands will actually return states to HA. So we recommend just using Button for most commands" [[using-sensors-hassagent-documentation]] [[using-commands-hassagent-documentation]]. The community demand signal is real and mod-endorsed: the WTH thread asking for a macOS-like app drew the moderator's pointer to glances, netdata, and system-bridge for Linux, and users trading the exact trade-offs this report weighs — one participant: "I personally hate mqtt... Also mqtt is not a native way to integrate with home assistant in my opinion", answered by another that HASS.Agent without MQTT loses "most features... for bidirectional communication" [[wth-there-is-no-windows-and-linux-ha-app-similar-to-macos-month-of-what-the-heck]].

The honest scorecard for ha-linux-agent on this vocabulary: roughly a quarter of go-hass-agent's generic sensor coverage (sysinfo CPU/memory/disk/load/uptime, logind idle/locked, UPower battery), no SMART, no network rates, no OOM events, no firmware security, no GPU, no per-core frequencies; eight test functions against 3,909 commits; eleven commits of history against a monthly release cadence with cosign-signed artefacts across 26 assets per release [[interim-report-adopt-vs-build-honest-verdict]] [[releases-joshuargo-hass-agent-github]] [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. Its notification story is a button whose payload becomes a body via mqtt.publish — a payload hack, not a notify entity [[interim-report-adopt-vs-build-honest-verdict]]. Nothing in this comparison is unkind; it is simply the shape of the gap between a personal prototype and an ecosystem product [[repo-map-ha-linux-agent]].

## 4. The Build-vs-Buy Dialectic: Custom Rust Agent vs Telegraf, Glances, and Netdata

The build camp's strongest case, stated at full strength because it deserves it: the fleet's deciding feature is not sensors, it is the launcher mutual-exclusion session select — a Home Assistant dropdown that switches a kiosk between dashboard and arcade modes by starting and stopping systemd units in a mutually exclusive group, with the entity surface generated declaratively from `jupiter.services.haAgent.launcherApps` in the host config, plus a backlight-as-dimmable-light profile fused to the kiosk power service and a customer-display switch, all at one-second polling [[interim-report-adopt-vs-build-honest-verdict]]. go-hass-agent's control vocabulary is button, switch, and number only; its own user hit this exact wall in January 2026 trying to build an audio-output selector: "Wondering if we can select audio output device with go-hass-agent... I can't see a means to do a drop-down selector box with multiple text items" [[go-hass-agent-a-native-app-integration-for-desktoplaptop-devices-share-your-proj]]. Its controls are explicitly unsynchronised: "States are not kept in sync. This is most important for all controls besides buttons" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. Its dual-transport design produces the split-brain it documents itself: sensors under the Mobile App integration, controls under the MQTT integration, and "due to limitations with the Home Assistant architecture, these cannot be combined in a single place" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. It cannot run MQTT-only ("It makes use of the Native App Integration API that is not MQTT only"), it requires MQTT v5 on the broker, and it refuses to run as root — matching the fleet's user-service-plus-linger deployment shape but foreclosing a system-service fleet design [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[interim-report-fleet-service-model-by-host-class]]. Neither incumbent has a nixpkgs service module — the audited module-list carries home-assistant, esphome, zigbee2mqtt, zwave-js, matter-server and more, but no go-hass-agent or lnxlink module — and lnxlink is not packaged at all [[module-listnix]].

Now the sceptic's answers, honestly weighted. First, the select gap is thinner than "architecturally inexpressible." lnxlink ships a Steam game-launcher dropdown (a select of launchable games) and a bash-command module that creates sensors, binary_sensors, buttons, and switches from shell scripts [[lnxlink]] — a mutual-exclusion session select is one bash module emitting the current active unit and toggling via `systemctl start`, which is where the mutual exclusion already lives anyway: the launcher backend's entire mechanism is shelling out to `systemctl start/stop/is-active` against polkit-gated units that jupiter-os already defines [[interim-report-adopt-vs-build-honest-verdict]]. The claim that only a bespoke Rust backend can express "start exactly one of these units" overstates what the backend does [[repo-map-ha-linux-agent]]. Second, the split-brain is real and is adoption's genuine price — but weigh it against the live alternative: two coherent devices per kiosk versus one device per kiosk that is currently unavailable in the dashboard [[interim-report-mqtt-lifecycle-supervisor-spec]]. A split identity that works beats a unified identity that doesn't. Third, the notification asymmetry that motivated HASS.Agent fandom — actionable notifications — has no Linux implementation anywhere: go-hass-agent's feature requests for smart notifications with action buttons (#667, opened December 2025) and clear_notification support (#926, August 2026) sit open with zero maintainer engagement [[interim-report-adopt-vs-build-honest-verdict]]. The build camp cites this against MQTT; it is equally evidence that no transport gets you this today, so it cannot decide between them.

On the boring-tooling flank, concede the incumbents' failures at full strength, because they do not rescue the custom agent. Glances is Home Assistant's own documented monitoring path — Local Polling of a per-host Glances REST server (Web Server Mode, port 61208, API v3), with a genuinely broad sensor catalogue (per-mount disk usage, per-disk IO rates, memory and swap, load, process counts, CPU, lm-sensors temperatures, Docker counts, RAID devices, per-NIC rx/tx, per-GPU VRAM/processor/temperature/fan, uptime) [[glances-home-assistant]]. It is also a six-year reliability cautionary tale: sensors renamed with `_2` suffixes after every restart (issue #32328, February 2020, "This renaming is undone if I remove then re-add the integration... until the next restart. Then it happens again"), integrations that "loses connection and doesn't automatically recover" (issue #110551, February 2024, closed as not planned and labelled stale, with the reporter forced to hit reload "for several days until it happens again"), and "sometimes stops reporting current data" (issue #170384, May 2026, possibly broken by the 2026.05 release) [[glances-sensors-are-renamed-after-a-restart-issue-32328-home-assistantcore-githu]] [[glances-integration-loses-connection-and-doesnt-automatically-recover-issue-1105]] [[glances-integration-sometimes-stops-reporting-current-data-issue-170384-home-ass]]. It serves 1.3% of active installations with a single integration owner [[glances-home-assistant]]. Glances is not the answer, and the fleet should not adopt it. Telegraf's MQTT output plugin is real and current — protocols 3.1.1 and 5, QoS control, retain flags, homie-v4 layout [[telegrafpluginsoutputsmqttreadmemd-at-master-influxdatatelegraf-github]] — but it emits metric topics, not Home Assistant discovery payloads; making entities appear requires telegraf2hassio-style hub-side glue or manual template sensors, and the plugin's own documentation carries a mosquitto keep-alive footnote ("there is a bug requiring the keep_alive value to be set non-zero in Telegraf. Otherwise, the server will return with identifier rejected") [[telegrafpluginsoutputsmqttreadmemd-at-master-influxdatatelegraf-github]]. Telegraf cannot discover; koying's actual recommendation bypasses the problem entirely — Telegraf straight to InfluxDB, with Home Assistant's InfluxDB integration importing what automations need [[system-design-architecting-ha-data-flows-with-telegraf-mqtt-influxdb-and-grafana]]. Netdata's marketed footprint ("CPU 1%-5% of a single core with default settings... RAM 100-200 MB on an empty system; 250-350 MB in typical production. Disk ~4 GiB by default") is already too heavy for kiosk-class hardware, and the community record is worse: "From 200-400 MB for regular servers to 700-1000+MB for kvm hypervisors. USED memory. And that's just in a single month" — with a Netdata staff reply conceding the 100 MB claim is "obsolete" and steering low-resource systems toward Parent-Child centralisation, RAM mode, and disabling ML [[resource-utilization-netdata-agent-learn-netdata]] [[insane-netdata-memory-usage-help-netdata-community-forums]] [[agent-performance-optimization-guide-configuration]]. For the server hosts, though, this boring stack is proven: smartd does SMART alerts with no agent at all (below), NUT covers UPS with buttons, switches, and automation examples Home Assistant documents itself [[network-ups-tools-nut-home-assistant]], and Prometheus handles metric history — with the concession that Home Assistant's own Prometheus integration exports entity-level metrics only ("alarm_control_panel, automation, binary_sensor, climate, cover..."), not host metrics, so hosts need a separate scraper and Grafana [[prometheus-home-assistant]].

The dialectic's resolution from this side of the table: the custom agent loses on sensor breadth catastrophically, loses on reliability provenance (its defects are the incumbents' fixed bugs [[changelogmd]]), loses on packaging (nixpkgs proper versus a flake with a red check [[go-hass-agent-mynixos]] [[interim-report-testing-gate-for-hardware-daemon]]), and wins only on the launcher session model — which, examined closely, is a systemd-and-polkit design wearing a Rust backend as a coat [[interim-report-adopt-vs-build-honest-verdict]] [[repo-map-ha-linux-agent]]. Buy the agent. Keep the systemd design. It was never the daemon's to begin with.

## 5. NixOS Fleet Architecture: From Kiosk-Only to Every Host in jupiterOS

The honest scope first, because the ambition outpaces the fleet's own configuration: "every host in jupiterOS" currently means four of seven. The agent runs on the four TCxWave kiosks (amalthea, adrastea, metis, thebe); callisto deliberately opts out (its arcade-console module strips "cage + polkit + ha-agent wiring for a dashboard this host doesn't have"); europa — the ZFS NAS running headscale and syncthing, the exact host the zfs/syncthing/headscale backends were written for — does not run it; and pallene, a ZFS-less Kamatera VPS, hard-opts-out ("No ZFS, no impermanence, no sops-nix, no ha-linux-agent") [[interim-report-adopt-vs-build-honest-verdict]] [[interim-report-fleet-service-model-by-host-class]] [[interim-report-headless-privilege-ladder]]. Any fleet architecture claim must survive this ground truth: the deployment question is not "how to reach every host" but "what does each host class need, and what decision unblocks pallene" — and pallene's lack of sops-nix makes the secrets path a user decision no agent choice can dodge [[interim-report-fleet-service-model-by-host-class]].

The deployment model transfers. go-hass-agent's maintainer designs the systemd path for exactly this use: "The systemctl service is primarily for 'headless' usage (i.e., servers) not running any desktop environment" — with manual command-line registration (`go-hass-agent register --token ... --server ...`), enable-linger, and `systemctl --user enable go-hass-agent`, precisely the user-service-plus-linger shape jupiter-os already runs for the current agent, so the operational muscle memory is identical [[interim-report-adopt-vs-build-honest-verdict]] [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. The agent refuses root ("You cannot run Go Hass Agent with root privileges or as the root user. The agent will refuse to run"), which matches NixOS's least-privilege instincts, and applies file capabilities (cap_sys_rawio, cap_sys_admin, cap_mknod, cap_dac_override) for SMART only where the packaging controls it — capabilities on an unprivileged process, the same compromise the service-model investigation eventually reached for the custom agent [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[interim-report-fleet-service-model-by-host-class]]. The container path exists for the headless hosts if that shape is preferred: PROCFS_ROOT/SYSFS_ROOT/DEVFS_ROOT environment variables for alternative mount points, host /proc, /sys, and the D-Bus sockets mounted read-only, capabilities added [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. One recent NixOS change even improves the incumbent's user-service posture: since PR #517768 (May 2026) and the switch-to-configuration-ng rewrite, `nixos-rebuild switch` now restarts user units for users with active managers, so a user-service agent picks up config changes on switch rather than waiting for a reboot — the exact gap that motivated the custom agent's system-service redesign, closing for free under adoption [[interim-report-fleet-service-model-by-host-class]].

The concessions on this flank are packaging ones. Neither incumbent has a nixpkgs service module, so "adopt" means writing one — but a service module for an existing binary is a systemd unit, a sops secret, and an environment block: tens of lines, not twelve crates, and there is precedent to crib from in the nineteen home-automation modules already in-tree [[module-listnix]]. The Proxmox user's 2025 plea for a core/GUI package split ("When I try to install the .deb it fails because of dependencies related to the GUI") shows go-hass-agent's headless story took real time to mature [[go-hass-agent-a-native-app-integration-for-desktoplaptop-devices-share-your-proj]] — but it did mature: the modern v14 packaging installs cleanly headless, and the project auto-detects headless mode and defaults to it with a warning, a fix visible in the changelog ("if no GUI detected, default to running headless") [[interim-report-adopt-vs-build-honest-verdict]] [[changelogmd]]. lnxlink's NixOS story is genuinely bad: not in nixpkgs, and a 2025 packaging attempt documents a propagatedBuildInputs list coupling the agent to pygobject3, ewmh, xlib, opencv-python, pulsectl, pyalsaaudio, docker, and speechrecognition — a GUI-and-audio-coupled Python surface that explains why no one has upstreamed it and that pushes lnxlink toward Docker or pipx on NixOS rather than native packaging [[python-packaging-error-needs-specific-setuptools-version-nixos-discourse]]. The honest fleet recommendation this implies: go-hass-agent as the native NixOS agent (it is one `environment.systemPackages` line away today at v14.15.1 [[go-hass-agent-mynixos]]), lnxlink only if the desktop long tail (screenshots, hotkeys, clipboard) ever becomes a real requirement [[lnxlink]], and a secrets decision for pallene that is orthogonal to which agent wins [[interim-report-fleet-service-model-by-host-class]].

## 6. JupiterOS-Specific Feature Gaps

Walk the gap list the improvement camp compiled and price each item at adoption rates. **Systemd unit health:** lnxlink ships it as a first-class module ("Manage Linux services; check status, start, or stop specific units") [[lnxlink]]; go-hass-agent reaches it through script sensors or arbitrary D-Bus invocation [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]; and the unprivileged system-bus subscription design the privilege investigation proved live (match rules, no polling, logrotate's job delivered to io with zero grants on callisto) is a channel any agent or script can use — it was never exclusive to a bespoke backend [[interim-report-headless-privilege-ladder]]. **SMART/NVMe:** the mature tooling landscape is the point — an entire ranked landscape of NVMe/SSD health tools exists, from netdata's per-second collectors to smartctl_exporter's 60-second scrapes [[best-nvme-ssd-health-monitoring-tools-9-options-ranked]]. smartd already runs privileged on europa and its `-M exec` directive turns disk problems into events, exporting SMARTD_DEVICE, SMARTD_DEVICETYPE, SMARTD_FAILTYPE, SMARTD_MAILER and a documented set of environment variables to any script — with the one honest caveat that "smartd will block until the executable PATH returns, so if your executable hangs, then smartd will also hang" [[smartdconf5-smartmontools-debian-testing-debian-manpages]]. Whole products exist above smartctl: smartctl_exporter (325 commits, smartmontools >= 7.0 for JSON output, 60-second polls, 10-minute rescans, port 9633, root-privileged by design, with an explicit no-data-mutation policy — "In general, the smartctl_exporter should not modify the data in flight. If the data is missing from smartctl, it should not be in smartctl_exporter") and Scrutiny (hub-and-spoke with one collector per server, InfluxDB-backed history, real-world failure-rate correlation — "merging manufacturer provided S.M.A.R.T metrics with real-world failure rates") [[github-prometheus-communitysmartctl_exporter-export-smartctl-statistics-to-prome]] [[github-analogjscrutiny-hard-drive-smart-monitoring-historical-trends-real-world]]. go-hass-agent ships per-disk SMART with capability handling in its own binary [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. The fleet's SMART need is a solved problem with four shipping solutions; the custom backend is a fifth, unverified one [[interim-report-adopt-vs-build-honest-verdict]]. **ZFS pool health:** concede cleanly — no incumbent ships a ZFS pool-state sensor, and "the thing you'd actually want an HA alert on" is real [[interim-report-adopt-vs-build-honest-verdict]]. But the nearest incumbent mechanism is deliberately built for exactly this shape: a go-hass-agent script sensor is any shebang script emitting JSON on a cron schedule ("Go Hass Agent makes no attempt to do any analysis or sanitization of script output, other than ensuring the output is a supported format"), and a zpool health parse into a sensor is two lines of shell — and the unprivileged /proc/spl/kstat path the privilege investigation identified makes the read possible without root [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[interim-report-headless-privilege-ladder]]. The choice is not "backend-zfs crate versus nothing"; it is "backend-zfs crate versus a script sensor plus a zedlet." **Mesh/exit-node and syncthing:** same shape — headscale status and syncthing's REST API are one cron script each, and the custom backend's own unverified flag is an admission it never got further than that either [[interim-report-adopt-vs-build-honest-verdict]]. **Nix generation/boot health:** a script sensor over the profiles directory — configuration, not architecture [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. **Remote reboot/poweroff:** go-hass-agent ships suspend, hibernate, power off, and reboot controls natively over logind, plus inhibit locks; lnxlink ships shutdown/restart/suspend/boot-select; the custom agent's reboot command is a `systemctl` shell-out it shares with both [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[lnxlink]].

The pattern across every row: the jupiterOS "gaps" are either already shipped by incumbents (power, systemd, SMART, GPU, backlight) or are natural script-sensor material (ZFS, headscale, nix generations) — the two-line-shell class of feature [[lnxlink]] [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. The one genuinely bespoke item remains the launcher mutual-exclusion select, and its bespoke content lives in the fleet's systemd units and polkit rules, which adoption leaves untouched [[interim-report-adopt-vs-build-honest-verdict]]. The feature-gap table, priced honestly, is an argument for adoption, not against it: the custom agent's architecture is a twelve-crate answer to a two-line-shell question, minus the parts the incumbents already ship [[repo-map-ha-linux-agent]].

## 7. Testing a Hardware-Touching Daemon

The testing investigation produced a disciplined seven-step ladder: fix the clippy lint, wire `craneLib.cargoTest` so the eight existing tests finally run in a gate, inject a sysfs root and test against tempfile-built synthetic trees, extract an Agent::run seam, build a mosquitto-subprocess harness with port-0 binding and Drop-guard kills, add a private dbus-daemon harness, and cap it with a runNixOSTest cribbed from nixpkgs' own three-node mosquitto test — testcontainers explicitly rejected on fleet ground truth (no container runtime exists on any jupiterOS host or remote builder) [[interim-report-testing-gate-for-hardware-daemon]]. It is a good plan. It is also the strongest single argument for adoption, because every rung of it is work the incumbents finished long ago and maintain in public. go-hass-agent ships .golangci-ci.yaml, codecov.yml, .pre-commit-config.yaml, an osv-scanner.toml, a BREAKING_CHANGES.md discipline, release-please automation, and a changelog whose every entry is a commit hash traceable to a tested change — the 3,909-commit figure is not a vanity metric, it is CI throughput [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[releases-joshuargo-hass-agent-github]]. smartctl_exporter carries device_filter_test.go and smartctl_test.go in its tree [[github-prometheus-communitysmartctl_exporter-export-smartctl-statistics-to-prome]]. The defect-named regression tests the ladder prescribes — broker-restart re-subscribe, birth-message republish, SIGTERM offline-then-disconnect, hung-backend isolation — are re-creations of scenarios the incumbent changelogs show being fixed and regressed against in public: go-hass-agent's "reconnect to MQTT on disconnect and fix issue with MQTT commands not working" is the broker-restart test with a commit attached [[changelogmd]].

The fleet-specific constraint the ladder honours — no Docker anywhere, so testcontainers is dead on arrival — is real, and it cuts both ways: it means any adoption path inherits incumbents whose CI runs elsewhere (GitHub runners, cosign-signed release pipelines [[releases-joshuargo-hass-agent-github]]), unconstrained by the fleet's containerless builders. The build path alone must solve hardware-daemon testing inside a Nix sandbox, on remote kiosk builders, without a container runtime, before the first reliability fix can even be gated [[interim-report-testing-gate-for-hardware-daemon]]. When the choice is "write a novel test harness for a prototype" versus "inherit a tested product," the testing section of this report is not a neutral methodology discussion — it is a tally of the adoption discount.

## 8. Ordered Improvement Roadmap

Read the heading as the question intends it — improve the fleet's agent situation — and the ordered roadmap is: stop, trial, migrate, decommission, and only then, if the evidence demands, build. Ordered by risk and reversibility:

**Phase 0 — stop the bleeding and establish the baseline (days).** Freeze feature work on ha-linux-agent [[repo-map-ha-linux-agent]]. The kiosks currently read unavailable in Home Assistant [[interim-report-mqtt-lifecycle-supervisor-spec]]; either accept the outage window or apply the single-line mitigations that cost nothing (mosquitto `persistence true` on callisto so broker restarts stop wiping sessions fleet-wide) while the trial runs [[interim-report-mqtt-lifecycle-supervisor-spec]]. Capture the fleet's actual entity usage — the launcher select, the backlight light, the customer-display switch, the hardware sensors at one-second polling [[interim-report-adopt-vs-build-honest-verdict]] — as the acceptance checklist any successor must meet.

**Phase 1 — trial go-hass-agent on one kiosk and one server (a fortnight).** Install the nixpkgs v14.15.1 package on amalthea [[go-hass-agent-mynixos]]; register with a long-lived token; run it as the user service with linger, the shape the fleet already operates [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[interim-report-adopt-vs-build-honest-verdict]]. Measure honestly: how much of the sensor catalogue survives a cage-kiosk NixOS host with no XDG portal and no desktop environment — platform-conditional degradation is a documented risk class (the project's own sensor list warns "the actual sensors reported may be less due to lack of support in the system configuration or missing hardware", and its FAQ admits hardware sensors ship "without any chip-dependent scaling/transformation") [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. In parallel on europa: keep smartd (it is already privileged and scheduled [[interim-report-headless-privilege-ladder]]), wire one `-M exec` hook or one script sensor for pool health [[smartdconf5-smartmontools-debian-testing-debian-manpages]], and confirm the headless service path [[interim-report-adopt-vs-build-honest-verdict]].

**Phase 2 — rebuild the control plane as configuration, not code (a fortnight).** The launcher mutual-exclusion select becomes either a lnxlink bash-command module or a go-hass-agent script sensor plus a D-Bus command — the mutual exclusion itself stays in the systemd units and polkit rules jupiter-os already owns [[lnxlink]] [[interim-report-adopt-vs-build-honest-verdict]]. Backlight-as-light: go-hass-agent honours backlight controls (v14.10.3 fixed ddcutil backlight detection; v14.15.0 honoured disabled preferences before capability checks) [[releases-joshuargo-hass-agent-github]], or the existing udev GROUP="video" fix the privilege investigation prescribed — which is a fleet fix, not an agent feature, and ports to any agent [[interim-report-headless-privilege-ladder]]. Notifications: one-way via the incumbent's native path; accept that actionable notifications have no Linux implementation anywhere and stop pricing them into the decision [[interim-report-adopt-vs-build-honest-verdict]].

**Phase 3 — fleet rollout and decommission (a month).** Roll to the remaining kiosks [[interim-report-fleet-service-model-by-host-class]]; make the pallene secrets decision explicitly (long-lived token in a unit EnvironmentFile, or extend sops-nix to the VPS — orthogonal to agent choice) [[interim-report-fleet-service-model-by-host-class]]. Decommission ha-linux-agent with a zero-payload discovery cleanup so no ghost devices linger in Home Assistant — ironically, the one lifecycle feature the improvement roadmap specified that adoption still needs to borrow [[interim-report-mqtt-lifecycle-supervisor-spec]].

**Phase 4 — the honest flip conditions (contingency).** The adoption path fails and the build case revives if and only if: the kiosk trial shows go-hass-agent's sensor surface degrades materially on cage-kiosk NixOS [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]; the launcher select cannot be expressed cleanly through lnxlink's or go-hass-agent's extension mechanisms [[lnxlink]]; or the split-brain two-device identity proves operationally unacceptable in the fleet's real dashboards and automations [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. If any of those fire, the correct next step is the improvement camp's audited fix list — ConnAck supervisor, capability ladder, testing ladder [[interim-report-mqtt-lifecycle-supervisor-spec]] [[interim-report-headless-privilege-ladder]] [[interim-report-testing-gate-for-hardware-daemon]] — with the present draft's concession table as the spec's risk register. The audit work is not wasted either way; it is the acceptance criteria for whichever agent wins.

## Opinionated Synthesis

The thesis, committed: ha-linux-agent should not be improved; jupiterOS should adopt go-hass-agent as its fleet agent, keep smartd/Telegraf-class boring tooling for server depth, and express the launcher session model in the systemd-and-polkit layer where it already lives. The chain: (1) the codebase has never been reliable — its two verified lifecycle defects fire on every broker restart, and the broker's own defaults guarantee restarts, so "never reliable" is not a perception but the system's steady state [[interim-report-mqtt-lifecycle-supervisor-spec]]; (2) the improvement programme is a solo re-derivation of reliability lessons every incumbent shipped publicly, on a dependency whose own reconnect bug has been open five-plus years [[changelogmd]] [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]] [[interim-report-rumqttc-dependency-fitness]]; (3) the incumbents' documented imperfections — split-brain identity, unsynchronised controls, MQTT v5 requirement, missing NixOS modules, lnxlink's packaging morass — are real but are configuration and polish problems [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[module-listnix]] [[python-packaging-error-needs-specific-setuptools-version-nixos-discourse]], while the custom agent's are existence problems [[interim-report-testing-gate-for-hardware-daemon]]; (4) every jupiterOS-specific gap is either already shipped (power, systemd, SMART, GPU, backlight) or a two-line script sensor (ZFS, headscale, nix generations) [[lnxlink]] [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[smartdconf5-smartmontools-debian-testing-debian-manpages]]; (5) the one genuinely bespoke feature, the mutual-exclusion session select, owes its existence to systemd units and polkit rules the fleet already maintains — the Rust backend is a relay, and relays are commodities [[interim-report-adopt-vs-build-honest-verdict]] [[repo-map-ha-linux-agent]]. The deepest point in favour of adoption is the one the build camp's own audit supplies: a project whose CI runs zero tests and whose check gate is red does not need a roadmap; it needs a reason to exist [[interim-report-testing-gate-for-hardware-daemon]]. The fleet's requirements, examined row by row, do not supply one. The forward-looking implication: the incumbent's monthly cadence means the fleet's agent gets better every month without this project's owner writing a line — sensor depth, hardware quirks, security bumps arrive as nixpkgs updates [[releases-joshuargo-hass-agent-github]] [[go-hass-agent-mynixos]] — while the build path means every D-Bus API change, every backlight driver quirk, every MQTT subtlety, and every rustc release is this project's problem forever. Choose the future where the maintenance is someone else's full-time job and the fleet's bespoke surface is a directory of declarative configuration.

## Source Tensions

**MQTT hop vs direct database injection.** koying's "unnecessary point of failure" is this draft's home turf, and it holds for the metrics half of the fleet's needs: europa's long-horizon history belongs in Telegraf-to-database flows, not in a broker hop [[system-design-architecting-ha-data-flows-with-telegraf-mqtt-influxdb-and-grafana]]. The honest scoping concession: jupiterOS runs no InfluxDB and its kiosk control plane genuinely needs bidirectionality, so MQTT survives for control and presence — halinuxcompanion's own migration-to-MQTT to-do (native API leaves sensors "stuck" when hosts go offline; only will topics reflect it) is the counter-architecture conceding the point from the inside [[github-muniterhalinuxcompanion-homeassistant-linux-companion-github]], and HA core's MQTT const.py carrying notify among discovery-supported components removes the last "notifications need the native API" argument [[corehomeassistantcomponentsmqttconstpy-at-dev-home-assistantcore-github]]. The resolution this draft argues: split the problem along the same seam koying drew — boring pipelines for data, a maintained MQTT agent for control — rather than building one daemon that is mediocre at both.

**go-hass-agent's MQTT v5 + unsynchronised controls vs the custom agent's v3.1.1 + synced state.** This is the objection I must disarm, and the disarm is the split-brain: adopting go-hass-agent means every control's state is unsynchronised AND every host appears as two devices that "cannot be combined" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. The honest answer is not denial but weighting: unsynchronised switch state is a dashboard annoyance with a mitigation (poll the real state via a script sensor [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]), whereas the custom agent's synchronised state rides on a transport that goes permanently deaf after a broker restart [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]] [[interim-report-mqtt-lifecycle-supervisor-spec]] — state sync atop a channel that drops commands is worse than no state sync on a channel that works. The fleet's live unavailability is the tiebreaker [[interim-report-mqtt-lifecycle-supervisor-spec]].

**Netdata's marketed footprint vs community-documented blowups.** Both sides are right in scope: the vendor's 100-200 MB is the empty-system default, and the community's 200-1000+ MB is the metric-heavy reality, with the vendor's own optimisation guide a recipe for disabling most of the product [[resource-utilization-netdata-agent-learn-netdata]] [[insane-netdata-memory-usage-help-netdata-community-forums]] [[agent-performance-optimization-guide-configuration]]. This tension refutes Netdata for the kiosk hardware class and leaves it a legitimate europa option — it does not touch the go-hass-agent case, whose own FAQ claims "well less than 50 MB" with jittered polling intervals [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]].

**In-process SMART polling vs smartd's privileged hooks.** The smartd `-M exec` path wins for this fleet — zero new privilege, smartd already runs on europa, and the SMARTD_* contract is man-page documented [[smartdconf5-smartmontools-debian-testing-debian-manpages]] [[interim-report-headless-privilege-ladder]] — but note what that means: the fleet's SMART answer is a mature daemon and a hook script, which is precisely the boring-tooling thesis, and it undercuts the custom backend-hardware crate as much as it undercuts smartctl_exporter's root-privileged polling [[github-prometheus-communitysmartctl_exporter-export-smartctl-statistics-to-prome]].

**Testcontainers consensus vs containerless fleet ground truth.** The consensus is correct for Docker-equipped CI and dead on arrival for this fleet's builders [[interim-report-testing-gate-for-hardware-daemon]] — but the tension dissolves under adoption: the incumbent's test suite runs on its own CI [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[releases-joshuargo-hass-agent-github]], and the fleet's containerless constraint stops being a testing constraint at all. It only binds the build path, which is why it appears here as an adoption argument.

**Retained-everything discipline vs birth-triggered republish with broker sizing.** The rare fully-resolved tension: retain everything AND republish on birth/ConnAck with jitter AND size the broker — Z2M and ESPHome's combined posture [[mqtt-home-assistant]] [[interim-report-mqtt-lifecycle-supervisor-spec]]. From this angle it is a burden line, not a fight: whichever agent wins, it must implement the full contract; go-hass-agent's changelog shows it doing exactly that work in public [[changelogmd]], while the custom agent has implemented none of it [[interim-report-mqtt-lifecycle-supervisor-spec]]. A resolved tension where one side has shipped the resolution and the other has a specification is not a tension — it is a purchase order.
