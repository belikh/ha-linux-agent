# The Boundary Is the Feature: A Conditions-Based Architecture for ha-linux-agent on Every jupiterOS Host

**Answer first.** The "sloppy, never reliable" state of ha-linux-agent is real, verified, and fixable — and the right course is neither pure rebuild nor adoption of an incumbent, because the correct decision varies by a boundary the evidence draws with unusual clarity: **the boundary is the feature, not the host.** Where jupiterOS-native control is load-bearing — the kiosks' launcher mutual-exclusion session select, the backlight-as-dimmable-light profile, the server hosts' ZFS/headscale/syncthing surfaces — improving this agent wins outright, because every incumbent is architecturally incapable of expressing those features: go-hass-agent's complete release history from v4.3.1 to v14.15.1 contains zero occurrences of select entities, control state synchronisation, or NixOS support [[changelogmd]], its own documentation admits "States are not kept in sync" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]], and neither go-hass-agent nor lnxlink has a NixOS service module in nixpkgs [[module-listnix]]. Where plain monitoring would nominally suffice — the server hosts' telemetry — the monitoring incumbents fail this fleet's HA integration needs too: Glances is a local-polling REST scrape used by 1.3% of HA installations with a multi-year failure history, Telegraf cannot speak HA discovery without hub-side translation glue, and Netdata's real-world footprint refutes it for TCx Wave-class hardware. The same agent on every host is not ideology — it falls out of the boundary analysis on both sides.

The improvement is made safe by four pieces of boundary machinery: a **host-class service split** (one system service, `User=io`, everywhere — the 2026 switch-to-configuration-ng change makes user units actively harmful [[anyone-seeing-nixos-rebuild-switch-kick-you-out-to-gdm-andor-log-gpf-errors-spec]]); a **zero-capability event-driven privilege matrix** (smartd `-M exec` hooks, a zed bridge, D-Bus match rules, udev video-group membership — no AmbientCapabilities by default [[interim-report-headless-privilege-ladder]]); the **notification fork resolved onto notify.mqtt** ("notify" in HA's MQTT `SUPPORTED_COMPONENTS` [[corehomeassistantcomponentsmqttconstpy-at-dev-home-assistantcore-github]], the platform landed in HA 2024.5 with a two-field upstream test payload [[test_notifypy]]); and a **7-step testing ladder as definition-of-done**, anchored by a mosquitto-subprocess harness the Nix sandbox source itself validates [[local-derivation-goalcc]]. Reliability first, fleet-wide second, features third — because nothing else matters while the agent is intermittently deaf.

## 1. Current State: A Verified Reliability Audit

The presenting symptom is live: the four kiosks' Home Assistant entities read UNAVAILABLE on callisto's HA instance right now — the exact "never reliable" complaint, observed in production. The audit grounds every defect in file:line evidence, observed exit codes, or verbatim source, and closes with the boundary-condition reading that determines the whole report.

**The verified defect inventory.** The codebase is 43 files, 278 symbols, 12 crates, 11 commits [[repo-map-ha-linux-agent]]. The lifecycle core — `crates/core/src/agent.rs`, 198 lines — carries the two root-cause defects: subscriptions issued exactly once in a fire-and-forget setup task (`agent.rs:134-138`) while the poll loop swallows every reconnect event with `Ok(_) => {}` (`agent.rs:190`); and availability "online" published retained exactly once (`agent.rs:139-144`) and never re-asserted. The first broker restart, HA restart, or network blip therefore permanently deafens the agent (it keeps publishing but can never receive) and permanently marks it offline in HA — the mirror-image pair every user reads as "the agent is broken" [[interim-report-mqtt-lifecycle-supervisor-spec]]. Four aggravators, each verified: the request channel is built at capacity 64 rather than the rendezvous semantics rumqttc's docs recommend, so outages queue stale telemetry; backend-syncthing builds its reqwest client with no timeout (`backend-syncthing/src/lib.rs:75`, `:98`) and `agent.rs:154-157` polls all backends sequentially in one task, so one hung daemon starves every sensor on the host while availability still says "online" — sensors that lie rather than sensors that vanish, the worst failure class a fleet can have; there is no signal handling anywhere (zero grep hits) and the deployed user unit sets no `Restart=`, so a crashed agent stays dead until reboot; and the graceful-shutdown absence is saved only by an accident — the ungraceful TCP close fires the retained last-will [[interim-report-mqtt-lifecycle-supervisor-spec]].

**The privilege story is worse than sloppy — it is silently broken.** jupiterOS ships a root-owned oneshot `ha-linux-agent-sysfs-perms` (`ha-agent.nix:117-124`) chmoding backlight and cpufreq nodes 0664, with a comment at `ha-agent.nix:112` claiming "io is in the groups that own the nodes (video for backlight...)". That comment is false: 0664 grants group-write to group `root`; io's only group is `wheel`; no host adds io to `video`. The agent's brightness/governor/EPP writes therefore fail EACCES today, logged only as a `warn!` in `write_sys_file` (`backend-hardware/src/lib.rs:108-111`), invisible at the HA layer — while `tcxwave-kiosk.nix:199` still claims "0666 permission" [[interim-report-fleet-service-model-by-host-class]]. The kiosks run `pollIntervalSecs = 1` ("i want updates every second", per the fleet's own comment): a hardware-touching daemon failing its hardware writes on its four only consumers, silently. An audited absence compounds it: no mako, dunst, or swaync ships anywhere in the fleet, so the notification backend is dead code on every host it ships on [[interim-report-adopt-vs-build-honest-verdict]].

**The quality gates are absent, not merely failing.** The workspace has 8 test functions (3 in `discovery.rs`, 5 in `backend-launcher/lib.rs` — the "3 tests" figure from earlier in this research was stale; the deeper truth is that none run in any gate: the flake's checks contain only `buildPackage` and `cargoClippy --deny warnings`, no `craneLib.cargoTest` at all). Clippy is red at `backend-hardware/src/lib.rs:117` (`map_or` → `is_some_and`), so `nix flake check` fails before a single test could run; there is no `.github/`; and the README flags three backends — zfs, syncthing's REST fields, lutris's JSON field names — as "unverified in a live environment" [[interim-report-testing-gate-for-hardware-daemon]]. The repository's own ROADMAP names backend-zfs's pool-health binary sensor as "the thing you'd actually want an HA alert on" [[interim-report-adopt-vs-build-honest-verdict]] — an aspiration on a backend that has never run against a real pool.

**The boundary-conditions reading.** A flat audit says "prototype, rewrite or replace". The boundary reading is more precise: the defects are not uniformly distributed — they cluster in the lifecycle core every host class shares, while the per-backend surfaces are small self-contained crates of 100-330 lines behind two traits [[interim-report-adopt-vs-build-honest-verdict]]. That distribution is why "reliability first" is a sorting, not a slogan: fixing `agent.rs` lifts kiosks, servers, and future desktop hosts simultaneously, and no incumbent substitution delivers that leverage. A small, auditable prototype whose worst defects are known to the line and concentrated in one file pair is an argument for fixing it, not proof it is unfixable.

## 2. The MQTT Lifecycle Problem: Why It Is Never Reliable

"Never reliable" has a mechanical explanation, and it is not vague: two bugs in the agent, two default-shaped traps in the broker, and one library-level design fact that will never change upstream.

**The library-level fact.** rumqttc 0.24.0 — the exact version pinned in Cargo.lock — reconnects automatically when the application keeps polling its event loop, but it never re-establishes subscriptions after a reconnect. Issue #250 has been open since February 2021; the "in-pipeline" label points at PR #1052, which is open, unreviewed, v5-scoped, and — decisively — even its own design leaves subscription ownership with the application, emitting only a reconnect signal. The only credible alternative, Paho, has the same application-owned re-subscription plus a C-toolchain cost on NixOS builds [[interim-report-rumqttc-dependency-fitness]]. Inference, stated per the deep-inference licence: no single source announces "the supervisor must live in the application forever", but the rumqttc PR design (signal-only) and the Paho callback surface (application re-subscribes) jointly imply it — waiting for upstream saves nothing.

**The two agent bugs and what they compound into.** With a clean session (rumqttc's default), every reconnect destroys broker-side session state — subscriptions included. Callisto's mosquitto sets no `persistence`, so the "in memory only" default applies: every broker restart wipes all sessions fleet-wide. The result is deterministic: the first mosquitto restart, HA restart with a dropped connection, or network blip leaves every agent permanently deaf (it can still publish — the poll task is independent — but no command will arrive) and, once the last-will has fired, permanently marked offline in HA. The Zigbee2MQTT availability machinery — the production reference — shows what correctness looks like: retained QoS 1 availability publishes, check-in windows (10 minutes active, 25 hours passive), pings with bounded random jitter (max 30,000 ms), backoff at ×1.5/×3/×6/×12, timeout state persisted across restarts [[device-availability-zigbee2mqtt]]. ESPHome, the other reference, pairs birth and will with an explicit `shutdown_message` for clean exits and a 15-minute `reboot_timeout` watchdog — the exact combination the agent lacks [[mqtt-client-component-esphome-smart-home-made-simple]].

**The broker-side traps.** Mosquitto's per-client queue defaults to 1000 QoS 1/2 messages (`max_queued_messages`), with `persistence` false; queue admission is per-client and, for a disconnected client, the in-flight adjustment zeroes out — `db__ready_for_queue` computes `valid_count = source_count - adjust_count < max_queued_messages` and sets `adjust_count = 0` when the client is not connected, so the full queue depth is available to an offline replay [[databasec]]. At scale this is exactly the mechanism behind HA issue #135266: at 5,374 entities the broker silently dropped retained messages during HA's startup replay — 56 of 112 affected topics arrived empty while MQTT Explorer showed them present — and raising the queue limit was "the instant cure" [[interim-report-mqtt-lifecycle-supervisor-spec]]. No source states jupiterOS's entity count will hit that wall; the sizing rule (queue ≥ 4× retained inventory) and the incident jointly imply the hygiene is cheap now and load-bearing later: pair the client fix with `persistence true`, queue headroom, and a `$SYS` confirmation check reading `$SYS/broker/publish/messages/dropped` — the counter mosquitto(8) defines as "dropped due to inflight/queuing limits" [[mosquitto8-mosquitto-debian-unstable-debian-manpages]].

**The committed supervisor design.** One structural change: drive the lifecycle from the poll loop's ConnAck event. On every ConnAck — first or reconnect — re-issue all command-topic subscribes (idempotent; SUBSCRIBE refreshes broker state) and re-assert retained availability "online" before resuming telemetry. Subscribe to `homeassistant/status` and, on HA's birth message, republish all discovery configs after 0-30 s random jitter per host (HA's contract: devices "should subscribe to the Birth message and use this as a trigger to send the discovery payload", random delay recommended against IO storms; Z2M's jitter default supplies the number). Set the request channel capacity to 0 and wrap each publish in a per-tick timeout, so stale state is bounded by one poll interval — and because all state lands on one retained topic per host, a fresh publish overwrites any stale payload: staleness self-heals by construction. Add SIGTERM handling: retained "offline", await, `disconnect()` (which exists in the pinned 0.24.0), exit. Isolate every backend poll and command dispatch in its own timeout-wrapped task with 5-second reqwest timeouts, per rumqtt's rule "Don't block this while iterating" [[interim-report-mqtt-lifecycle-supervisor-spec]].

Two boundary judgements deserve their conditions named. First, `clean_session = true` (explicitly, stable client id) rather than the persistent session an earlier phase presumed: a persistent session's only unique deliverable here is broker-side queueing of commands for offline hosts — and kiosks power off overnight, so it would replay week-old commands on Monday boot with no TTL and no timestamp to age them by. Always-on servers lack the hazard but gain nothing from session state given ConnAck-driven re-subscribe; the design is unconditional, the reasoning kiosk-shaped [[interim-report-mqtt-lifecycle-supervisor-spec]]. Second, the "v3.1.1 forecloses message expiry" claim is half-wrong: rumqttc 0.24.0 ships a complete v5 module internally — `message_expiry_interval`, `session_expiry_interval` — a module-scope switch away, verified in the pinned crate source [[interim-report-rumqttc-dependency-fitness]]. The decommission path stays in the roadmap as hygiene — optional hardening, not a forced workaround; if the fleet adopts MQTT v5 end-to-end, the v5 module is the path and the 0.25.x bump is measured painless (exit 0, zero code changes) but buys nothing today.

The committed position: "never reliable" is two file:line bugs amplified by two broker defaults and one permanent library design fact; the ConnAck-driven supervisor fixes all five at once, fully supported by the pinned dependency; and no feature work should precede it, because a deaf agent makes every new sensor a lie.

## 3. What a Proper Linux Agent Looks Like: The Comparison Set

The comparison set divides into companion-class agents (HASS.Agent, go-hass-agent, lnxlink, halinuxcompanion, the mobile apps) and monitoring-class stacks (Glances, Telegraf, Netdata, node_exporter). A "proper Linux agent" for Home Assistant in 2026 is defined by what the companion class converged on — and the boundary analysis turns on which of those features jupiterOS exercises.**What the companion class established as the baseline.** The mobile companion apps define the contract: a broad sensor set through a single registered device, and actionable notifications whose button taps fire the `mobile_app_notification_action` round-trip — HASS.Agent (Windows) implements it via its `hass_agent_notifications` event. The community's demand signal for a Linux equivalent is explicit — "WTH there is no windows and Linux HA app similar to macOS" (December 2024), a moderator answering "For Linux you've got glances, netdata, system bridge, and system monitor" (the Linux shelf conceded to the monitoring class), and the original poster's "I personally hate mqtt… mqtt is not a native way to integrate" drawing the correction that matters: "You don't have to have MQTT to use HASS.Agent; however, most features rely on it for bidirectional communication. Without MQTT, only Quick Actions will work" [[wth-there-is-no-windows-and-linux-ha-app-similar-to-macos-month-of-what-the-heck]]. The exchange is build-vs-buy in miniature: the moment you want control rather than readout, the ecosystem routes you to MQTT.

**The Linux companion candidates, on the axes that matter.** go-hass-agent is the most mature: dual-transport (mandatory mobile_app registration, optional MQTT v5 side), a large D-Bus/ProcFS/SysFS/Netlink sensor catalogue, script sensors on cron schedules, and a `commands.toml` vocabulary of button/switch/number. Its costs are architectural and self-documented: it "requires MQTT v5 support on your MQTT broker"; it appears in two places in HA — "under the Mobile App integration… under the MQTT integration… due to limitations with the Home Assistant architecture, these cannot be combined in a single place" (split-brain identity); and its controls' "States are not kept in sync… changes to the state you make outside of Home Assistant will not be reflected" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. It refuses root and requires file capabilities (`cap_sys_rawio,cap_sys_admin,cap_mknod,cap_dac_override=+ep`) for SMART — suiting rpm/deb packaging but awkward on a declarative fleet. lnxlink is the feature-envelope champion — roughly 50 modules including notify, idle, media, brightness, and systemd unit management ("check status, start, or stop specific units") — but GUI-coupled (hotkeys "Not for Wayland"), with a pruning-exercise headless install, and not packaged in nixpkgs at all [[lnxlink]]. halinuxcompanion is the cautionary tale from the opposite direction: a native-API Python agent (90 stars) whose own to-do says "Move sensors to MQTT", because "the limitations of the API" leave sensor values "stuck" when the host goes offline, whereas "if the app uses MQTT it can set will topics for the sensors to be updated when the client can't communicate with the server" [[github-muniterhalinuxcompanion-homeassistant-linux-companion-github]] — the one agent that tried native-only is migrating to the transport this repo already uses.

**The definitional table.** On the companion axes — single-device identity, discovery, control model with state sync, notifications, headless fit, NixOS story — the comparison reads:

| Axis | ha-linux-agent (improved) | go-hass-agent v14.15.1 | lnxlink | halinuxcompanion |
|---|---|---|---|---|
| Transport | MQTT-only, one device per host | mobile_app + MQTT v5; two devices, "cannot be combined" | MQTT-only | native API; MQTT on to-do |
| Discovery | MQTT discovery; `select` and `notify` both in HA's supported components [[corehomeassistantcomponentsmqttconstpy-at-dev-home-assistantcore-github]] | MQTT discovery for controls only | MQTT autodiscovery | none (registered device) |
| Control model | select with state round-trip via shared state topic; launcher mutual-exclusion groups | button/switch/number, "States are not kept in sync" | switches/selects per module, no mutual exclusion | notification-attached commands |
| Notifications | notify.mqtt entity (one-way); VFD last mile | one-way; actionable open (#667, #926), maintainer-silent | rich desktop notify | actionable via HTTP round-trip |
| Headless | same binary, backend detect() gates | maintainer-designed headless mode | documented pruning install | desktop-oriented |
| NixOS | flake module + `jupiter.services.haAgent`, deployed today | in nixpkgs as a package; no service module [[module-listnix]] | no package, no module | none |

The committed reading: the comparison set does not show a better agent to adopt; it shows that the companion class's definitional features — single identity over MQTT discovery, controls whose state syncs, headless operation — are exactly the axes where the incumbents are weakest and this repo's architecture (MQTT-only, one device, shared-state-topic selects) is already right. The proper-Linux-agent question is not "which crate has the most sensors" but "which architecture can express the fleet's control plane".

## 4. The Build-vs-Buy Dialectic: Custom Rust Agent vs Telegraf, Glances, and Netdata

**The strongest case for buying, at full strength.** go-hass-agent v14.15.1 is packaged in nixpkgs proper, current with upstream, building for all 24 Linux platforms, maintained at roughly monthly cadence with signed releases — v14.15.1 fixed a concurrent map-read data race in the CPU usage worker, the intermittent-defect class a fleet fears, and v14.15.0 added NVIDIA/AMD GPU memory sensors [[changelogmd]]. Its sensor coverage is roughly 3-4× this repo's generic backend; lnxlink's ~50 modules extend the tail further [[lnxlink]]. Against 3,909 commits of maturity stands an 11-commit, 12-crate workspace with 8 tests that never run and three backends the README flags as unverified. On any generic fleet, buy.

**Why that case loses here — the boundary is the feature.** The features that decide jupiterOS's value are not sensors. They are the launcher mutual-exclusion session select (dashboard ↔ arcade on one tty, an HA `select` whose grouped profiles yield exactly one entity — regression-tested in this repo), the backlight-as-dimmable-light profile fused to `tcxwave-screen-power.service`, and the ZFS/headscale/syncthing backends mapping one-to-one onto europa and callisto. The audited record shows the incumbents cannot express these: a full-text pass over go-hass-agent's entire changelog returns zero occurrences of select entities, control state synchronisation, or NixOS support — the only "sync" entries are the Go sync package and sensor-state bookkeeping [[changelogmd]]; its user documentation hit the missing-select wall in January 2026, when a PipeWire output-device selector "can't be expressed" because the commands vocabulary has no dropdown; and the state-sync admission is architectural — a control model that cannot reflect out-of-band changes cannot back a mutual-exclusion group, whose whole point is that the compositor's real session state, not HA's last command, is the truth [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. Neither incumbent has a NixOS service module: nixpkgs' services/home-automation directory hosts home-assistant, esphome, zigbee2mqtt, zwave-js, matter-server, govee2mqtt, evcc, ebusd, and homebridge — neither Linux-agent incumbent appears anywhere in module-list.nix, while lnxlink lacks even a package [[module-listnix]]. Adopting would mean inheriting the split-brain identity and then building the launcher/session layer as configuration glued around an agent that does not natively model it — a worse position than owning 12 small crates whose worst defects are already audited to the line.

**And the monitoring-class incumbents fail the fleet's integration needs too — which is why "buy for the servers" also loses.** Glances, the canonical HA answer for host metrics, is wrong on the record: a local-polling REST integration scraping a Glances web server (port 61208, Glances ≥ 2.3, API v3), maintained by a single integration owner, used by 1.3% of active HA installations, with a history of connection loss that does not automatically recover, sensors that stop reporting current data, and sensor renames after restarts — years of exactly the reliability class this report exists to eliminate. Telegraf is a superb metrics pipeline and a poor HA citizen: its MQTT output publishes measurement formats for a metrics consumer, not HA discovery payloads, so the glue lives in a hub add-on (telegraf2hassio subscribes to `telegraf/#` and re-publishes as discoverable sensors — discovery logic on the far side of a translation shim). Netdata is the strongest monitoring product and the worst fit per hardware class: official documentation prices the default agent at 100-200 MB RAM (250-350 MB in production, ~4 GiB disk, 1-5% of a core), while community deployments report 200-1000+ MB and the maintainer-endorsed production recipe disables most of the product (alloc mode, ML off, health off) to squeeze under 50 MB — both sides right in scope: official numbers describe an empty system, community numbers metric-heavy reality, so for TCx Wave-class kiosks and a seven-host fleet the *effective* Netdata is the stripped one, at which point a purpose-built agent is the lighter choice [[interim-report-adopt-vs-build-honest-verdict]]. Even node_exporter is Prometheus-pull-oriented: HA's Prometheus integration exposes HA entity metrics to an external scraper; it does not ingest host metrics into entities.

**The MQTT-hop objection, answered by boundary condition.** The one principled anti-MQTT position, at full strength: a long-time HA contributor asks "Could you clarify your reasoning behind going through MQTT for influxdb injection? Seems an unnecessary point of failure to me. I go directly from telegraf to influxdb, then use the influxdb integration inside HA" — coherent for a DB-centred pipeline. It fails for this fleet on scope: jupiterOS runs no InfluxDB, and its needs (automations, dashboards, kiosk session control, offline detection) are exactly the bidirectional case MQTT natively provides — halinuxcompanion's to-do is the ecosystem's own testimony that native APIs cannot reflect a host going offline while an MQTT last-will can [[github-muniterhalinuxcompanion-homeassistant-linux-companion-github]]. If the fleet later wants long-horizon metric history, Telegraf→DB alongside the agent is the complement, not a replacement.

The committed position: improve on both sides of the boundary — not because the incumbents are bad products, but because the boundary features (select-with-state-sync control plane, single-device identity, server backends, NixOS module) are inexpressible in the companion incumbents, while the HA-integration shape (discovery entities, availability, round-trips) is inexpressible in the monitoring incumbents. The concession table stays on the record: ~25% of go-hass-agent's sensor coverage, 8 tests against 3,909 commits, three unverified-live backends, a notify payload-hack — every one addressed by the roadmap, none missed by the fleet's actual automations.

## 5. NixOS Fleet Architecture: From Kiosk-Only to Every Host in jupiterOS

This is where the 2026 evidence redrew the map: **the user-vs-system boundary moved this year, and the fleet's current design sits on the wrong side of it.**

**The old argument is stale; the new fact is worse.** The 2023 Discourse position — user units "don't start/restart on nixos-rebuild switch like system ones do. You need to relog" — was the classic reason to prefer system services [[what-is-the-difference-between-systemdservices-and-systemduserservices-help-nixo]], and an October 2025 thread kept it current [[interim-report-fleet-service-model-by-host-class]]. Citing either today understates the problem. PR #517768, merged into nixpkgs staging in May 2026, hardened switch-to-configuration-ng's user-unit migration pass — making `nixos-rebuild switch` restart user units other than `nixos-activation.service` for any user with an active manager [[switch-to-configuration-ng-harden-user-unit-migration-second-pass-by-r-vdp-pull]]. The stc-ng source confirms the mechanics: the parent enumerates users via `logind.list_users()`, stats `/run/user/{uid}` as an atomic liveness check (exists iff the user manager is active, lingered included), and for each live manager spawns a setuid child running `do_user_switch` — a daemon-reload plus stop/reload/restart passes with literal `restart_unit` calls over `/etc/systemd/user` [[mainrs]]. For an appliance fleet this restarts the agent's unit — and the surrounding user slice — on every configuration change, with two failure modes documented in production. First, the migration-candidate broadening (commits 6ced06a1b, 76c8d4509) restarts session-coupled units: since 2026-05-26 (nixpkgs 26.05.20260515.d233902 → 26.05.20260523.64c08a7, systemd constant at 260.1), users have been kicked out to GDM mid-switch as user-manager restarts collapse `graphical-session.target` — a one-way teardown, since the target declares `RefuseManualStart=yes` and nothing consults that on the restart path; one reporter hit 7 occurrences in 57 switches, session units stopping 150-730 ms after the daemon-reload and never returning [[anyone-seeing-nixos-rebuild-switch-kick-you-out-to-gdm-andor-log-gpf-errors-spec]]. Second, when the session death takes the launching terminal with it, stc-ng loses its stdout pipe and exits 101 — leaving a half-applied generation; on one documented occurrence docker, home-assistant, and NetworkManager were stopped and never came back [[anyone-seeing-nixos-rebuild-switch-kick-you-out-to-gdm-andor-log-gpf-errors-spec]]. For a fleet that includes the box running Home Assistant itself, that detail is disqualifying. Inference per the deep-inference licence: no source says jupiterOS kiosks will hit the GDM teardown — they do not run GNOME sessions — but the stc-ng source (restart_unit over /etc/systemd/user units for every live manager) and jupiterOS's deployment model (remote `nixos-rebuild switch` against lingered kiosks) jointly imply every agent config change now restarts the agent's user unit mid-flight, at minimum. The user-unit shape is retired because 2026 switch semantics make it an appliance-fleet hazard.

**The system-service shape, and the boundary facts that permit it.** One `systemd.services.ha-linux-agent` per host with `serviceConfig.User = "io"`, `Restart = on-failure`, `After=network-online.target`, and a `role` option (`kiosk | server | minimal`) mkIf-switching the host-class bits. The two facts that were supposed to force a user/system split both dissolved under audit. The session-bus argument dissolved because a `User=io` system service reaches the per-user bus at `/run/user/1000/bus` with two `Environment=` lines — the bus is per-(user, machine), its socket UID-gated by filesystem mode alone [[d-bus]]; jupiterOS itself proves the pattern via `mkSessionLauncher`, which exports `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS` in root-started units to reach cage/gamescope sessions [[interim-report-fleet-service-model-by-host-class]]. The lifecycle argument inverted (above). The remaining user-manager mechanics are reasons the agent must not *depend* on a user manager, which a system service does not: user units cannot order against system units, and headless boxes without a session bus produce the "Failed to connect to bus: No medium found" ladder the openclaw issue documents on EC2 [[systemduser-archwiki]] [[openclaw-gateway-status-fails-on-ec2headless-servers-due-to-missing-user-level-s]]. Declarative linger (NixOS 23.11, closing a nine-year gap) stays useful — for the cage sessions, not the agent [[nixosusers-groups-add-user-option-to-enable-lingering-by-toxicfrog-pull-request]]; `dbus-user-session` wires the bus socket the Environment block points at [[set-up-systemd-services-with-session-dbus-on-headless-linux-baeldung-on-linux]]. And the agent's only session-bus consumer today is dead code anyway (no notification daemon ships anywhere), while its live D-Bus sensors (login1, UPower) use the system bus, which any user may reach [[interim-report-fleet-service-model-by-host-class]].

**The fleet's actual coverage — the honest 4/6.** "Every host in jupiterOS" is the user's ambition; the fleet's configuration currently contradicts it. The agent ships on the four TCx Wave kiosks (amalthea, adrastea, metis, thebe). Callisto — the MQTT broker, postgres, headscale-target, syncthing-hub host — deliberately opts out (its arcade-console module strips the "cage + polkit + ha-agent wiring for a dashboard this host doesn't have"). Europa — the ZFS NAS, iscsi target, syncthing and headscale server — opts out despite backend-zfs, backend-syncthing, and backend-headscale existing for exactly that host. The gap the user is asking to close is precisely callisto and europa: the two hosts whose backends exist but whose wiring does not.

The committed position: one system service, `User=io`, role-parametrised, on every common.nix host (the kiosks, callisto, europa), the user unit deleted rather than deprecated; double-registration handled by making the shapes mutually exclusive via the role option's mkIf; no out-of-fleet hosts. The unit needs no capabilities anywhere by default — the matrix that replaces the chmod hack is the next section's subject.

## 6. JupiterOS-Specific Feature Gaps

The feature gaps are where the zero-capability, event-driven privilege matrix lives — the report's second load-bearing boundary result: every subsystem the fleet needs has an unprivileged, push-shaped channel, so the agent's privilege surface can be empty by default.

**SMART (europa's disks): consume smartd, don't become it.** The kernel capability matrix is settled by source: `NVME_IOCTL_ADMIN_CMD` requires CAP_SYS_ADMIN (checked in `nvme_user_cmd` in drivers/nvme/host/pci.c), CAP_SYS_RAWIO suffices for SATA/SCSI only, and the Scrutiny maintainer's confirmation is blunt — "there is nothing you can do except grant that" [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]]. But europa already runs smartd as a privileged daemon (`jupiter.storage.smartMonitoring.enable`, 1800-second interval, scheduled self-tests), and smartd has a documented event channel: `-M exec PATH` runs a script on detection events with the full SMARTD_* context exported (`SMARTD_DEVICE`, `SMARTD_FAILTYPE`, `SMARTD_MESSAGE`), plus the `/etc/smartmontools/smartd_warning.d/` plugin convention and `-n standby,15,q` power-mode protection so polling does not spin up the WD 18TBs [[smart-archwiki]] [[smartdconf5-smartmontools-debian-testing-debian-manpages]]. Design: smartd (root) detects, a root-owned hook writes a line into a world-readable spool (or publishes directly to the agent's MQTT user), the agent consumes — zero capabilities gained, smartd's scheduling and self-test logic inherited for free. The smartctl_exporter shape (root, privileged, 60-second polls) becomes a per-host opt-in for a future local-NVMe host. One caveat the man page supplies: "smartd will block until the executable PATH returns, so if your executable hangs, then smartd will also hang" — the hook must be fire-and-forget [[smartdconf5-smartmontools-debian-testing-debian-manpages]].

**ZFS (europa only, and that boundary is a finding): pool state via procfs, transitions via a zed bridge.** The audited absence first: there is no documented unprivileged `zpool`//dev/zfs read path on Linux — every zpool command in the ArchWiki ZFS material runs at a root prompt, and zed(8) states plainly "The ZED requires root privileges", with ZEDLETs required to be root-owned, executable-but-not-group-writable [[zed8in]]. But node_exporter's ZFS collector reads pool state from `/proc/spl/kstat/zfs/<pool>/state` — plain procfs opens, no ioctl, no privilege, NixOS defaults leaving the tree world-readable — precisely the channel a rewritten backend-zfs should use, replacing its `zpool list` shell-outs and their avoidable root requirement [[interim-report-headless-privilege-ladder]]. For push: ZED is the event channel — zevents arrive in zedlets as `ZEVENT_`-prefixed environment variables, prefix-matched by filename — and NixOS already ships the surface: `services.zfs.zed.settings` renders into `/etc/zfs/zed.d/zed.rc`, stock zedlets install via `environment.etc`, and `zfs-zed.service` ships inside the zfs package wanted by zfs.target whenever ZFS is enabled — jupiterOS needs no new unit, only a custom zedlet handing transitions to the agent (the same spool/MQTT trick as smartd) [[zfsnix]]. Thresholds from the monitoring literature: capacity warn 80-85%/critical 90%, fragmentation 30%/50%, ARC hit ratio under 80% as a problem indicator, any non-ONLINE state as a binary_sensor problem [[how-to-monitor-zfs-pool-health-and-status-on-ubuntu]]. The scoping premise: callisto's only ZFS exposure is the iSCSI zvol with no local pool — the design is europa-only [[interim-report-headless-privilege-ladder]].

**systemd unit health (callisto, europa, the kiosks): D-Bus match rules, live-proven unprivileged.** The live experiment on callisto settled what the docs only imply: `busctl --system monitor` (BecomeMonitor, the eavesdropping API) is polkit-denied for io — but normal match-rule subscription works unprivileged. `Subscribe()` on the systemd Manager succeeded as io, and a `JobRemoved` signal for logrotate.service (fired by the nightly timer) was delivered to the unprivileged subscriber within seconds — 27 PropertiesChanged signals in the same window — while unprivileged job *creation* remains correctly polkit-gated, with jupiterOS's own `polkitUnitRule` in modules/lib.nix:194 the shipped mechanism for the launcher backend's start/stop permissions [[interim-report-headless-privilege-ladder]]. The subtlety worth encoding: Manager signals like JobRemoved are not emitted until the client calls `Subscribe()` — a plain method call, not polkit-gated — so the backend must Subscribe() at startup; PropertiesChanged needs no such call. The pattern has an old production precedent — systemd_mon has subscribed to D-Bus unit notifications with "no polling, and no busy-loops" since the v204 era, queuing intermediate transitions to notify once with full history [[github-joontysystemd_mon-monitor-for-systemd-to-alert-failed-services-github]] — and the rejected alternative is the `OnFailure=` global drop-in (`failure-handler@%N.service` template), systemd-native but requiring root-owned writes into /etc [[see-also-3]]. Design: a backend-systemd (or an extension of backend-generic, already zbus-on-system-bus) mapping watched-unit transitions to HA binary_sensors — mqtt, postgres, syncthing, headscale, the iscsi target, the kiosk power services — the list generated from the same jupiterOS config that defines the launcher profiles.

**Backlight (the kiosks): fix the DAC, take the free push channel.** The kernel source is unusually generous: `brightness_store()` unconditionally generates a `KOBJ_CHANGE` uevent with `SOURCE=sysfs|hotkey|unknown` and a `sysfs_notify` on `actual_brightness` after every store attempt — and the hotkey path feeds the same generator, so platform-initiated changes are signalled identically [[interim-report-headless-privilege-ladder]]. The kiosks' 1-second poll-everything default can therefore become push: listen on the uevent socket (confirmed unprivileged on callisto) or POLLPRI on `actual_brightness`, dropping to event-driven plus a slow heartbeat. The write-side fix is one udev rule and one group membership: `GROUP="video"` on `SUBSYSTEM=="backlight"` nodes plus `io` in `video` — the same pattern the fleet already uses for the customer-display hidraw nodes — replacing the broken chmod oneshot with ordinary discretionary access control [[interim-report-fleet-service-model-by-host-class]]. logind's Session.SetBrightness exists but is Session-scoped with no manager-level path and no named polkit action — a desktop nicety, not a fleet channel.

**The notification fork, resolved — and the last mile is not a notification daemon.** The HA→agent notification leg now has a first-class MQTT path: "notify" sits in the mqtt integration's `SUPPORTED_COMPONENTS` alongside "select" — both load-bearing — the platform landed via PR #115653 in HA 2024.5 (Quality Scale gold), and the upstream test suite publishes a working discovery payload barely two fields long: `{"name": "test", "command_topic": "test_topic"}`, the notify service call arriving on the command topic verbatim ("Beer message") or shaped by an optional `command_template` [[test_notifypy]]. This replaces the current raw button whose payload becomes the body. The other-side boundary: the platform is one-way — no actions schema, no event round-trip — and notify entities still cannot drive HA's alert integration natively [[notification-entities-and-alert-integration-configuration-home-assistant-communi]]. But the audited fleet fact dissolves most of that residual: no notification daemon (mako/dunst/swaync) ships on any jupiterOS host, so the session-bus last mile is dead code everywhere today; the kiosks' real last mile is the customer-display VFD overlay — and a notify.mqtt entity writing to the VFD is strictly simpler than any session-bus path. Actionable notifications have no Linux implementation anywhere: go-hass-agent's requests #667 (actionable buttons) and #926 (clear_notification) are open with zero maintainer engagement [[interim-report-adopt-vs-build-honest-verdict]]. MQTT-only loses almost nothing, and what it loses is recoverable in-pattern: expose notification actions as buttons/selects on the device, automations listening on those command topics.

**The future-desktop boundary: same-UID sockets cover it.** backend-niri is speculative today — niri appears in zero jupiterOS host configs — but its boundary condition is solved from source: the compositor's IPC socket is created as `niri.{wayland_socket_name}.{pid}.sock` under the user's runtime directory, so a same-UID `User=io` system service reaches it by globbing the runtime dir, no session unit required; and the event-stream contract ("complete current state up-front, then follow up with updates… your state can never 'desync'") is the same push-state model the backlight and D-Bus rows adopt [[serverrs]] [[ipc-niri-msg-niri]]. The system-service design covers a future desktop host class without a shape change.

The committed position: the feature gap list and the privilege matrix are the same document — every gap closes through a channel either unprivileged by design (procfs, system-bus match rules, same-UID sockets, group-gated sysfs) or pushed from a privileged incumbent the host already runs (smartd, zed) — and the unit needs no AmbientCapabilities, no sudo, and no root anywhere in the fleet, the one opt-in exception being a future local-NVMe host wanting agent-side SMART polling (CAP_SYS_ADMIN there, per the kernel matrix [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]]).

## 7. Testing a Hardware-Touching Daemon

The testing answer is fleet-specific, and the web's consensus gets it wrong for this deployment; getting the harness right is what makes both the reliability fixes and the fleet rollout safely shippable. The 7-step ladder is the definition of done.

**Step 0 — the ground truth that shapes everything else.** The recount first: 8 tests, not 3 (3 in `discovery.rs`, 5 in `backend-launcher` on grouped-profile semantics, all pure `#[test]`s written as named regression guards), zero of which run in any gate because the flake's checks contain no `craneLib.cargoTest`; clippy is red at `backend-hardware/src/lib.rs:117`, so `nix flake check` fails before testing anything; and there is no CI beyond the flake [[interim-report-testing-gate-for-hardware-daemon]]. Then the harness decision the corpus consensus gets wrong: testcontainers is the documented default — `Mosquitto::default().start()`, broker URL from the mapped port, "Starts a MQTT broker without authentication" [[testcontainers-mosquitto-module]] [[mosquitto-in-testcontainers_modulesmosquitto-rust]] — and dead on arrival here: no container runtime exists on any jupiterOS host or Nix remote builder (audited across /etc/nix/machines and host configs), and `nix flake check` builds on those remote builders where a Docker socket cannot exist anyway [[interim-report-testing-gate-for-hardware-daemon]]. The principle recurs throughout: web consensus optimises the generic case; fleet ground truth overrides it. The subprocess harness borrows testcontainers' hard-won lessons — URL always derived from the harness; readiness probed before assertions; per-test exclusive broker — from the mosquitto binary the devShell already ships: bind a `TcpListener` to `127.0.0.1:0`, read the port, drop it, hand the port to `mosquitto -p <port>` (no-config default: anonymous, local-only), TCP-probe with a `try_wait()` fail-fast, kill on Drop.

**The sandbox-legality proof, from the Nix source itself.** Can a build-sandbox derivation even open a TCP socket pair? The Nix source answers at the syscall level: `runChild()` performs `ioctl(SIOCSIFFLAGS)` on `lo` with `IFF_UP | IFF_LOOPBACK | IFF_RUNNING` — throwing "cannot set loopback interface flags" on failure — inside a network namespace cloned with `CLONE_NEWNET` for every non-fixed-output derivation, and the design comment states the builder "only has a private loopback interface" by intent, with `/etc/hosts` written as `127.0.0.1 localhost` [[local-derivation-goalcc]]. In-sandbox client-server pairs are upstream-blessed by construction, and the subprocess harness inside `craneLib.cargoTest` — mosquitto in `nativeBuildInputs`, attributes passing straight through crane — needs no `__noChroot` escape, no VM. This is the boundary-conditions method applied to tooling itself: not "is the subprocess harness generally better than testcontainers" (it is not, on Docker-equipped CI) but "which harness is valid inside this fleet's actual build environment".

**The regression tests, named per defect.** Five integration tests in `crates/core/tests/`, each against the ephemeral broker with a second rumqttc client as observer (same stack as production, not a mock): `broker_restart_resubscribes_and_reasserts_availability` (kill -9 the broker, restart on the same port, publish a command via the observer, assert the agent handles it — proving the ConnAck re-subscribe `agent.rs:190` currently swallows — then assert a fresh retained "online"); `birth_message_triggers_discovery_republish` (jitter injectable to 0); `sigterm_publishes_offline_then_disconnects`; `hung_backend_doesnt_starve_sensors` (one backend whose poll never returns plus one healthy one; assert the healthy one still publishes within the interval); and `decommission_zero_payload`. Every await wrapped in `tokio::time::timeout` — a reliability gate that can hang is not a gate. These require the `Agent::run()` seam extraction first (shutdown channel, jitter bound, config-driven interval) — the same refactor the supervisor spec requires, so ladder and reliability phase are one work item [[interim-report-testing-gate-for-hardware-daemon]].

**The D-Bus layers, split by what each can prove.** A private `dbus-daemon` per test binary (`--session --print-address` into a tempdir, `DBUS_SESSION_BUS_ADDRESS` pointed at the printed address) exercises the agent's zbus plumbing using the `pkgs.dbus` buildInput the flake already carries; the honest limit is that a private bus hosts no `org.freedesktop.systemd1`, so unit-health assertions cannot live there. The real gate is the NixOS test: `pkgs.testers.runNixOSTest` is the out-of-tree invocation the manual documents ("Outside the nixpkgs repository, you can use the runNixOSTest function from pkgs.testers… runNixOSTest returns a derivation that runs the test") [[nixos-manual]], headless in QEMU where a full system bus and real systemd exist, cribbed from nixpkgs' own mosquitto test — a single node with broker and agent (the kiosk failure mode is local), `wait_for_unit`, then `machine.systemctl("restart mosquitto.service")` mid-test to assert re-subscribe and availability return. VMs, not containers, because the unit's hardening and sysfs paths must be real. The `$SYS` check belongs in the same assertions: read `$SYS/broker/publish/messages/dropped` and require zero [[mosquitto8-mosquitto-debian-unstable-debian-manpages]].

The committed position: the ladder's order is the dependency order — (1) clippy fix so the gate can gate; (2) `craneLib.cargoTest` wiring the existing 8 tests (the single cheapest reliability win: real tests, zero new code, in the gate); (3) sysfs-root injection plus tempfile fixtures (synthetic `/sys` trees — canonical, since std::fs is a module, not a mockable trait); (4) the `Agent::run` seam; (5) the mosquitto-subprocess harness and the five defect-named tests; (6) the private dbus-daemon layer; (7) the runNixOSTest gate, which also pins the section-5 unit shape in one stroke. Steps 1 and 2 are minutes of work; the reliability phase inherits its definition of done at step 2.

## 8. Ordered Improvement Roadmap

The order follows the boundary analysis: lifecycle core first (nothing else is observable while the agent is deaf), service shape second (the 2026 stc-ng behaviour makes this operational, not aesthetic), features third (each already carrying its privilege design), and the test ladder threaded through rather than bolted on at the end.

**Phase 0 — make the gate exist (a day).** Fix the clippy `map_or`→`is_some_and` at `backend-hardware:117` so `nix flake check` can go green; add `craneLib.cargoTest` with cargoArtifacts from the existing buildDepsOnly, wiring the 8 existing tests into the gate. Exit criteria: `nix flake check` green, tests visible in the output. No behaviour change ships.

**Phase 1 — the reliability core (the ConnAck supervisor, one to two weeks).** Implement section 2's spec: ConnAck-driven re-subscribe and availability re-assert, birth-subscription with 0-30 s jitter (`homeassistant/status` is ACL-legal on callisto — the ACL already grants readwrite on `homeassistant/#`), cap-0 rendezvous publishes under per-tick timeout, SIGTERM offline-then-disconnect plus `Restart=on-failure`, per-backend/per-command task isolation with 5-second reqwest timeouts, exponential backoff 1→60 s with ±20% jitter so a broker restart does not synchronise the fleet. Broker pairing on callisto: `persistence true` + queue headroom (at ~25 entities per host the default 1000 does not bind — hygiene plus the `$SYS` check, not urgent 8192 sizing) [[interim-report-mqtt-lifecycle-supervisor-spec]]. A `--decommission` subcommand publishing zero-length payloads, state/availability first and configs last. Exit criteria: the five defect-named regression tests pass against a killed-and-restarted broker; the kiosks' entities stay available across a `systemctl restart mosquitto` on callisto; the live presenting symptom is gone.

**Phase 2 — the fleet service model (one week, mostly Nix).** Rewrite the flake's `nixosModules.default` to ship `systemd.services.ha-linux-agent` with `User=io`, `Restart=on-failure`, `After=network-online.target`, and a `role` option (`kiosk | server | minimal`) mkIf-switching host-class bits: the `Environment=` session-bus block only on lingering hosts; the udev `GROUP="video"` backlight rule plus `io` in `video` on kiosks; per-backend enabling for servers (zfs on europa only; syncthing, headscale, and the systemd D-Bus backend on europa and callisto). Delete the `systemd.user.services` shape and the broken `ha-linux-agent-sysfs-perms` oneshot; fix the false comment at `ha-agent.nix:112`; keep `sops.secrets.mqtt_ha_linux_agent.owner = "io"` unchanged (the sops path works identically for a system service). Wire callisto and europa — closing the 4/6→6/7 gap. [[interim-report-fleet-service-model-by-host-class]]. Exit criteria: `nixos-rebuild switch` restarts the agent on every host every time (the property the current fleet lacks); brightness writes succeed on a kiosk with no chmod oneshot; the runNixOSTest pins the unit shape in both roles.

**Phase 3 — features, each with its privilege design settled (two to three weeks, severable).** The notify.mqtt discovery entity replacing the payload-hack button (the upstream test suite is the schema [[test_notifypy]]), the kiosk last mile driving the customer-display VFD; the smartd `-M exec` hook on europa feeding a SMART binary_sensor; backend-zfs rewritten onto `/proc/spl/kstat/zfs/<pool>/state` plus the zedlet bridge via `services.zfs.zed.settings` — europa only; the backend-systemd D-Bus unit-health sensors with the watched-unit list generated from the jupiterOS module inventory; the backlight read side onto KOBJ_CHANGE/POLLPRI push, retiring the 1-second default. Optional per-host opt-in: agent-side SMART polling with CAP_SYS_ADMIN on a future local-NVMe host. Exit criteria: each feature carries at least one ladder-level test; none adds a capability, a sudo, or a root-owned write.

**Phase 4 — close the ladder (parallel with Phase 3).** The runNixOSTest gate cribbed from nixpkgs' mosquitto test, including the mid-test broker restart; the private dbus-daemon plumbing harness; a KVM availability check on the remote builders (`ls -l /dev/kvm`) to decide whether the VM gate is per-check or nightly.

**Forward-looking.** Six to twelve months out, three developments would change the boundary conditions. If go-hass-agent or lnxlink lands a NixOS service module or select-with-state-sync controls upstream (zero movement through v14.15.1 [[changelogmd]]), the build-vs-buy arithmetic for *generic* hosts reopens — though not for the launcher layer, inexpressible in a commands-file vocabulary. If MQTT v5 is adopted end-to-end, rumqttc's internal v5 module becomes the path, message expiry bounds the stale-command hazard, and the clean-session reasoning loosens — the upgrade measured painless [[interim-report-rumqttc-dependency-fitness]]. And if jupiterOS gains a desktop host class (niri/himaya), the same-UID socket reachability proven from source means the system-service shape covers it without a redesign [[serverrs]] — the boundary machinery, not the host list, is what makes "every host" a stable promise.

## Source Tensions: Six Disagreements, Each True in Its Place

**1. MQTT hop vs direct database injection.** The HA contributor's objection — going through MQTT for metrics injection is "an unnecessary point of failure; I go directly from telegraf to influxdb" — is correct for a DB-centred pipeline with long-horizon metric history as the goal. It fails for this fleet on scope: jupiterOS runs no InfluxDB, and its needs are bidirectional (kiosk session control, automations, offline detection) — exactly where MQTT's discovery contract and last-will semantics are load-bearing, as the native-API agent's own to-do ("Move sensors to MQTT… it can set will topics") concedes [[github-muniterhalinuxcompanion-homeassistant-linux-companion-github]]. Direct-to-DB wins the day jupiterOS wants a metrics archive — add Telegraf→DB alongside, not instead.

**2. go-hass-agent's MQTT v5 requirement vs the fleet's broker surface.** The incumbent requires v5-capable brokers and keeps control states unsynced; the fleet's mosquitto on callisto is version-current (v5 available) and this agent's rumqttc 0.24.0 path speaks v3.1.1 with a v5 module one import-switch away [[interim-report-rumqttc-dependency-fitness]]. The state-sync admission is the load-bearing half: kiosk session switching requires switches that reflect real unit state, which go-hass-agent's own documentation disclaims. The v5 requirement is satisfiable by upgrading the broker; the unsynced-control admission is architectural and does not move — which is why this tension feeds the improve-don't-adopt verdict rather than standing as a broker-version question.

**3. Netdata's marketed footprint vs community-documented blowups.** Both sides are right in scope: official figures describe a default agent on an empty system; community deployments and the maintainer's own optimisation guide describe metric-heavy reality where the effective configuration is the stripped one. The resolution is hardware-class-conditional: for TCx Wave kiosks and a seven-host fleet, the effective Netdata is the 50 MB recipe, at which point the purpose-built agent is the lighter choice. On big always-on servers with capacity to spare, Netdata's depth wins; jupiterOS's server hosts are not that class today.

**4. In-process SMART polling vs smartd's privileged event hooks.** The exporter pattern (root, privileged, 60-second smartctl polls — the smartctl_exporter and Scrutiny shape) buys in-process freshness at the price of a CAP_SYS_ADMIN surface on every server host; the hook pattern buys zero new privilege by riding the privileged daemon europa already runs. Sub-minute SMART freshness would flip this row to the exporter shape — but SMART health is a slow-moving signal where minute-level freshness has no consumer in this fleet, and the kernel-source capability matrix makes polling's privilege cost explicit and permanent [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]]. Hooks win at this fleet's granularity.

**5. Testcontainers consensus vs containerless fleet ground truth.** The four-source consensus for Mosquitto-in-testcontainers is correct for Docker-equipped CI and wrong for a fleet whose hosts and Nix remote builders have no container runtime — a gate that cannot run is not a gate. The day this project gains hosted CI with Docker, the spawn-guard swaps for `Mosquitto::default().start()` and the test bodies survive unchanged — deliberately harness-agnostic below the spawn primitive. The principle generalises across this report: web consensus optimises the generic case; audited fleet ground truth overrides it.

**6. Retained-everything discipline vs selective retention with expiry.** The rare fully-resolved tension, and conjunctive: retain everything except command topics (the Z2M/ESPHome posture), AND republish on birth/ConnAck with jitter (HA's mandate, because broker queue limits silently drop retained replay at scale — the #135266 mechanism), AND size and persist the broker. Retention alone fails at HA-restart replay scale; republish alone fails the first cold broker start (nothing to replay). The section-2 contract is this synthesis, not a choice between its halves.

## Opinionated Synthesis

The thesis, committed: **improve ha-linux-agent, run it as one system service on every host that will take it, and let the boundary — the feature, not the host — decide every contested question.** Where jupiterOS-native control is load-bearing, improvement wins because the incumbents architecturally cannot follow: zero select/state-sync/NixOS occurrences across go-hass-agent's entire release history [[changelogmd]], a self-documented split-brain identity and unsynced controls [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]], no NixOS module for either incumbent [[module-listnix]]. Where plain monitoring would nominally suffice, the monitoring incumbents fail this fleet's integration needs on the record, so the agent's server backends are the right answer there too — the boundary delivers the same verdict on both sides. The machinery that makes it safe: the host-class service split (user units retired per the 2026 stc-ng restart semantics [[anyone-seeing-nixos-rebuild-switch-kick-you-out-to-gdm-andor-log-gpf-errors-spec]] [[mainrs]]), the zero-capability privilege matrix (smartd hooks, procfs-plus-zed, live-proven D-Bus match rules, udev video-group backlight [[interim-report-headless-privilege-ladder]]), the notification fork resolved onto notify.mqtt with the VFD as the real last mile [[test_notifypy]], and the 7-step testing ladder anchored by the sandbox-legal subprocess harness [[local-derivation-goalcc]]. Reliability first, fleet second, features third — with the flip conditions on record: an upstream NixOS module plus native select controls from an incumbent would reopen the generic-host arithmetic; an end-to-end MQTT v5 decision would loosen the clean-session reasoning; a desktop host class is already covered by the same-UID socket boundary. Until one of those fires, the evidence points one way, and the plan follows it.
