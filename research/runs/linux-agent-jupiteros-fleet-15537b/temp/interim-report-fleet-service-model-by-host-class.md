# Interim report: fleet-service-model-by-host-class

**Locus question:** How does ONE agent codebase and ONE NixOS module actually serve all 7 jupiterOS hosts — user-service-with-linger on kiosks/desktops vs system-service-with-capabilities on headless boxes — covering unit lifecycle (the nixos-rebuild user-unit restart gap), D-Bus access (`/run/user/<uid>/bus` reachability from a system service), privileges, and double-registration avoidance?
**Flavor:** dialectical
**Register:** advocate, deep inference

## What the corpus already said

The width sweep already established the mechanics of both positions. For **Position A (user service + linger)**: the Arch wiki [[systemduser-archwiki]] (user manager is per-user not per-session; `loginctl enable-linger` keeps it alive; user units cannot order after system units — flagged "disputed-section" but confirmed by the NixOS wiki); the NixOS wiki [[systemduser-services-official-nixos-wiki]] (NixOS `users.users.<name>.linger` + `ConditionUser` for per-user scoping); nixpkgs PR #260248 [[nixosusers-groups-add-user-option-to-enable-lingering-by-toxicfrog-pull-request]] (declarative linger landed Oct 2023, NixOS 23.11, closing a 9-year gap from issue #3702 [[enabling-persistent-user-instance-systemd-issue-3702-nixosnixpkgs-github]]); go-hass-agent [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] ("You cannot run Go Hass Agent with root privileges... The agent will refuse to run" + enable-linger guidance + SMART via file capabilities `cap_sys_rawio,cap_sys_admin,cap_mknod,cap_dac_override=+ep` applied by the packages). For **Position B (system service)**: tejing's Feb 2023 Discourse [[what-is-the-difference-between-systemdservices-and-systemduserservices-help-nixo]] ("They don't start/restart on nixos-rebuild switch like system ones do. You need to relog... or manually handle them"); the Dec 2024 beginner thread [[how-to-create-user-systemd-service-help-nixos-discourse]] (the full failure ladder: `systemctl --user` as root → "No medium found", `serviceConfig.User` in a user unit → 216/GROUP); the openclaw issue [[openclaw-gateway-status-fails-on-ec2headless-servers-due-to-missing-user-level-s]] (headless SSH breakage chain: no session bus → no XDG_RUNTIME_DIR → the fix is linger + explicit XDG_RUNTIME_DIR); Baeldung [[set-up-systemd-services-with-session-dbus-on-headless-linux-baeldung-on-linux]] (linger + `dbus-user-session` wires `/run/user/<uid>/bus`); and the SMART capability matrix [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]] (NVMe REQUIRES CAP_SYS_ADMIN — "if you read the source code for NVME_IOCTL_ADMIN_CMD it requires CAP_SYS_ADMIN, so there is nothing you can do except grant that"; SATA needs CAP_SYS_RAWIO) plus smartctl_exporter [[github-prometheus-communitysmartctl_exporter-export-smartctl-statistics-to-prome]] ("smartctl needs to be run as root... ATA_12 and ATA_16 are always blocked for non-root users"). The contradiction graph's own delta: "Side B has the stronger structural argument for SERVER hosts (ordering, lifecycle); side A has the stronger security/practical argument for DESKTOP hosts (session bus for notifications/niri). The evidence reconciles by host-class, not by winner" — but no source actually designed the split. That design work is this locus's contribution.

## What the new sources say

**systemd.exec(5)** [[systemdexec]] — the upstream authority on the execution options both positions hinge on. Load-bearing: `User=`/`Group=` are "only available for system services and are not supported for services running in per-user instances of the service manager. For user services of any other user, switching user identity is not permitted." And `AmbientCapabilities=` (v229+): "Ambient capability sets are useful if you want to execute a process as a non-privileged user but still want to give it some capabilities. Note that, in this case, option keep-caps is automatically added to SecureBits=." Also decisive for the design space: "this option [DynamicUser=] is currently incompatible with D-Bus policies, thus a service using this option may currently not allocate a D-Bus service name (note that this does not affect calling into other D-Bus services)" — calling INTO buses still works, only name allocation breaks — and DynamicUser implies ProtectSystem=strict/ProtectHome=read-only, which would block the agent's sysfs/probe surface.

**NixOS Discourse, Oct 2025, ElvishJerricco** [[restart-oneshot-systemd-service-on-every-rebuild-help-nixos-discourse]] — closes the locus's open question (c): the user-unit restart gap is STILL true on current NixOS, and worse than the 2023 thread stated. Verbatim: "I don't think we have an equivalent reactivation thing for user services, other than the user service nixos-activation.service, which just runs system.userActivationScripts... **Note that nixos-rebuild switch only restarts nixos-activation.service in the user level systemd manager for users that are currently logged in.**" And waffle8946: "Within systemd, any relations between services (or any units) must be among services under the same service manager... So you cannot have user services depend on system ones or vice versa, by design." So under the current user-service deployment, a `nixos-rebuild switch` that changes the agent's ExecStart or config takes effect on headless kiosks only at the next reboot — the user manager of a lingered-but-not-logged-in user never sees the new unit. (Discourse topic 70853, fetched fresh for this locus.)

**dbus-daemon(1)** [[dbus-daemon]] — the per-user bus address semantics: the session service directory is `$XDG_RUNTIME_DIR/dbus-1/services`, the recommended topology is "a separate session bus per (user, machine) pair", and "the well-known session bus normally allows sending any message... any connection to request any well-known name" — i.e. any process that can reach the socket can use it; access control is the socket's filesystem mode (0700 root:root on the runtime dir), not D-Bus policy. This is what makes `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus` a complete, credential-free handshake for any process running as that UID.

**systemd.special(7)** [[systemdspecial]] — user-manager units hang off `default.target` inside `user.slice`; `graphical-session.target` is the passive target that tracks whether a graphical session is running. Confirms a user service cannot express "run after the network/system is up" in any ordered way.

**systemd.io UIDs/GIDs** [[users-groups-uids-and-gids-on-systemd-systems]] — system users belong in 1–999 (privilege-separated daemons), the DynamicUser= range 61184–65519 is explicitly not for regular users, and "the user database is used as synchronization mechanism" for dynamic allocations. For a fleet agent a static system user (or reuse of an existing login user) is the canonical shape.

**sops-nix** [[github-mic92sops-nix-atomic-secret-provisioning-for-nixos-based-on-sops-github]] — the system module decrypts to `/run/secrets` with per-secret `owner`/`group` ("sops.secrets.example-secret.owner = config.users.users.nobody.name") plus `restartUnits` to bounce consumers when a secret changes. This is the existing credential path in jupiter-os (ha-agent.nix:97: `sops.secrets.mqtt_ha_linux_agent.owner = "io"`), and it works IDENTICALLY for a system service — no home-manager indirection needed. The home-manager sops path (`$XDG_RUNTIME_DIR/secrets.d`, ordering after `sops-nix.service`) exists but is strictly more machinery for the same outcome.

## Ground truth from the two repos (audited directly, the highest-tier evidence)

**The deployed shape today is Position A, but a *weakened* hybrid.** `jupiter-os/modules/services/ha-agent.nix` ships: `systemd.user.services.ha-linux-agent` with `unitConfig.ConditionUser = "io"` (line 105), `users.users.io.linger = true` (line 102), `sops.secrets.mqtt_ha_linux_agent.owner = "io"` (line 97) — and **a root-owned SYSTEM oneshot** `ha-linux-agent-sysfs-perms` (lines 117–124) that `chmod 0664`s backlight and cpufreq nodes. So Position A as deployed already concedes system-level privilege for the hardware backend; the "no root anywhere" claim of pure Position A is not what jupiterOS runs.

**A live defect in that sysfs workaround (evidence for Position B).** The kernel's backlight class registers `DEVICE_ATTR_RW(brightness)` (drivers/video/backlight/backlight.c:224 in torvalds' tree) — sysfs attributes default `root:root 0644`. `chmod 0664` makes the node group-writable **by group root**. But io's complete group membership is `extraGroups = [ "wheel" ]` (jupiter-os/modules/common.nix:139) — no host in the fleet adds io to `video`, `root`, or `disk`. The module's own comment (ha-agent.nix:112: "io is in the groups that own the nodes (video for backlight...)") is **false** — the udev rules that set `GROUP="video"` (modules/services/tcxwave-power-tuning.nix:178–179) apply only to the TCxWave customer-display hidraw/usb nodes, not backlight/cpufreq sysfs. And tcxwave-kiosk.nix:199 still claims "0666 permission". Net: the agent's brightness/governor/EPP **writes** should fail EACCES with only a `warn!` in `write_sys_file` (crates/backend-hardware/src/lib.rs:108–111) — the failure is silent at the HA layer. This is exactly the fragility AmbientCapabilities= exists to remove.

**What the agent actually needs, per backend (crates/):** the generic backend's login1/UPower sensors use the **system bus** (crates/backend-generic/src/lib.rs:32–40, `Connection::system()`); only notifications need the session bus, and it degrades gracefully to `warn!` + `None` (lib.rs:41–49: "no session bus, notifications disabled"). The KDE backend hard-fails without a session bus (`Connection::session().await?`, backend-kde/src/lib.rs:41) — but **no jupiterOS host runs Plasma** (greps for plasma/kde in hosts/ and modules/ return nothing). The niri backend shells out to `niri msg --json` needing `NIRI_SOCKET`/`WAYLAND_DISPLAY` in io's environment (backend-niri/src/lib.rs:47) — but **niri appears nowhere in jupiter-os except the ha-agent.nix comment** (line 100). The launcher backend runs `systemctl [--user] start/stop/is-active` (backend-launcher/src/lib.rs:162–175) — and every single `launcherApps` profile in the fleet uses `scope = "system"` (dashboard-gaming.nix:271,280; tcxwave-kiosk.nix:215,229), gated by polkit rules for **io** (`polkitUnitRule "io" "tcxwave-screen-power.service"`, tcxwave-touch-wake.nix:287; customer-display.nix:697; the session-select rule at dashboard-gaming.nix:239–256). The hardware backend reads `/sys/class/{backlight,hwmon,thermal}` and `/sys/devices/system/cpu/...` and writes governor/EPP/brightness. ZFS backend shells out to `zpool list` (backend-zfs/src/lib.rs:72) — needs `zpool` on PATH, works unprivileged for status reads.

**Host-class reality:** europa (ZFS NAS + smartd, common.nix io user exists) and callisto (arcade-console host, io user exists) have NO haAgent wiring (greps return nothing; arcade-console.nix deliberately strips "cage + polkit + ha-agent wiring" per its header line 22); So "every host in jupiterOS" means: 4 TCxWave kiosks + callisto (kiosk-class with arcade session) + europa (server-class) = 5 import-common.nix hosts.

## Evidence synthesis

The corpus and ground truth agree on all the mechanics; what they jointly determine is that the "one service model for all hosts" framing is the wrong axis. The genuinely required axis is **what the agent must touch on each host class**, and that partitions cleanly:

**D-Bus reachability (open question b — resolved YES).** A system service with `User=io` CAN reach the user bus at `/run/user/1000/bus` under linger: dbus-daemon's session bus is per-(user,machine) [[dbus-daemon]], the socket lives in the user's runtime dir (mode 0700 io:io), and **access control is purely the filesystem mode** — any process with UID 1000 can connect; no credentials, no polkit. jupiter-os itself already proves the pattern works from the *system* side: `mkSessionLauncher` (modules/lib.nix:60–67) exports `XDG_RUNTIME_DIR="/run/user/$(id -u kiosk)"` and `DBUS_SESSION_BUS_ADDRESS="unix:path=$XDG_RUNTIME_DIR/bus"` in a root-started system unit to reach the session user's bus for the cage/gamescope sessions. The same two lines in an `Environment=` block give a system `ha-linux-agent.service` with `User=io` the same bus. The zbus side needs no code change: `Connection::session()` reads `DBUS_SESSION_BUS_ADDRESS` (zbus docs.rs [[zbus-rust]]: "DBUS_SESSION_BUS_ADDRESS environment variable must be set"), and the agent's generic backend already falls back to warn+disable when the bus is absent — which is the correct behaviour on europa where no io session ever exists. The openclaw "No medium found" maze [[openclaw-gateway-status-fails-on-ec2headless-servers-due-to-missing-user-level-s]] is the failure of *interactive tooling* connecting to `--user` buses, not of a service that is handed the address explicitly.

**Unit lifecycle (open question c — gap CONFIRMED, current as of Oct 2025).** ElvishJerricco's statement is unambiguous and recent: user services only get reactivated for **currently-logged-in** users [[restart-oneshot-systemd-service-on-every-rebuild-help-nixos-discourse]]. jupiterOS kiosks are erasure-tolerant appliances but they DO get `nixos-rebuild switch` deployed remotely (the fleet uses GitHub-driven builds per common.nix comments) — so today, every agent config change on a kiosk silently waits for the next reboot. The system-service model gets `restartIfChanged` semantics from the same `nixos-rebuild switch`. This is the single strongest operational argument for Position B and it was previously only supported by a Feb 2023 thread; it is now confirmed current.

**Privileges (open questions d and e).** Credentials: sops-nix system module + `owner`/`group` per secret works unchanged for a system service [[github-mic92sops-nix-atomic-secret-provisioning-for-nixos-based-on-sops-github]] — and ha-agent.nix already owns the mqtt secret as io. The dead `tls` knob (config.rs:88 parses `mqtt.tls`, `agent.rs` never calls `set_transport` — grep returns 0 hits) is orthogonal to the service model but is part of the same "server hosts need broker TLS" story; on a LAN with callisto's mosquitto it's deferrable. SMART: the capability matrix is settled (CAP_SYS_ADMIN for NVMe, CAP_SYS_RAWIO for SATA, both needed on europa's mixed MX500-SSD + 18TB WD SATA fleet [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]]); `AmbientCapabilities=` is exactly the designed mechanism for "unprivileged user + selected capabilities" [[systemdexec]] and is only meaningfully grantable on system units (in user instances it requires the PrivateUsers= userns dance). go-hass-agent — the strongest Position-A precedent — *itself* bridges to Position B for SMART: it refuses root AND requires file capabilities `cap_sys_rawio,cap_sys_admin,cap_mknod,cap_dac_override=+ep` on the binary, i.e. capabilities on an unprivileged process, which under NixOS packaging is `security.wrappers` or a system unit's AmbientCapabilities= — not something a pure user unit can self-grant. The launcher backend's `scope = "user"` code path is dead in the fleet (0 of N profiles use it); its `scope = "system"` path is polkit-gated for io today and would keep working identically under a system service running as io — the polkit rules key on `subject.user == "io"`, which a User=io system service satisfies.

**Double-registration avoidance.** The device identity is `device.id = config.networking.hostName` (ha-agent.nix settings) with discovery prefix `homeassistant` and per-device topics — one device per host regardless of service model. The real double-registration risk is shipping BOTH unit types (the module currently defines `systemd.user.services` in the flake [[repo-map-ha-linux-agent]] and jupiter-os adds `ConditionUser` + the sysfs oneshot); a host-class split must make the two shapes mutually exclusive per host (mkIf on a `role` option), not additive.

### Position A: user service + linger everywhere

Steelmanned: no root anywhere (go-hass-agent refuses root as a security posture; the agent's attack surface is a 12-crate Rust daemon talking MQTT — least privilege is real). The session bus comes free inside the user manager's environment, so notifications and session-scoped sensors (niri active window, KDE activities, logind session) work with zero wiring. jupiter-os ships it today (`ConditionUser=io`, `linger = true`), so it is proven on 4 kiosks, and NixOS's declarative linger (23.11+) closed the last declarative gap. User slices get resource accounting for free via user.slice.

But as deployed it is not actually Position A: it carries a root-owned chmod oneshot (system service!) whose comment mis-states io's groups, and whose chmod grants group-root write on nodes io can't write — so even the flagship kiosk deployment depends on system-level privilege, applied imprecisely. And the model's lifecycle cost is confirmed-current: config changes don't reach headless lingered users until reboot.

### Position B: system service (User=/AmbientCapabilities=) at least on servers

Steelmanned: restart-on-switch for every host; ordering after network-online.target and after mosquitto on callisto; AmbientCapabilities= grants exactly the SMART/sysfs set (CAP_SYS_ADMIN, CAP_SYS_RAWIO) to an otherwise-unprivileged User=io process — removing both the root chmod oneshot AND its ownership bug; the session bus remains reachable via two Environment lines (proven pattern in modules/lib.nix); sops secrets and the existing polkit rules work unchanged; europa gets the agent with no login-session scaffolding at all; and DynamicUser= is ruled out by its D-Bus and ProtectSystem implications, so User=io + capabilities is the canonical minimal shape.

But a naive all-system-service deployment loses the free session-bus environment for notifications, and running the agent as root (the default system-service identity) would be a genuine regression against every security argument in the corpus — Position B only works in its User=<login-user> + AmbientCapabilities= form, which is really "Position A's identity with Position B's lifecycle".

## Committed position

**The evidence supports a third shape neither position names: ONE system service per host, User= set to the host's human/agent user (io), AmbientCapabilities= per host class — with the user-service shape retired entirely.** The load-bearing reason: the two facts that were supposed to force the split both dissolved under direct audit. The session-bus argument for user services dissolved because a User=io system service reaches `/run/user/1000/bus` with two Environment lines (the fleet's own mkSessionLauncher already does this exact thing for cage sessions — modules/lib.nix:60–67), dbus's per-user bus is UID-gated by socket mode alone [[dbus-daemon]], and the agent's only session-bus consumers (notifications, niri, KDE) are absent or optional on every jupiterOS host that lacks a desktop (niri and Plasma appear in zero host configs). The lifecycle argument for system services got *stronger*, not weaker, since 2023: as of Oct 2025 `nixos-rebuild switch` still reactivates user services only for currently-logged-in users [[restart-oneshot-systemd-service-on-every-rebuild-help-nixos-discourse]], so the current kiosk deployment silently reboots-or-stales on every agent config change — an unacceptable property for an appliance fleet the user wants to manage from HA. Meanwhile the deployed "user service" already contains a system unit (the sysfs chmod) whose comment doesn't match the fleet's actual group wiring — evidence that the hybrid is being maintained by hand-waving, not by mechanism. Concretely: the flake's `nixosModules.default` should ship `systemd.services.ha-linux-agent` with `serviceConfig.User` (default "io"), `AmbientCapabilities` (empty on kiosks/callisto; `CAP_SYS_ADMIN CAP_SYS_RAWIO` where SMART is enabled, e.g. europa), `Environment=DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/%U/bus` + `XDG_RUNTIME_DIR=/run/user/%U` (gated on linger existing), `After=network-online.target`, and a `role`-driven mkIf that deletes the sysfs chmod oneshot and the `systemd.user.services` block. Keep `users.users.io.linger = true` on kiosks only (it's what makes the runtime dir exist at boot for the bus Environment to point at — linger is then bus infrastructure, not service model); europa doesn't linger at all, their agents just start with no session bus and the generic backend's existing graceful degradation handles it. Double-registration is prevented because there is only ever one unit shape; the dead `scope = "user"` launcher path should be deleted (0 uses in the fleet) rather than maintained.

**Position:** One NixOS module shipping a single `systemd.services.ha-linux-agent` with `User=io`, host-class-parametrised `AmbientCapabilities=` (CAP_SYS_ADMIN+CAP_SYS_RAWIO for SMART on europa; none on kiosks), explicit `/run/user/<uid>/bus` Environment on hosts that linger, and no user unit anywhere — replacing the current user-service + root-chmod hybrid.

**Confidence:** high (75–80%). The mechanics (User= on system units, AmbientCapabilities semantics, session-bus-at-fixed-path reachability, restart-on-switch gap) are each confirmed by upstream docs or the fleet's own working code; the residual 20–25% is whether notifications-on-kiosks (the one feature that genuinely wants io's session bus) behaves identically when reached from a system service — untested on live hardware in this investigation.

**Boundary conditions:** This position holds for jupiterOS's concrete shape: io exists on every fleet host (common.nix), all launcher profiles are system-scope, niri/Plasma are absent, and the broker is on the LAN. It does NOT hold where (a) the agent must survive on hosts with no static user (DynamicUser would be needed — and it breaks D-Bus name allocation and implies ProtectSystem=strict, both disqualifying for a hardware-probing agent), (b) per-user multi-tenant agents are wanted (several humans, one machine — then user services + ConditionUser are the right tool), or (c) the fleet adopts a desktop backend (niri/KDE sensors) that can't degrade gracefully — the KDE backend's `Connection::session().await?` hard-fails and would need the generic backend's warn-and-continue pattern first. 

**What would change this position:** (1) A live test on a kiosk showing notification delivery from a User=io system service via `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus` fails (e.g. a notification daemon that only activates per-session) — then kiosks keep user services and only servers move, i.e. the host-class split revives with a vengeance. (2) Evidence that `nixos-rebuild switch` gained user-unit reactivation for lingered users post-Oct-2025 (an upstream NixOS change or the `sysinit-reactivation.target` equivalent for user managers) — that removes Position B's lifecycle advantage and makes Position A's simplicity competitive again. (3) A jupiterOS decision to run Plasma/niri desktops fleet-wide with per-session sensors load-bearing — the session-bound environment then becomes a real requirement, not a nice-to-have.

**Evidence weight:** 6 primary-source confirmations (systemd.exec, systemd.special, dbus-daemon, Oct 2025 Discourse, sops-nix, systemd.io UIDs) + 2 kernel-source facts (backlight DEVICE_ATTR_RW default mode; NVMe CAP_SYS_ADMIN requirement via scrutiny #26) + direct repo audit (flake.nix, ha-agent.nix, common.nix, modules/lib.nix, 4 launcher-scope uses, 0 niri/Plasma hosts) all support the merged position; 1 corpus precedent (go-hass-agent's user-service + linger guidance) supports Position A but concedes capabilities for SMART itself; nothing directly contradicts the merged design except the untested notification path.

**Prescriptive specificity.** The module contract, concretely: (1) `systemd.services.ha-linux-agent` with `serviceConfig = { User = "io"; AmbientCapabilities = lib.mkIf cfg.smart [ "CAP_SYS_ADMIN" "CAP_SYS_RAWIO" ]; CapabilityBoundingSet = [ "~" ]` — bounding set inverted-empty means "all", so instead enumerate `CAP_SYS_ADMIN CAP_SYS_RAWIO` and let AmbientCapabilities ⊆ Bounding; `Restart = "on-failure"; RestartSec = 5; }`, `wantedBy = [ "multi-user.target" ]`, `after = [ "network-online.target" ]`; (2) on hosts where io lingers (kiosks, callisto): `Environment = [ "XDG_RUNTIME_DIR=/run/user/%U" "DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/%U/bus" ]` — the systemd `%U` specifier resolves to the User='s UID; on servers, omit and let the generic backend degrade; (3) keep `sops.secrets.mqtt_ha_linux_agent.owner = "io"` unchanged — sops-nix system module + owner works identically; (4) delete `ha-linux-agent-sysfs-perms` on hosts whose writes AmbientCapabilities covers (kiosks keep NO capabilities and simply lose write-governor/backlight — kiosks already run `backlight = false` and their brightness goes through the launcher `light` profile, which must then ALSO move to a udev `GROUP="video"` + `users.users.io.extraGroups = [ "video" ]` fix or its own capability), and fix the ha-agent.nix:112 comment either way; (5) the flake's `nixosModules.default` gains a `role` option (`kiosk | server | minimal`) that mkIf-switches the Environment block and capabilities, so ONE module serves adrastea–thebe (kiosk), callisto (kiosk), europa (server: SMART caps + ZFS `zpool` on PATH via `environment.systemPackages` or ` SupplementaryGroups = [ "disk" ]`... note zpool status reads work unprivileged, no cap needed), ; (6) `nixos-rebuild switch` then restarts the agent on every host, every time — the property the current fleet lacks. Verification gate: a `runNixOSTest` that boots the module in both roles and asserts (a) the unit is `active (running)` as `system` with `User=io` (`systemctl show -p User`), (b) `switch` with a changed config restarts the unit, (c) on a lingered-user host the process can `busctl --user --address=...` list the session bus.

## Open questions

1. **Notification delivery from the system side — untested.** The design's weakest link is whether a notification daemon (mako/dunst) exists at all in io's user session on the kiosks to receive org.freedesktop.Notifications — greps found no mako/dunst package in jupiter-os; notifications may already be dead code on every host, which would make the whole session-bus Environment block unnecessary rather than merely untested. Worth one live `busctl` check on amalthea before the module rewrite.

3. **smartd -M exec vs in-agent SMART on europa.** jupiter-os already runs smartd (smart-monitoring.nix) with no notification hook wired (`-m` unset → writes to syslog by default). Whether europa's agent should do SMART itself (capabilities on the agent unit) or subscribe to smartd's channel is the headless-privilege-ladder locus's territory; my position only requires that IF in-agent SMART is chosen, it's AmbientCapabilities on the system unit.
4. **`%U` specifier in Environment=.** systemd's `%U` expands to "the UID of the user running the service" — verified semantics for User= services in systemd.unit(5) specifiers table, but I did not fetch the specifier man page in this budget; trivially verifiable at implementation time.
5. **Whether the 4 kiosks ever get reboot-scheduled.** If the fleet reboots kiosks weekly anyway, the restart-on-switch gap bites less — but that's an operational fact I couldn't verify from the repos (no reboot timer found; the arcade module has a nightly gamescope recycle, not a reboot).
