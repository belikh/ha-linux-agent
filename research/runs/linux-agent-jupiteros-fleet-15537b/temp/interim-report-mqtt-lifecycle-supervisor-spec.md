# Interim report: mqtt-lifecycle-supervisor-spec

**Locus question:** What is the concrete, implementable MQTT lifecycle supervisor design on rumqttc — re-subscribe on every ConnAck, clean_session handling + stable client_id, birth-message-triggered discovery republish with jitter, LWT + explicit SIGTERM offline publish, stale-message bounding, ghost cleanup via empty-payload publishes, per-backend task isolation (fixes the verified hung-syncthing stall), and the paired broker `max_queued_messages` sizing on callisto — mapped defect-by-defect to the file:line audit?

**Flavor:** technical (convergent)

## What the corpus already said

The width sweep established WHAT the agent must do with near-consensus, but not HOW. [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]] shows rumqttc reconnects but never re-establishes subscriptions after reconnect (issue open since Feb 2021, still open, "in-pipeline"); the workaround is re-calling `client.subscribe()` in the poll loop's error branch. [[eventloop-in-rumqttc-rust]] and [[rumqttrumqttcsrceventlooprs-at-main-bytebeamiorumqtt-github]] establish the reconnect contract: keep polling through errors; `clean()` preserves unacked QoS≥1 for replay; `if !connack.session_present { self.pending.clear(); }`; and the docs recommend `AsyncClient` channel capacity 0. [[rumqttc-reconnection-to-mqtt-broker-and-pending-messages-ttl-issue-211-bytebeami]] documents that rumqttc has NO disconnect callback and NO pending-message TTL (open since Dec 2020, labelled stale/blocked) — stale telemetry can publish on reconnect. [[librs]] confirms rumqttc at main is MQTT v3.1.1-only (no session expiry, no message expiry), `set_clean_session(false)` panics on empty client_id. [[mqtt-home-assistant]] gives HA's official birth-message contract: "A device or service that exposes the MQTT discovery should subscribe to the Birth message and use this as a trigger to send the discovery payload. To avoid high IO loads on the MQTT broker, adding some random delay in sending the discovery payload is recommended," and HA's own will fires on both clean and unclean shutdown. [[device-availability-zigbee2mqtt]] gives the production jitter/backoff reference (max_jitter 30 s, x1.5/x3/x6/x12 backoff). [[comments]] (HA issue #135266 full thread) shows broker-side silent retained-message drop at HA-restart replay scale (56 of 112 topics arrived empty; the user's broker had a too-low allowed-maximum-queued-messages; raising it "seems to be the instant cure"). [[mqtt-availability-community]], [[my-hand-built-mqtt-devices-are-unavailable-after-hassio-restart-but-zigbee2mqtt]], and [[the-homie-convention]] establish the retained-discipline matrix (config+state+availability retained, commands never) and Homie's empty-payload removal ordering. [[mqtt-client-component-esphome-smart-home-made-simple]] contributes the shutdown_message pattern (LWT cannot cover clean shutdown) and the reboot_timeout watchdog pattern. [[what-is-mqtt-last-will-and-testament-lwt-mqtt-essentials-part-9]] confirms the broker discards the stored LWT on a graceful DISCONNECT.

## What the new sources say

**[[mosquittoconf-man-page-eclipse-mosquitto]]** (mosquitto.conf(5) — the highest-priority gap fill): `max_queued_messages` — "The maximum number of QoS 1 or 2 messages to hold in the queue (per client) above those messages that are currently in flight. Defaults to 1000. Set to 0 for no maximum (not recommended)." `max_queued_bytes` — "Once this limit has been reached, subsequent messages will be silently dropped… Defaults to 0. (No maximum)." `persistence` — "If false, the data will be stored in memory only. Defaults to false," with "connection, subscription and message data" (i.e. including retained messages) written to mosquitto.db when true, at `autosave_interval` (default 1800 s) and on clean exit. `queue_qos0_messages` "Defaults to false" — QoS 0 messages are not queued for disconnected persistent clients.

**[[availabilityts]]** (Zigbee2MQTT availability extension source): the production algorithm is `const jitter = Math.random() * this.getMaxJitter(device);` (max_jitter default 30 000 ms) applied to every availability-ping timeout; on ping failure, `this.pingBackoffs.set(device.ieeeAddr, currentBackoff * (available ? 1.5 : 2));` producing "backoffs: *1.5, *3, *6, *12… (with default timeout: 10, 15, 30, 60, 120)"; availability publishes are retained QoS 1 — `this.mqtt.publish(topic, JSON.stringify(payload), {clientOptions: {retain: true, qos: 1}})` — deduped via `lastPublishedAvailabilities`; and reconnect triggers a 2-s-debounced state retrieval.

**[[mqttoptions-in-rumqttc-rust]]** (rumqttc 0.24.0 — the EXACT version pinned in this repo's Cargo.lock): `set_clean_session` semantics verbatim — "clean_session = true removes all the state from queues & instructs the broker to clean all the client state when client disconnects. When set false, broker will hold the client state and performs pending operations on the client when reconnection with same client_id happens. Local queue state is also held to retransmit packets after reconnection. Panic: Panics if clean_session is false when client_id is empty." Also present in 0.24.0: `set_keep_alive`, `set_last_will`, `set_request_channel_capacity`, `set_pending_throttle`, `set_inflight(u16)`, `set_manual_acks`. **No MQTT v5 clean-start/session-expiry API** — 0.24.0's options surface is v3.1.1-only.

**[[staters]] + [[eventlooprs]]** (rumqttc state.rs/eventloop.rs at main, re-fetched raw): definitively answers the subscribe-before-connect question — `client.subscribe()` before the first connection is safe: subscribe requests are buffered in the bounded flume channel (`EventLoop::new` does `bounded(cap)`) and drained only inside `select()`, which runs post-ConnAck; "If available, prioritises pending requests from previous session." On poll error, `clean()` merges unacked publishes + channel contents into `pending` (dropping only `Request::PubAck`); on next connect, "if !connack.session_present { self.pending.clear(); }". And the standing rule: "NOTE Don't block this while iterating."

**[[asyncclient-in-rumqttc-rust]]** (rumqttc 0.24.0 AsyncClient docs): `pub async fn disconnect(&self) -> Result<(), ClientError>` — "Sends a MQTT disconnect to the EventLoop" — the graceful-shutdown primitive EXISTS in the pinned version. Also `try_disconnect`, `try_publish`, `try_subscribe` non-blocking variants.

**[[rumqttc-rust-2]]** (rumqttc 0.24.0 crate front page): confirms the pinned version advertises "Automatic reconnections by just continuing the eventloop.poll() loop," "Natural backpressure to client APIs during bad network," and queue-size flow control — with re-subscription NOT among the advertised features.

**[[mqtt-zigbee2mqtt]]** (Z2M MQTT config guide): keepalive 60 s, `cache_state` send-on-change with periodic resend, and `force_disable_retain` caveats — corroborating the retained-first design.

## Evidence synthesis: the defect-by-defect supervisor spec

Ground truth audited directly: `crates/core/src/agent.rs` (198 lines, quoted verbatim below where load-bearing), `crates/backend-syncthing/src/lib.rs`, `Cargo.toml`/`Cargo.lock` (rumqttc pinned 0.24.0), `crates/agentd/src/main.rs` (no signal handling anywhere — verified by grep for `SIGTERM|signal|ctrl_c|shutdown` across `crates/`: zero hits), `/home/io/projects/jupiter-os/modules/services/mqtt.nix`, `/home/io/projects/jupiter-os/modules/services/ha-agent.nix`, and `hosts/callisto/configuration.nix:214-227`.

### Defect D1 — Deafness after any reconnect (THE root cause of "never reliable")

`agent.rs:134-138` subscribes exactly once, inside a fire-and-forget setup task: `for topic in &command_routes_keys { if let Err(e) = client_for_setup.subscribe(topic, QoS::AtLeastOnce).await { warn!("subscribing to {topic}: {e}"); } }`. The poll loop at `agent.rs:177-196` swallows ConnAck with `Ok(_) => {}` (line 190) and never re-subscribes. rumqtt #250 (open since Feb 2021, in-pipeline as #1052): after a reconnect with a clean session, "I'm not seeing any data coming in from subscribed topics" — subscriptions live only in broker-side session state, which a clean session destroys on every reconnect. Compounding on callisto: `mqtt.nix` sets no `persistence`, so mosquitto defaults `persistence false` — "data will be stored in memory only" — meaning **every broker restart wipes all sessions and subscriptions fleet-wide**. Result today: the first mosquitto restart, HA restart (if the broker connection drops), or network blip permanently deafens every agent — it keeps publishing state (the poll task is independent) but can never receive commands again. This alone explains "never reliable."

**Spec:** in the poll loop, explicitly match `Ok(Event::Incoming(Packet::ConnAck(ack)))`; on every ConnAck (first or reconnect, `session_present` either value), (a) re-issue all command-topic subscribes (idempotent — SUBSCRIBE refreshes broker-side subscription state), and (b) re-assert the connection-level lifecycle publishes (D3). Subscribe-before-connect is proven safe (requests buffer in the flume channel until post-ConnAck `select()` drains them — [[eventlooprs]]), so the current setup task's subscribes can stay as a fast path, but the ConnAck branch is the mandatory one.

### Defect D2 — Availability stuck "offline" forever after the first blip (second root cause, equally severe)

`agent.rs:139-144` publishes retained availability "online" exactly once in the setup task: `client_for_setup.publish(&avail_topic_setup, QoS::AtLeastOnce, true, "online")`. But on any ungraceful disconnect the broker fires the LWT (`agent.rs:55-60`, retained "offline") — correct behaviour. The bug: on reconnect the agent never re-publishes "online". So after the FIRST reconnect, the retained availability topic permanently says "offline" while state telemetry flows normally — HA marks every entity of that host unavailable forever (per [[mqtt-availability-community]], an entity with `availability_topic` stays unavailable until a payload actually arrives on that topic; state alone is not enough). Hosts look dead in HA while actually working — the mirror image of D1, and users read both as "the agent is broken."

**Spec:** on every ConnAck, publish retained `ha-linux-agent/{device_id}/availability` = "online" (QoS 1, retain) BEFORE resuming telemetry; on SIGTERM, publish retained "offline" explicitly then disconnect (D7).

### Defect D3 — Discovery loss at HA restart, and no birth-triggered republish

Corpus-established: retained discovery is necessary but not sufficient. [[some-mqtt-devices-unavailable-after-ha-restart-issue-135266-home-assistantcore-g]] + [[comments]]: at 5374 entities, retained configs existed on the broker and fresh state arrived, yet 8-10 devices stayed unavailable — broker replay dropped messages (D9). HA's own contract ([[mqtt-home-assistant]]): agents "should subscribe to the Birth message and use this as a trigger to send the discovery payload," with "some random delay" recommended to avoid IO storms.

**Spec:** subscribe to `homeassistant/status` (ACL-legal on callisto: the agent's acl already grants `readwrite homeassistant/#` — `callisto/configuration.nix:221-227`). On payload "online" (HA birth), republish ALL discovery configs (idempotent, retained) after a uniform random jitter of 0–30 s per host (Z2M's `max_jitter` default 30000 ms, `Math.random() * getMaxJitter(device)` — [[availabilityts]]), then re-assert availability "online". Also subscribe `homeassistant/status` in the ConnAck re-subscribe set so a HA-while-agent-restarted sequence is covered both ways.

### Defect D4 — Stale-message bounding (rumqtt #211 has no fix, and none is coming)

`AsyncClient::new(opts, 64)` (`agent.rs:62`) — capacity 64. The poll task publishes retained state every `poll_interval` (default 30 s) regardless of connection state (`agent.rs:149-172`), so during an outage up to 64 stale state messages queue, the poll task then blocks on the bounded channel, and on reconnect the whole stale burst replays. rumqtt #211 (Dec 2020, labelled stale/blocked): "no way to… set a TTL or garbage-collect stale pending messages." The rumqtt docs' own recommendation ([[eventloop-in-rumqttc-rust]], [[eventlooprs]]): "we recommend setting AsyncClient's channel capacity to 0."

**Spec:** (a) set the request channel capacity to 0 (rendezvous semantics — each publish hands off directly to the eventloop); (b) wrap every state publish in `tokio::time::timeout(poll_interval)` and drop that tick's payload on timeout — this bounds published-state staleness to at most one poll interval and never blocks the poll task; (c) because all state goes to ONE retained topic per host (`discovery.rs:6-8`), a fresh publish overwrites any older retained payload — staleness is self-healing by design. Do NOT gate telemetry on a connection flag (a watch channel adds race complexity for no gain over the rendezvous+timeout pair).

### Defect D5 — The verified hung-syncthing stall: one backend starves all sensors (lying-telemetry failure mode)

`backend-syncthing/src/lib.rs:75` and `:98`: `reqwest::Client::builder().build()` — **no `.timeout()`** (reqwest has no default timeout). `agent.rs:154-157` polls ALL sensor backends sequentially in ONE task: `for backend in &sensor_backends { for state in backend.poll().await { … } }`. A hung syncthing daemon (or half-open TCP to its REST API) blocks `poll()` forever → no state publishes from ANY backend → every sensor on the host goes stale in HA while the availability topic still says "online" and the LWT never fires (the MQTT connection is fine). This is the worst failure class in the fleet: sensors that lie rather than sensors that vanish.

**Spec:** (a) build the syncthing reqwest client with `.timeout(Duration::from_secs(5)).connect_timeout(Duration::from_secs(2))`; (b) wrap each `backend.poll()` in `tokio::time::timeout(poll_interval)` and merge whichever backends answered — a timed-out backend contributes nothing that tick and logs a warning; (c) same isolation for commands: `backend.handle(command_id, &payload).await` at `agent.rs:185` is awaited INLINE in the eventloop poll loop — a hung command handler blocks the loop, keepalive pings stop, the broker drops the connection, the LWT fires and availability flaps. rumqtt's standing rule: "NOTE Don't block this while iterating." Dispatch every command via `tokio::spawn` with its own timeout; the poll loop only routes.

### Defect D6 — No graceful shutdown; systemd never restarts the agent

`main.rs` has no signal handling (verified: zero grep hits for signal/SIGTERM/ctrl_c across crates/). `ha-agent.nix:104-106` defines `systemd.user.services.ha-linux-agent.unitConfig = { ConditionUser = "io"; }` and nothing else — NixOS user services default `Restart=no`, so a crashed agent stays dead until reboot. Today's SIGTERM path works only by accident: the process dies, TCP closes ungracefully, the LWT fires "offline" retained. The accident breaks the day someone adds a graceful path without the explicit publish — per [[what-is-mqtt-last-will-and-testament-lwt-mqtt-essentials-part-9]], the broker DISCARDS the stored LWT on a clean DISCONNECT, so a clean shutdown that sends DISCONNECT without first publishing "offline" leaves the retained availability stuck at "online" forever (the exact trap [[mqtt-client-component-esphome-smart-home-made-simple]] solves with `shutdown_message`).

**Spec:** (a) handle SIGTERM/SIGINT: publish retained availability "offline", await that publish (QoS 1), then `client.disconnect()` (exists in 0.24.0 — "Sends a MQTT disconnect to the EventLoop", [[asyncclient-in-rumqttc-rust]]), then exit — availability is correct by construction on both paths; (b) systemd: `Restart=on-failure`, `RestartSec=5s`, plus `WatchdogSec=` via sd_notify (ESPHome's reboot_timeout analogue: reboot the agent after 15 min without a healthy loop) — at minimum Restart=on-failure so a panic doesn't kill the host's telemetry until the next boot.

### Defect D7 — Ghost entities: no decommission path, no MQTT v5 expiry available

rumqttc 0.24.0 is MQTT v3.1.1-only ([[mqttoptions-in-rumqttc-rust]] — no session/message expiry API), so HA's `message_expiry_interval` is unavailable. A host decommissioned, or sensors removed from its config, leave retained discovery configs that resurrect on every HA restart (ESPHome ships `clean-mqtt` for exactly this). HA's official removal semantic (corpus, discovery.py): an EMPTY payload published to a discovery config topic cleans up the entity and, for device-based discovery, regenerates cleanup for the device's components. Homie ([[the-homie-convention]]) prescribes clearing retained topics with zero-length payloads in order.

**Spec:** add a `ha-linux-agent --decommission` mode (or `clean` subcommand) that publishes zero-length payloads to every discovery config topic it owns, then to the state and availability topics (order: state/availability first, configs last, mirroring Homie's state-first rule); derive the topic list from the same descriptors used for discovery so the two can never drift. Also emit it opportunistically: if the configured sensor/command set differs from the last published set (persisted in e.g. `/var/lib/ha-linux-agent/last-discovery.json`), clear the removed topics on next start.

### Defect D8 — clean_session: the locus presumption is wrong for this fleet

The locus one_line presumed `clean_session=false + stable client_id`. The evidence says otherwise for THIS fleet. What a persistent session buys: broker-held subscriptions (moot — D1 re-subscribes on ConnAck), unacked-publish replay (moot — retained state self-heals by overwrite), and **broker-side queueing of QoS 1 messages for the offline agent — which for this fleet means commands**. HA publishes commands to `ha-linux-agent/{id}/cmd/#` non-retained QoS 1; with a persistent session, commands sent while a host is off (kiosks power off overnight; `ha-agent.nix` enables them fleet-wide) queue on callisto and replay at morning boot — with no TTL available in v3.1.1 (rumqtt #211) and no timestamp in the payload, the agent cannot tell a week-old command from a fresh one. A replayed launcher toggle or reboot command is a real, fleet-specific hazard. The production references all use clean sessions plus birth/LWT: ESPHome's IDF client defaults clean_session true, Z2M's mqtt.js client defaults clean true — both rely on birth-triggered reannounce rather than session state, exactly the pattern D1–D3 implement.

**Spec:** keep `clean_session = true` (the rumqttc default — set it explicitly for intent), stable client_id (`ha-linux-agent-{device_id}` at `agent.rs:45`, and `device.id = config.networking.hostName` per `ha-agent.nix:129` — stable across reboots), and get all reliability from the ConnAck-driven re-subscribe + re-assert + birth republish. If offline command queueing is ever wanted deliberately (e.g. "boot into arcade mode" sent while off), flip per-host to `set_clean_session(false)` and accept replay semantics consciously.

### Defect D9 — Broker pairing on callisto: defaults are wrong at fleet scale

`mqtt.nix` sets only port/anonymous/users — no `max_queued_messages`, no `persistence`. Defaults ([[mosquittoconf-man-page-eclipse-mosquitto]]): `max_queued_messages 1000`, `max_queued_bytes 0`, `persistence false`, `autosave_interval 1800`. HA #135266 ([[comments]]): at 5374 entities the broker's per-client queue overflowed during HA's startup retained replay and "SILENTLY DROPPED retained messages (56 of 112 topics for the affected device arrived empty)" — retained configs existed on the broker, fresh state arrived, and devices still showed unavailable; raising the broker limit "seems to be the instant cure." Callisto currently carries HA + every agent host on the same default-1000 broker.

**Spec (prescriptive sizing rule):** fleet retained-message inventory R = Σ(entities per host) + 2 per host (state + availability) + 1 (`homeassistant/status`). Size `max_queued_messages ≥ 4×R` to absorb HA-restart replay plus concurrent birth-triggered republishes. Concrete: a 20-host fleet averaging 50 entities → R ≈ 1 100 → set `max_queued_messages 8192` (power-of-two headroom; "Set to 0 for no maximum (not recommended)" per the man page). Also set `persistence true` + `persistence_location /var/lib/mosquitto/` on callisto — without it every broker restart wipes all retained messages, sessions, and subscriptions, making D1's ConnAck re-subscribe the only thing standing between a callisto reboot and a fleet-wide deafness event (and the birth-republish of D3 the only thing restoring HA's entity state). In jupiter-os terms: extend `mqtt.nix` with a `settings` passthrough (or `extraConf`) emitting `max_queued_messages`, `persistence true`, `persistence_location`; wire defaults so every fleet broker gets them, with the assertion message updated to mention the drop-at-scale failure.

### Reconnect backoff (smaller item)

The error branch at `agent.rs:191-193` does a fixed `sleep(5s)`. rumqtt has no built-in backoff (reconnect is attempted on every `poll()`), so the inter-poll sleep IS the backoff. **Spec:** exponential 1 s → 2 s → 4 s → … capped 60 s, with ±20 % jitter per attempt so a broker restart doesn't synchronise N hosts into a reconnect stampede (Z2M's jitter rationale, fleet-sized).

## Committed position

The evidence adds up to a supervisor whose entire reliability posture hangs on ONE structural change: **the connection lifecycle must be driven from the poll loop's ConnAck event, not from a fire-and-forget setup task** — because rumqttc (pinned 0.24.0, and at main per #250/#1052, open 5+ years) will reconnect forever but will never re-subscribe or re-assert availability on its own, and every other defect in the audit is either a consequence of that omission (D1 deafness, D2 permanent-offline, D3 no birth response) or an independent but well-evidenced fix (D5 backend/command isolation with reqwest timeouts, D4 cap-0 + publish-timeout stale bounding, D6 SIGTERM offline-then-disconnect with AsyncClient::disconnect() which exists in 0.24.0, D7 empty-payload decommission since v3.1.1 forecloses message expiry, D9 callisto max_queued_messages 8192 + persistence true since the mosquitto default of 1000 is empirically the silent retained-drop mechanism from HA #135266). I commit AGAINST the locus's presumed `clean_session=false`: for a fleet whose kiosks power off overnight, a persistent session's only unique deliverable is replaying stale commands with no TTL and no age information (rumqtt #211, blocked since 2020), while every reliability benefit the locus sought is provided by the ConnAck-driven re-subscribe/re-assert and birth-triggered republish — the exact clean-session + birth/LWT pattern the production references (ESPHome, Z2M) use. The load-bearing reason in one sentence: rumqttc's reconnect is unconditional but its re-subscription is non-existent and callisto's defaults are amnesiac, so the agent must own its lifecycle on every ConnAck and the broker must be sized and persisted to match, or the fleet goes deaf and dark on the first restart.

- **Position:** ha-linux-agent's "never reliable" is two bugs (no ConnAck re-subscribe at agent.rs:134-138; availability "online" published exactly once at agent.rs:139-144) amplified by three default-shaped traps (mosquitto `persistence false` wiping sessions per broker restart, `max_queued_messages 1000` silently dropping HA's retained replay at fleet scale, rumqttc's unbounded stale pending queue) plus the verified hung-backend stall from the timeout-less reqwest client (backend-syncthing/src/lib.rs:75,98) — and the fix is a ConnAck-driven supervisor with clean_session=true, cap-0 rendezvous publishes under per-tick timeout, birth-subscription with 0–30 s jitter, SIGTERM offline-then-disconnect, per-backend/per-command task isolation with 5 s HTTP timeouts, a zero-payload decommission path, and a paired jupiter-os mqtt.nix change (max_queued_messages ≥ 4× fleet retained inventory, persistence true).
- **Confidence:** high (>80%) on the defect audit and the ConnAck/birth/LWT mechanism (primary-source code + rumqttc 0.24.0 API docs + mosquitto.conf(5) + HA's own docs and maintainer-resolved issue all point the same way); medium on the two judgement calls inside the spec — clean_session=true over the locus's presumption (the stale-command replay hazard is reasoned from fleet behaviour, not measured) and the exact 4× sizing multiplier for max_queued_messages (extrapolated from one 5374-entity incident).
- **Boundary conditions:** this spec holds for an MQTT v3.1.1 client on rumqttc 0.24.x talking to a mosquitto broker shared by HA at fleet sizes up to low hundreds of hosts; if the agent later moves to an MQTT v5 client (rumqttc's options surface gains session/message expiry, or a client switch per the sibling rumqttc-fitness locus), the stale-command argument weakens (message expiry bounds replay) and clean_session=false + session_expiry_interval becomes reasonable again. Outside the kiosk overnight-off pattern (an always-on server fleet), the persistent-session hazard mostly evaporates but the ConnAck-driven supervisor remains mandatory regardless.
- **What would change this position:** (1) evidence that rumqtt ≥ some release actually re-subscribes after reconnect (closing #250/#1052) would demote the ConnAck re-subscribe from mandatory to defensive; (2) a measured fleet test showing mosquitto at default max_queued_messages does NOT drop HA's replay below ~100 retained topics would soften D9's sizing urgency; (3) a jupiter-os policy decision that commands must queue across host power-off would flip D8 back to clean_session=false and require an idempotency contract on every command handler; (4) discovery that HA's MQTT integration no longer subscribes broadly enough to hit per-client queue limits at jupiterOS's actual entity counts would reduce D9 to a hygiene fix.
- **Evidence weight:** 3 primary-source code reads (rumqttc 0.24.0 API docs, eventloop.rs/state.rs at main, agent.rs/lib.rs ground truth) + 2 official man/doc pages (mosquitto.conf(5), HA MQTT integration) + 2 production-reference implementations (Z2M availability.ts + ESPHome docs) + 1 maintainer-resolved HA issue thread (#135266 with its 22-comment API fetch) all support the mechanism; 1 locus presumption (clean_session=false) contradicted by fleet-specific reasoning; the max_queued sizing multiplier is single-incident extrapolation.

## Open questions

- `expire_after` on sensors as a complementary staleness bound (entity goes unavailable after N seconds without a state message — would surface a hung poll task as "unavailable" rather than stale-lying): the exact semantics live in HA's per-platform sensor docs, which this locus did not fetch (only the abbreviation `exp_aft` appears in the integration page). Recommend a small follow-up if the orchestrator wants it in the final report's prescriptive table.
- The precise NixOS wiring for global mosquitto options: jupiter-os's `mqtt.nix` uses per-listener `settings`; whether `max_queued_messages`/`persistence` belong in a listener's `settings` or global `extraConf` in the NixOS mosquitto module needs a check against the module source (the man page says the queue option "applies globally").
- Whether HA's default MQTT integration subscribes to `#` (as the #135266 debug log showed: "Subscribing with mid: 11 to topics with qos: [('#', 0)]") or per-component wildcards (as discovery.py suggests) at current HA versions — it changes which client's queue overflows, but not the sizing rule.
- Whether any launcher-style command semantics in this fleet are non-idempotent (reboot/power commands) — if none are, the clean_session question becomes lower-stakes than argued.
- Measured per-host entity counts on the real fleet (the 20×50 = 8 192 sizing is an estimate; `sensors()` per host varies by backend availability per machine).
