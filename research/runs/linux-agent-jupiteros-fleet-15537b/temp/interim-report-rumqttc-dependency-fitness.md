# Interim report: rumqttc-dependency-fitness

**Locus question:** Is rumqttc (pinned 0.24 here) the right dependency to build the reliability phase on: is re-subscription (#250, labelled in-pipeline as #1052) actually fixed in any release, what is the crate's real maintenance state, and does its MQTT v3.1.1-only surface force the lifecycle spec's workarounds — or should the agent switch clients?
**Flavor:** technical (convergent)

## What the corpus already said

The width sweep established that rumqttc's headline reliability claim is narrower than it looks: [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]] (issue #250, open since Feb 2021, labelled "in-pipeline… Planned to be resolved in a future release" as of #1052) shows the eventloop reconnects automatically but **never re-establishes subscriptions** — after a ConnAck with `session_present: false`, "no more incoming data" arrives and the user "XXX: Here I have to re-subscribe to the topics :(". [[rumqttc-reconnection-to-mqtt-broker-and-pending-messages-ttl-issue-211-bytebeami]] (open since Dec 2020, labelled stale/blocked) shows there is no disconnect callback and no TTL on the pending queue, so arbitrarily old messages replay on reconnect. [[eventloop-in-rumqttc-rust]] and [[rumqttrumqttcsrceventlooprs-at-main-bytebeamiorumqtt-github]] confirm the poll() contract: "Continuing to poll will reconnect to the broker if there is a disconnection", `clean()` preserves unacked QoS≥1 for replay, "If it's a new session, clear the pending packets", and the docs recommend setting AsyncClient's channel capacity to 0 when managing pending. [[librs]] established that `set_clean_session(false)` panics on empty client_id and that defaults are clean_session=true / keep_alive=60s / cap=10. What the corpus had NOT verified: whether any release actually shipped re-subscription handling, what changed 0.24→0.25.x, and whether the "v3.1.1-only" framing holds.

## What the new sources say

**[[releases-bytebeamiorumqtt-github]]** (full release list 0.22.0→0.25.1): the crate is **alive but slow** — 0.24.0 released 21 May, 0.25.0 on 09 Sep, 0.25.1 on 21 Nov (latest, signed). Critically, **no release note in the 0.24.0→0.25.1 range mentions re-subscription, #250, #1052, or #211**. 0.25.0's headline: "Session Management: Added support for session_expiry_interval in MQTT v5 connections, giving you better control over session persistence", plus v5 Auth, public DisconnectProperties, and "Improved event ordering in poll() method for more predictable behavior". 0.25.1: "This patch release focuses on fixing the broken WebSocket feature and includes dependency updates" — nothing else. So the re-subscription fix the roadmap was implicitly waiting on **has not shipped in any release**.

**[[rumqttc-emit-eventreconnect-on-successful-re-connack-closes-250-by-pbujanda1978]]** (PR #1052): the "in-pipeline" label's referent is **OPEN, not merged** — "pbujanda1978 wants to merge 1 commit into bytebeamio:main" (opened May 2026, one community comment, no maintainer engagement visible on timing). And its design is telling: it does NOT put re-subscription in the library. It emits a synthetic `Event::Reconnect` "after subsequent successful CONNACKs", and "the caller pattern is: Ok(Event::Reconnect) => { for (topic, qos) in &my_subs { client.subscribe(topic, *qos).await?; } }". The PR's own problem statement is the best articulation of the agent's defect: "After a transport drop and successful reconnect, the broker has a fresh session. With clean_session = true (or session expiry), every subscription the client had is gone. rumqttc itself doesn't remember them either, so the application is silent on the new session until it re-subscribes — but it has no signal that a reconnect happened. This is #250: a long-standing rumqttc footgun where a transient network blip leaves a process running but unable to receive any publishes, with no error in the event loop." Scope: "only v5 here — the same fix applies to v4; happy to add it in this PR or a follow-up". Even the proposed fix leaves ownership of subscriptions with the application — it only adds the *signal*.

**[[rumqttc-rust-3]] + [[event-in-rumqttc-rust]]** (docs.rs 0.24.0, the EXACT locked version): `Event` has exactly two variants — "pub enum Event { Incoming(Incoming), Outgoing(Outgoing), }" — **no `Reconnect` variant in 0.24.0**. poll() yields `Event::Incoming(Packet::ConnAck)` on every connect, so a second CONNACK is the only reconnect signal the pinned version offers. "Automatic reconnections by just continuing the eventloop.poll()/connection.iter() loop" and "Natural backpressure to client APIs during bad network" are confirmed in-version; re-subscription is conspicuously absent from the feature list.

**[[asyncclient-in-rumqttc-rust-2]]** (0.25.1 AsyncClient) + **[[asyncclient-in-rumqttc-rust]]** (0.24.0 AsyncClient, reused from a sibling locus): the public client API is **method-for-method identical across 0.24.0 → 0.25.1** (new/from_senders/publish/try_publish/ack/publish_bytes/subscribe/try_subscribe/subscribe_many/unsubscribe/try_unsubscribe/disconnect/try_disconnect — 0.25.1 adds nothing, removes nothing). `disconnect()` exists in 0.24.0: "Sends a MQTT disconnect to the EventLoop" — the graceful-shutdown primitive the sibling's spec (D6) depends on is available in the pinned version.

**[[github-eclipse-pahopahomqttrust-pahomqttrust-github]]** (Paho Rust README) + **[[asyncclient-in-paho_mqttasync_client-rust]]** (Paho 0.14.0 AsyncClient docs) + **[[releases-eclipse-pahopahomqttrust-github]]**: the main alternative supports "MQTT v5, 3.1.1, and 3.1" with "Automatic Reconnect" and "Offline Buffering" built in, and is runtime-agnostic ("Tested with tokio and smol"). Maintenance is active (v0.14.0 on 26 Mar; note v0.12.3 was a reconnect-bug fix). **But** it is "a safe wrapper around the Paho C Library… Requires Paho C v1.3.16" — default builds need CMake + a C compiler + system OpenSSL, which in a jupiterOS (NixOS) fleet context means a foreign C dependency chain in every host closure; and crucially **Paho does not auto-resubscribe either** — its API offers `set_connected_callback` / `set_connection_lost_callback` / `reconnect()` as the hook points where the *application* re-subscribes. The problem rumqttc is criticised for is identical in Paho; only the callback surface differs.

**Ground truth read locally (zero fetches, highest rank per run directives):** Cargo.lock pins **exactly 0.24.0** (checksum e1568e15…). agent.rs uses cap=64 (not 0), ignores ConnAck (`Ok(_) => {}` at agent.rs:190), never re-subscribes in the Err branch (agent.rs:191-194 — it warns and sleeps 5s), and runs all discovery/subscribe/availability setup exactly once in a fire-and-forget task (agent.rs:92-145) — the precise shape issue #250 says goes permanently deaf after any broker restart. And a **correction to the locus premise**: grepping the actual 0.24.0 crate source shows rumqttc 0.24.0 is **not v3.1.1-only** — `src/lib.rs:113` declares `pub mod v5;` with a complete v5 client: `v5::AsyncClient` with `publish_with_properties(PublishProperties)` whose mqttbytes expose `message_expiry_interval: Option<u32>`, `subscribe_with_properties`, and v5 `MqttOptions` with `clean_start` and `session_expiry_interval`. The single `unimplemented!()` in v5/state.rs:214 sits on request variants (PubComp/SubAck/UnsubAck/PingResp) the public client never sends — unreachable from agent code. The "v3.1.1 lock-out" is real only for the default v4 surface the agent currently uses; MQTT v5 is a module-scope switch away inside the same pinned version.

**Measured upgrade test (run directives: measured exit codes outrank claims):** with `rumqttc = "0.25.1"` substituted into Cargo.toml, `cargo check -p ha-agent-core` → exit 0, `cargo test -p ha-agent-core` → "3 passed; 0 failed", `cargo clippy -p ha-agent-core --all-targets` → clean, all with **zero code changes**. Workspace subsequently reverted to pinned 0.24.0 (git checkout Cargo.lock; rumqttc = "0.24" restored).

## Evidence synthesis

The three questions resolve cleanly against the roadmap's implicit assumptions. First, **re-subscription is not fixed in any release and never will be fixed the way the issue title implies**: #250 (Feb 2021) is still open; the "in-pipeline" label points at PR #1052, which is open, unreviewed by maintainers, v5-scoped, and — even if merged tomorrow — only adds a reconnect *signal*, leaving subscription ownership with the application by design. The pattern PR #1052's caller illustrates is exactly the ConnAck-driven re-subscribe the sibling's supervisor spec mandates; waiting for upstream would save the agent nothing, because the application must hold its subscription set and re-drive it either way. Second, **maintenance is alive-but-slow, not dead**: three releases in ~6 months (0.24.0 → 0.25.1), GPG-signed, 2.2k stars, but the issues that gate fleet reliability (#250, #211) have been open 4-5+ years with no maintainer response, and the 35.34% docs coverage is a genuine tax. Third, the **v3.1.1-only premise is half-wrong**: 0.24.0 ships a full v5 module (message expiry, session expiry, clean_start, subscribe/publish with properties), so HA's `message_expiry_interval`-style features are available without changing dependencies — only by moving imports from `rumqttc::*` to `rumqttc::v5::*` and swapping the v5 MqttOptions/AsyncClient types. The genuine v4-path gaps that remain are: no message expiry (so stale telemetry bounding must be application-side — the sibling's cap-0 + per-tick timeout design), no session expiry (so clean_session=false means broker-held subscriptions persist indefinitely with no TTL on queued commands — the sibling's anti-persistent-session argument), and no disconnect callback (#211 — so disconnect detection is via poll() Err, which the supervisor pattern already handles).

Against the supervisor spec: rumqttc 0.24.0 supports every primitive that spec needs — ConnAck visibility via `Event::Incoming(Packet::ConnAck)` (both v4 eventloop.rs:469 and v5 eventloop.rs:406 emit it on every connect), `disconnect()` for SIGTERM-offline-then-disconnect, `clean()`-preserved QoS≥1 replay for the cap-0 rendezvous pattern, subscribe-before-connect safety via the bounded channel, and stable client_id + clean_session=true defaults. The alternative (Paho) is not better where it matters: same application-owned re-subscription, plus a C-toolchain dependency that is a real cost on NixOS fleet builds, plus a callback model that is thread-oriented rather than poll-loop-oriented (the rumqttc poll model is what makes the "supervisor owns lifecycle on ConnAck" design natural). rumqttc's tokio-native architecture matches the agent's existing tokio stack exactly. The upgrade to 0.25.1 is measured-zero-friction but buys nothing the supervisor needs (v5 session_expiry_interval is the only relevant delta, and the v5 module exists in 0.24.0 anyway); upgrading for its own sake has no payoff and small regression surface risk.

## Committed position

The evidence adds up to: **keep rumqttc, pinned at 0.24.0 for now, and stop waiting for upstream — the ConnAck-driven supervisor the sibling spec mandates is the only fix rumqttc will ever get, and the pinned version already supports it fully.** The load-bearing reason: both rumqttc and its only credible alternative leave re-subscription to the application (PR #1052 explicitly keeps it there; Paho's reconnect callbacks require the same application-side re-subscribe), so the "switch clients to get reliability" premise is false — the reliability work is application-side in every client, and rumqttc 0.24.0 already exposes every primitive the supervisor spec needs (per-connect ConnAck events in both v4 and v5 paths, disconnect(), clean()-preserved QoS≥1 replay, bounded-channel subscribe-before-connect). The v3.1.1 lock-out claim in the locus is factually wrong for 0.24.0 — the v5 module with message_expiry_interval and session_expiry_interval ships inside the pinned version, so the workarounds the spec designed around missing v5 features become optional hardening rather than forced; the spec's clean_session=true + stable client_id verdict stands regardless, because on the v4 path there is no session expiry to bound replay (and PR #1052 is open, unreviewed, v5-only — no signal event will arrive in the pinned version, making the poll loop's raw ConnAck match mandatory). Upgrade posture: do NOT churn to 0.25.1 now (measured zero code change but zero relevant delta; 0.25.1's only headline is a WebSocket fix the agent doesn't use); revisit only when a release actually ships #1052/#250-style reconnect signalling or the agent adopts the v5 module, at which point the bump is verified painless. Concretely: phase-1 reliability work should proceed on 0.24.0 with a ConnAck-matching poll loop (`Ok(Event::Incoming(Packet::ConnAck(_)))` → re-subscribe all command topics + republish availability "online" retained), cap-0 or timeout-bounded rendezvous publishes, and SIGTERM offline-then-`disconnect()` — none of which requires touching the dependency pin.

- **Position:** Keep rumqttc 0.24.0 (do not switch to Paho, do not churn to 0.25.x yet); build the ConnAck-driven supervisor on it — re-subscription will never come from the library (PR #1052 open/unreviewed/v5-scoped and even it only adds a signal), the pinned version already ships the v5 module (message_expiry_interval, session_expiry_interval) the locus thought was locked out, and the only alternative (Paho) has the same application-owned re-subscription plus a C toolchain cost on NixOS.
- **Confidence:** high (>80%) on the core verdict — the keep decision, the "no release fixes re-subscription" fact, and the 0.24.0-has-v5 discovery are all verified against primary sources (release notes, PR page, docs.rs version-specific pages, and the actual crate source on disk) plus a measured check/test/clippy pass. Medium on the sub-judgement that 0.25.1 should be skipped rather than taken now: the upgrade is measured painless, so the counter-position ("take the free bump for maintenance hygiene") is reasonable; my skip recommendation rests on zero-relevant-delta plus changelog-risk reasoning, not measurement.
- **Boundary conditions:** this verdict holds for a tokio-based Rust agent on a mosquitto broker at jupiterOS fleet scale (tens of hosts, kiosk + server classes). It would NOT hold if: (a) the agent needed MQTT v5 features on the *v4 default surface* without a module switch (then 0.25.x's MqttOptions v5 additions or a client switch matter); (b) a hard requirement emerged for callback-style disconnect notification (#211) that cannot be met by poll-Err handling — Paho's `set_connection_lost_callback` would then have an edge; (c) the fleet moved to a non-tokio runtime (Paho's runtime-agnosticism would matter); or (d) rumqttc goes genuinely unmaintained (no release for 12+ months — at ~3 releases/6mo currently, this is not the state today).
- **What would change this position:** (1) a merged+released #1052 (or any release note mentioning re-subscription) would make the raw-ConnAck match replaceable with `Event::Reconnect` and would trigger the 0.25.x+ upgrade — but would not change the keep verdict, since the merged design still leaves subscriptions application-owned; (2) evidence that Paho's offline buffering + auto-reconnect materially reduces application code on NixOS (e.g. a maintained nixpkgs Paho C + Rust packaging path with no friction) would reopen the client-switch question; (3) discovery that the v5 module in 0.24.0 is broken for subscribe flows in practice (the corpus shows it exists, not that it's battle-tested — no evidence either way on real-world v5 subscribe behaviour) would weaken the "v5 is a module switch away" claim and push toward 0.25.x where v5 got session-expiry attention; (4) a jupiterOS decision to adopt MQTT v5 end-to-end (HA + broker + agent) would flip the recommendation to "bump to 0.25.1 first, then adopt the v5 module", since 0.25.0's v5 session work is where upstream attention is.
- **Evidence weight:** 4 primary-source GitHub/docs.rs fetches (releases, PR #1052, 0.24.0 crate root + Event enum, 0.25.1 AsyncClient) + 3 alternative-comparison sources (Paho README, Paho AsyncClient docs, Paho releases) + direct source greps of the pinned crate on disk (v5 module existence, ConnAck emission in both eventloops, unimplemented! reachability analysis) + 1 measured build/test/clippy pass at 0.25.1 — all support KEEP; the corpus's 2 issue notes (#250, #211) support "alive but the warts are permanent design"; nothing contradicts keep except the locus's own "v3.1.1-only" premise, which the on-disk source refutes.

## Open questions

- Is rumqttc's v5 module battle-tested for subscribe flows in production? The corpus proves it exists in 0.24.0 with full v5 property support, but no source speaks to its real-world maturity; if jupiterOS ever adopts MQTT v5 end-to-end, a spike test (v5 module + mosquitto v5 + HA v5) should precede commitment.
- Would the rumqttc maintainers take a v4-scoped #1052-equivalent PR from this project? Filing one (the PR author himself says "the same fix applies to v4") is a low-cost upstream play that would give the agent an `Event::Reconnect`-shaped hook on the v4 path — worth a follow-up action item even under the keep verdict.
- Paho on NixOS: what does the paho-c + paho.mqtt.rust packaging story actually look like in nixpkgs today? If it's clean, the C-toolchain objection weakens (though the same-owned-resubscription fact still keeps rumqttc ahead for this codebase).
- rumqttd (the broker sibling) fixed "session present flag in CONNACK packets" and "event ordering returned on poll()" only in the 0.20.0 generation — is there any chance the rumqttc 0.25.0 "Improved event ordering in poll()" note fixed an ordering bug the agent's poll loop would notice? Nothing in the notes suggests the agent is affected, but the changelog line is uncharacterised upstream.
- The mosquitto side: the sibling spec pairs the client fix with broker config (max_queued_messages 8192, persistence true). My locus confirms client-side adequacy but the broker sizing remains the sibling's extrapolation from a single HA incident — a fleet-scale measurement would firm it up.
