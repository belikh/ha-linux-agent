# Two Located Bugs and a Fleet: Fixing ha-linux-agent for Every Host in jupiterOS

**The answer first.** ha-linux-agent's reputation for being "never reliable" is not a vague aura of sloppiness — it resolves to two precisely located bugs in one 198-line file, amplified by three default-shaped traps, and the presenting symptom is live right now: all four TCxWave kiosks read UNAVAILABLE on callisto's Home Assistant instance at this moment [[interim-report-mqtt-lifecycle-supervisor-spec]]. The agent subscribes to its command topics exactly once in a fire-and-forget setup task (`crates/core/src/agent.rs:134-138`) and swallows every connection acknowledgement in its poll loop (`Ok(_) => {}` at `agent.rs:190`), so after the first broker restart or network blip the client reconnects forever but never re-establishes subscriptions — every agent fleet-wide goes permanently deaf [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]]. The mirror-image bug publishes retained availability "online" exactly once (`agent.rs:139-144`), so after the same blip every host reads dead in HA while its telemetry still flows. The cure is a ConnAck-driven supervisor (re-subscribe, re-assert availability, birth-triggered rediscovery on every connect), it is implementable on the pinned rumqttc 0.24.0 with zero dependency churn, and it is the same disease the incumbent Windows agent shipped and fixed in a patch release [[releases-hass-agenthassagent-github]]. The correct course is ordered and non-negotiable: fix reliability first, deploy fleet-wide second (one system service per host, a role-driven NixOS module replacing the kiosk-only wiring), add features third. Adoption is the wrong move — the fleet's deciding features are exactly what no incumbent can express — and the strongest case for adoption is engaged at full strength below and answered on evidence.

## 1. Current State: A Verified Reliability Audit

An audit is only worth its ground truth, so this one reads the repository itself: measured build, test, and lint exit codes, file:line reads, and the fleet's own NixOS configurations. The workspace is twelve crates, eleven commits, 43 files, 278 symbols, with a 198-line `Agent::run()` at its centre that is a test-hostile monolith, and `backend-hardware`, `core/src/config.rs`, and `backend-gamescope` at the top of the reference graph [[repo-map-ha-linux-agent]]. Three structural findings define the "sloppy state" precisely.

**The reliability defects are located, not diffuse.** Nine defects, each with file:line evidence [[interim-report-mqtt-lifecycle-supervisor-spec]]:

| Defect | Location | Failure mode |
|---|---|---|
| Deafness after reconnect | `agent.rs:134-138` subscribe-once; `agent.rs:190` ConnAck swallowed | Agent reconnects but never re-subscribes; commands never arrive again |
| Availability stuck offline | `agent.rs:139-144` "online" published once; LWT retained "offline" at `agent.rs:55-60` | Host reads dead in HA while telemetry flows |
| No birth republish | absent | HA restart strands entities until manual re-send |
| Unbounded stale queue | `AsyncClient::new(opts, 64)` at `agent.rs:62` | Stale state replays as a burst on reconnect |
| Hung-backend starvation | `backend-syncthing/src/lib.rs:75,98` reqwest with no timeout; sequential polls at `agent.rs:154-157` | One hung daemon freezes every sensor on the host while availability says "online" |
| No graceful shutdown | zero signal-handling matches across `crates/` | A clean DISCONNECT silently discards the LWT; availability sticks "online" |
| Session and broker defaults unpaired | rumqttc defaults; callisto `mqtt.nix` sets neither `max_queued_messages` nor `persistence` | Clean sessions plus an amnesiac broker compound the deafness |

**The privilege workaround is not just ugly — it is broken today.** `jupiter-os/modules/services/ha-agent.nix:117-124` ships a root-owned oneshot that chmods backlight and cpufreq sysfs nodes 0664, behind a comment at line 112 claiming "io is in the groups that own the nodes (video for backlight…)". The comment is false: sysfs attributes default to `root:root 0644`, so `0664` grants group-write to group *root*, and io's only group anywhere in the fleet is `wheel` (`modules/common.nix:139` — no host adds io to `video`) [[interim-report-fleet-service-model-by-host-class]]. The agent's brightness, governor, and EPP writes therefore fail EACCES today, logged only as a `warn!` in `write_sys_file` (`backend-hardware/src/lib.rs:108-111`), invisible at the HA layer — while the kiosks run `pollIntervalSecs = 1` on hardware whose control surface silently does not work. A user service carrying a system-level privilege crutch that does not even function is the definition of hand-waved infrastructure.

**The quality gates are absent, not merely failing.** The workspace contains eight test functions — three in `core/src/discovery.rs`, five in `backend-launcher/src/lib.rs`, all pure shape and regression guards, zero on any hardware, D-Bus, or MQTT-touching path — but the flake's checks hold only `buildPackage` and `cargoClippy --all-targets -- --deny warnings`: no `craneLib.cargoTest` entry exists, so zero of the eight tests ever run in any gate [[interim-report-testing-gate-for-hardware-daemon]]. Clippy is red right now — the `unnecessary_map_or` family at `backend-hardware/src/lib.rs:117` fails `--deny warnings` — so the observed exit codes are 0 (build), 0 (test, only because nothing runs), and 101 (clippy): `nix flake check` cannot go green before a one-line fix [[interim-report-testing-gate-for-hardware-daemon]]. There is no `.github/` directory; there is no CI at all. A dead `tls` knob sits in `config.rs:88` unwired to anything, the README has drifted (backend-hardware ships undocumented; the zfs, syncthing, and lutris backends carry the repo's own "Unverified in a live environment" flags), and the hardware backend exposes placeholder select options rather than values enumerated from sysfs [[interim-report-adopt-vs-build-honest-verdict]].

**The fleet coverage fact.** The agent runs on four of six hosts — the four TCxWave kiosks (amalthea, adrastea, metis, thebe) via `tcxwave-kiosk.nix` — while callisto deliberately opts out (its arcade-console config strips the agent wiring), europa runs nothing despite backend-zfs, backend-syncthing, and backend-headscale existing for exactly that host, "Every host" is an ambition the fleet's own configuration currently contradicts.

The distribution of the defects is the strategic fact. They cluster in the lifecycle core every host class shares — `agent.rs` and the config plumbing — while the per-backend surfaces are small, self-contained crates of 100–330 lines behind two traits [[interim-report-adopt-vs-build-honest-verdict]]. A flat audit reads this list and says "prototype, replace it"; the precise reading is that fixing `agent.rs` lifts kiosks, servers, and future desktop hosts simultaneously, which no incumbent substitution can deliver.

## 2. The MQTT Lifecycle Problem: Why It Is Never Reliable

MQTT (a lightweight publish/subscribe protocol) is the agent's entire nervous system: Home Assistant learns about entities through discovery messages the agent publishes, tracks whether each host is alive through an availability topic, and sends commands back over subscribed topics. Two properties make or break this arrangement: the broker (the MQTT server, here mosquitto on callisto) forgets clean-session clients on every reconnect, and Home Assistant marks an entity unavailable until a payload actually arrives on its availability topic — fresh state alone never flips it back [[mqtt-home-assistant]]. The agent's connection lifecycle is driven from the wrong place entirely, and that one structural error produces every reliability symptom the fleet has felt.

**The library contract that decides everything.** rumqttc's poll loop reconnects unconditionally — "Continuing to poll will reconnect to the broker if there is a disconnection" — and the crate advertises "Automatic reconnections by just continuing the eventloop.poll()/connection.iter() loop", with re-subscription conspicuously absent from its own feature list [[eventloop-in-rumqttc-rust]] [[rumqttc-rust]]. Reconnection is not re-subscription. Issue #250, open since February 2021 and still labelled in-pipeline, documents the footgun precisely: after a reconnect with a clean session, "I'm not seeing any data coming in from subscribed topics", because subscriptions live only in broker-side session state, which a clean session destroys on every reconnect [[automatic-reconnect-and-subscribed-topics-issue-250-bytebeamiorumqtt-github]]. The in-pipeline fix, PR #1052, is open, unreviewed, v5-scoped, and — decisively — only emits a reconnect *signal*; its own caller pattern re-subscribes in application code, so subscription ownership stays with the application even if it merges [[interim-report-rumqttc-dependency-fitness]]. The alternative client, Paho, exposes rich reconnect callbacks but leaves re-subscription application-owned too, and drags a C toolchain dependency onto every NixOS fleet build [[asyncclient-in-paho_mqttasync_client-rust]] [[github-eclipse-pahopahomqttrust-pahomqttrust-github]]. No source announces "the supervisor must live in the application forever", but the rumqttc PR design (signal-only) and the Paho callback surface (application re-subscribes) jointly imply exactly that. Waiting for upstream saves nothing; a client switch buys nothing.

**The two bugs, mechanically.** rumqttc's defaults are `clean_session=true`, keepalive 60 s, inflight 100 [[librs]], and callisto's mosquitto sets no `persistence`, so the mosquitto default applies — connection, subscription, and message data "stored in memory only" — meaning every broker restart wipes all sessions fleet-wide [[mosquittoconf-man-page-eclipse-mosquitto]]. Combine that with subscribe-once and the swallowed ConnAck: the first mosquitto restart, HA restart with a broker drop, or network blip permanently deafens every agent. The poll task keeps publishing state — telemetry flows, dashboards look half-alive — but no command will ever arrive again. Then the mirror image fires: the broker correctly publishes the retained "offline" last will (LWT — the message a broker publishes when a client vanishes ungracefully) on the ungraceful disconnect, and the agent never re-publishes "online" after reconnecting, so the retained availability topic permanently reads "offline" while state flows normally [[interim-report-mqtt-lifecycle-supervisor-spec]]. The community's step-by-step demonstration of this trap — publish state, sensor stays unavailable; publish availability, sensor appears — is the failure mode in miniature [[mqtt-discovery-availability-home-assistant-os-home-assistant-community]]. Users read the two bugs together as "the agent is broken", because it is.

**The HA-side contract the agent does not honour.** HA's MQTT integration is explicit: "A device or service that exposes the MQTT discovery should subscribe to the Birth message and use this as a trigger to send the discovery payload. To avoid high IO loads on the MQTT broker, adding some random delay in sending the discovery payload is recommended" — HA publishes `online` to `homeassistant/status` on startup, and all discovered entities sit unavailable until a discovery message is processed [[mqtt-home-assistant]]. Retained discovery alone is necessary but not sufficient. HA issue #135266 shows the mechanism at scale: at 5,374 entities the broker's per-client queue overflowed during HA's startup retained replay and silently dropped messages — 56 of 112 affected topics arrived empty while MQTT Explorer showed them present on the broker, and the reporter's cure was "I have raised the allowed maximum number of queued messages on my broker" [[some-mqtt-devices-unavailable-after-ha-restart-issue-135266-home-assistantcore-g]] [[comments]]. The older issue #38661 shows the same stranded-entity class ending in manual delete-and-rediscover: "A lot of my MQTT sensors are unavailable after a restart. The solution to get them back is to delete the entity, and resend the discovery message" [[mqtt-sensors-unavailable-in-01140bx-others-stay-unknown-issue-38661-home-assista]]. The queue mechanics are per-client — mosquitto's `db__ready_for_queue` counts each client's queued messages against `max_queued_messages` (default 1000), and for a disconnected client the in-flight adjustment zeroes, making the full queue depth available to offline replay [[databasec]]. This is the one place the corpus genuinely disagrees with itself, and the resolution is conjunctive rather than either-or: retain everything (config, state, availability — the Zigbee2MQTT/ESPHome posture), AND republish on birth and ConnAck with jitter, AND persist and size the broker. Retention without republish strands entities when replay drops; republish without retention strands them when the broker forgets [[mqtt-client-component-esphome-smart-home-made-simple]] [[device-availability-zigbee2mqtt]]. One calibration keeps the sizing honest: at the fleet's measured ~25 agent entities per host, the default queue of 1000 never binds — the binding quantity in #135266 was HA's own `#`-wildcard client against broker-wide retained replay — so the broker work is cheap hygiene plus a confirmation check reading `$SYS/broker/publish/messages/dropped` (not the never-published `$SYS/broker/mqtt/*` variants, which mosquitto 2.1.2's source explicitly excludes) rather than urgent resizing [[documentation-on-sysbrokermqtt-topics-is-wrong-issue-3726-eclipse-mosquittomosq]] [[no-data-in-sysbrokermessagesinflight-issue-3021-eclipse-mosquittomosq]]. The load-bearing half is `persistence true`, because every broker restart still wipes sessions, which is why the ConnAck re-subscribe is mandatory regardless of queue arithmetic.

**The aggravators that make telemetry lie.** The request channel capacity of 64 at `agent.rs:62` contradicts rumqttc's own recommendation to set capacity 0 when managing pending state — during an outage, up to 64 stale messages queue and replay as a burst [[rumqttrumqttcsrceventlooprs-at-main-bytebeamiorumqtt-github]]. Worse is the starvation defect: `backend-syncthing` builds its reqwest client with no timeout (reqwest has none by default), and `Agent::run` polls all backends sequentially in one task, so a single hung syncthing daemon freezes every sensor on the host while availability still reads "online" — sensors that lie rather than sensors that vanish, the worst failure class a fleet can carry [[interim-report-mqtt-lifecycle-supervisor-spec]]. The shutdown path is an accident waiting to happen: the broker discards the stored LWT on a graceful DISCONNECT, so the current SIGTERM behaviour "works" only because the process dies ungracefully and the TCP close fires the will — the day anyone adds a clean shutdown that sends DISCONNECT without first publishing "offline", availability sticks "online" forever. ESPHome solves exactly this with a dedicated `shutdown_message` distinct from the will [[mqtt-client-component-esphome-smart-home-made-simple]].

**The supervisor spec.** One structural change: drive the lifecycle from the poll loop's ConnAck event. On every `ConnAck` — first connect or reconnect, either `session_present` value — re-issue all command-topic subscribes (idempotent; subscribe-before-connect is safe because requests buffer in the bounded channel until post-ConnAck) and re-assert retained availability "online" [[rumqttrumqttcsrceventlooprs-at-main-bytebeamiorumqtt-github]]. Subscribe to `homeassistant/status` and republish all discovery configs with 0–30 s per-host random jitter on HA's birth, following the production reference: Zigbee2MQTT's availability machinery applies `Math.random() * max_jitter` with a 30 s default, ×1.5/×3/×6/×12 backoff, retained QoS 1 availability, and dedup of consecutive identical states [[availabilityts]] [[device-availability-zigbee2mqtt]]. Set channel capacity 0 with per-tick publish timeouts so staleness is bounded to one poll interval — and because all state lands on one retained topic per host, a fresh publish overwrites any stale payload: staleness self-heals by construction. Wrap every backend poll and every command handler in `tokio::time::timeout`, dispatch commands via `tokio::spawn` with 5 s HTTP timeouts (rumqtt's standing rule: "Don't block this while iterating"), handle SIGTERM by publishing retained "offline", awaiting it, then `disconnect()` — which the pinned 0.24.0 ships — and add a `--decommission` mode publishing zero-length payloads to every owned topic, HA's official removal semantic [[interim-report-mqtt-lifecycle-supervisor-spec]]. Reconnect backoff runs 1→60 s with ±20 % jitter so a broker restart cannot synchronise seven hosts into a reconnect stampede.

Two boundary judgements deserve their conditions named. First, `clean_session = true` (explicitly, with a stable client id) rather than the persistent-session instinct: a persistent session's only unique deliverable here is broker-side queueing of QoS 1 commands for an offline agent, and the kiosks power off overnight — a week-old launcher toggle or reboot command replaying as fresh on Monday boot, with no TTL available in v3.1.1 (issue #211 has been open and labelled stale since December 2020) and no timestamp in the payload to age it by, is a real hazard no source states directly but the kiosk overnight-off pattern and rumqtt's documented lack of any pending-message TTL jointly imply [[rumqttc-reconnection-to-mqtt-broker-and-pending-messages-ttl-issue-211-bytebeami]]. Always-on servers lack the hazard and gain nothing from session state given ConnAck-driven re-subscribe, so the design is unconditional. Second, a premise correction that strengthens the design: the pinned 0.24.0 is *not* v3.1.1-locked — `src/lib.rs:113` declares `pub mod v5;` with full property support inside the pinned version, so the v5 escape hatch (message expiry, session expiry) is a module switch away, a named future option rather than the reason for any workaround [[interim-report-rumqttc-dependency-fitness]]. The upgrade to 0.25.1 was actually run — check, test, and clippy all exit 0 with zero code changes — and reverted, because it buys nothing the supervisor needs; the method-for-method-identical public API across the two versions is itself the evidence the bump is cosmetic for this codebase [[interim-report-rumqttc-dependency-fitness]].

The precedent that makes this credible rather than speculative: the incumbent Windows companion shipped the identical bug class and fixed it in a patch release — HASS.Agent 2.1.1: "MQTT autodiscovery messages were not republished after connection was lost and recovered" (#230), alongside rename-triggered discovery-removal failures (#376, #388) and an entire sensor class stopping on a WMI restart (#205) [[releases-hass-agenthassagent-github]]. Reconnect-deafness is the generic companion-agent disease; the difference is that this instance is diagnosed to the line and has a spec.

## 3. What a Proper Linux Agent Looks Like: The Comparison Set

"Proper Linux agent" is defined by the 2026 companion-agent ecosystem, not by this repository's current self. The comparison set divides into companion-class agents — HASS.Agent on Windows, go-hass-agent and lnxlink on Linux, the mobile apps — and monitoring-class stacks like Glances, Telegraf, and Netdata, which the next section eliminates. The bar a proper agent must clear has four axes, and the incumbents set them high.

**The sensor bar.** go-hass-agent (v14.15.1 of 2026-08-09, packaged in nixpkgs proper for all 24 Linux platforms, roughly monthly cosign-signed releases) sources its Linux surface from D-Bus (logind sessions, power state, screen lock, NetworkManager, XDG portal, UPower, MPRIS, fwupd), ProcFS (memory, disk, load, per-core CPU usage and frequency, uptime, kernel, CPU vulnerabilities), SysFS (disk I/O rates, hwmon), and Netlink (link states and rates) [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]] [[go-hass-agent-mynixos]]. Its recent cadence is the depth evidence: v14.15.1 fixed a concurrent map-read data race in the CPU usage worker, v14.15.0 added NVIDIA and AMD GPU memory sensors, v14.10.3 fixed ddcutil backlight detection [[releases-joshuargo-hass-agent-github]]. lnxlink's ~50 modules span idle-time, media control with metadata, brightness, fullscreen detection, screenshot streaming, audio-device selection, systemd unit management, GPU usage, restart-required and pending-updates tracking, WOL, BeaconDB location, and in-use sensors for mic, speaker, camera, and gamepad [[lnxlink]] — the fullest desktop envelope of any Linux agent. The mobile companion documentation contributes the canonical "companion" vocabulary — battery, connection, storage, frontmost app, active camera and audio, displays, media session [[sensors-home-assistant-companion-docs]]. By sensor count, ha-linux-agent today is roughly a quarter of go-hass-agent's generic surface, and that concession stands on the record.

**The control bar — where the comparison inverts.** The contract that matters for kiosks is not sensor breadth but controls whose state genuinely synchronises and entity shapes richer than buttons. Here the incumbents fail on their own documentation. go-hass-agent's `commands.toml` vocabulary is button, switch, and number only, and its README states plainly: "States are not kept in sync. This is most important for all controls besides buttons. For example, if you configure a switch, any changes to the state you make outside of Home Assistant will not be reflected in Home Assistant automatically" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. Its users hit the wall in January 2026, when a PipeWire output-device selector "can't be expressed" because the commands vocabulary has no dropdown [[go-hass-agent-a-native-app-integration-for-desktoplaptop-devices-share-your-proj]]. jupiterOS's kiosk session-switching requires a select whose options reflect real systemd unit state — grouped launcher profiles become one mutually exclusive select, with the shared state topic reshaping through discovery — a control vocabulary the incumbent architecturally lacks. lnxlink ships dropdowns (a Steam game-launcher select among them) and systemd unit control, but no mutual-exclusion semantics and no state round-trip tied to fleet power services [[lnxlink]].

**The identity and notification bars.** go-hass-agent is dual-transport by mandate — it registers via the mobile_app native API ("Go Hass Agent cannot run in an MQTT-only credentials [mode]") with an optional MQTT v5 side, and documents the consequence itself: sensors and controls land as two HA devices that "cannot be combined in a single place" [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. A single-device MQTT-only identity is not a cosmetic preference; every dashboard and automation targeting a kiosk sees one coherent device. On notifications, HA 2024.5 shipped a native MQTT notify entity platform — PR #115653, Quality Scale gold, "notify" sitting in the mqtt integration's `SUPPORTED_COMPONENTS`, with an upstream test publishing the working two-field discovery payload `{"name": "test", "command_topic": "test-topic"}` — giving an MQTT-only agent a first-class `notify.<device>` service, strictly better than the current raw-button payload hack, and implementable today [[add-mqtt-notify-platform-by-jbouwh-pull-request-115653-home-assistantcore-github]] [[corehomeassistantcomponentsmqttconstpy-at-dev-home-assistantcore-github]] [[test_notifypy]]. The platform is one-way — command topic plus optional template, no actions schema, no event round-trip [[mqtt-notify-home-assistant]] — but the honest comparison shows no Linux agent implements the action round-trip anywhere: HASS.Agent on Windows remains the gold standard with its `hass_agent_notifications` event round-trip [[actionable-notifications-hassagent]] [[home-hassagent-documentation]], while go-hass-agent's requests for actionable notifications (#667, December 2025) and clear_notification support (#926, August 2026) sit open with zero maintainer engagement [[interim-report-adopt-vs-build-honest-verdict]]. Going MQTT-only sacrifices almost nothing the ecosystem actually delivers.

**The transport question, resolved on scope.** A long-time HA contributor's objection deserves full strength: "Could you clarify your reasoning behind going through MQTT for influxdb injection? Seems an unnecessary point of failure to me. I go directly from telegraf to influxdb, then use the influxdb integration inside HA" [[system-design-architecting-ha-data-flows-with-telegraf-mqtt-influxdb-and-grafana]]. That is correct for a DB-centric time-series pipeline and irrelevant to this fleet: jupiterOS runs no InfluxDB and wants automations, dashboards, and kiosk *control* — the bidirectional case MQTT natively provides. The counter-architecture concedes the point from the inside: halinuxcompanion, the one native-API Linux agent, lists "Move sensors to MQTT" on its to-do because the native API leaves sensor values "stuck" when a host goes offline, whereas an MQTT last-will reflects it [[github-muniterhalinuxcompanion-homeassistant-linux-companion-github]]. The community thread that best captures the demand signal ends the same way — a moderator answering "there is no Windows and Linux HA app" with the monitoring-class shelf (glances, netdata, system bridge), while the original poster's "I personally hate mqtt" draws the correction that "most features rely on it for bidirectional communication" [[wth-there-is-no-windows-and-linux-ha-app-similar-to-macos-month-of-what-the-heck]]. The moment you want control rather than readout, the ecosystem routes you to MQTT. If long-horizon metric history ever becomes a requirement, Telegraf-to-database belongs alongside the agent, not instead of it.

| Axis | ha-linux-agent | go-hass-agent v14.15.1 | lnxlink | HASS.Agent (Windows) |
|---|---|---|---|---|
| Transport / identity | MQTT-only, one device per host | mobile_app + MQTT v5; two devices, "cannot be combined" | MQTT-only | MQTT, one device |
| Sensor surface | sysinfo CPU/memory/disk/load/uptime, logind idle/locked, UPower (~25 % of go-hass) | D-Bus/ProcFS/SysFS/Netlink catalogue, SMART, GPU, OOM events | ~50 desktop modules | Windows WMI surface |
| Control model | select with state round-trip; launcher mutual-exclusion groups | button/switch/number, "States are not kept in sync" | selects per module, no mutual exclusion | commands; "just using Button for most commands" recommended |
| Notifications | notify.mqtt entity (one-way) | one-way; actionable open, maintainer-silent | rich desktop notify | actionable round-trip (gold standard) |

The comparison set does not show a better agent to adopt. It shows that the companion class's definitional features — single identity over MQTT discovery, controls whose state syncs, headless operation — are exactly the axes where the incumbents are weakest and this architecture is already right. The proper-Linux-agent question is not which crate has the most sensors but which architecture can express the fleet's control plane; the sensor deficit is real, quantified, and addressed by the roadmap rather than denied.

## 4. The Build-vs-Buy Dialectic: Custom Rust Agent vs Telegraf, Glances, and Netdata

Build-versus-buy here has two forks: buy a monitoring stack for the hosts, or buy a companion agent. The monitoring fork dies on audited evidence quickly; the agent fork deserves its strongest case at full strength before the verdict.

### A. The case for adoption, stated as strongly as the evidence allows

go-hass-agent v14.15.1 is one `environment.systemPackages` line away on every host — verified in nixpkgs proper, not broken, not unfree, building for all 24 Linux platforms, maintained by two nixpkgs maintainers on a roughly monthly cosign-signed cadence with 3,909 commits of sensor and hardware polish [[go-hass-agent-mynixos]] [[releases-joshuargo-hass-agent-github]]. Its maintainer explicitly designs the systemd path for servers ("The systemctl service is primarily for 'headless' usage (i.e., servers)"), its changelog shows it paying the MQTT lifecycle dues in public — "reconnect to MQTT on disconnect and fix issue with MQTT commands not working", graceful channel shutdown, constant device ids — and it carries SMART with capability handling, per-core frequencies, network link rates, OOM events, fwupd firmware security [[changelogmd]] [[github-joshuargo-hass-agent-a-home-assistant-native-app-for-desktoplaptop-device]]. lnxlink covers the desktop long tail with ~50 modules, including a Steam game-launcher dropdown and a bash-command module that creates sensors, buttons, and switches from shell scripts [[lnxlink]]. Against that maturity stands a twelve-crate workspace with eleven commits, eight tests that never run, a red lint gate, verified reconnect deafness, and three backends self-flagged "Unverified in a live environment" — a prototype, not a foundation. And the sharpest form of the objection: the launcher mutual-exclusion select is one bash module away, because the mutual exclusion already lives in the systemd units and polkit rules jupiter-os owns — the backend is "a systemd-and-polkit design wearing a Rust backend as a coat", a relay, and relays are commodities [[interim-report-adopt-vs-build-honest-verdict]] [[repo-map-ha-linux-agent]]. The maintenance arithmetic clinches it: improving means one solo maintainer re-deriving, on a single-machine budget, a reliability curriculum every incumbent burned years of multi-contributor production reports to learn — while standing on a library whose own reconnect bug has been open five-plus years. Even the split-brain price is arguable: a split identity that works beats a unified identity that does not.

### B. Why the evidence refutes it

The packaging counter first. "One bash module away" carries a heavy deployment cost on this fleet: lnxlink is not in nixpkgs at all, and its Python dependency surface — pygobject3, ewmh, xlib, opencv-python, pulsectl, pyalsaaudio, docker, speechrecognition in one propagated list — is exactly why a 2025 packaging attempt failed and no one has upstreamed a module [[python-packaging-error-needs-specific-setuptools-version-nixos-discourse]]. go-hass-agent is packaged as a *binary* but has no NixOS service module: a full-text pass over module-list.nix returns zero occurrences of either incumbent, while the home-automation directory hosts home-assistant, esphome, zigbee2mqtt, zwave-js, matter-server, govee2mqtt, evcc, ebusd, and homebridge [[module-listnix]]. Adoption therefore means writing the module anyway, plus inheriting the split-brain, then building the launcher/session layer as configuration glued around an agent that does not natively model it.

Second, the expressibility record. go-hass-agent's complete changelog from v4.3.1 through v14.15.1 contains zero occurrences of select entities, MQTT control state synchronisation, or NixOS support — the gaps persist through the current era [[interim-report-adopt-vs-build-honest-verdict]] [[changelogmd]]. The mechanism-versus-surface decomposition is conceded in full: the mutual exclusion lives in fleet-owned systemd units and polkit rules, and would survive any adoption. But the *entity surface* — the typed, declarative select generated from `jupiter.services.haAgent.launcherApps`, the state round-trip through the shared state topic, the per-profile binary sensors — is agent-owned differentiation, regression-tested in this repo, and inexpressible in a commands-file vocabulary whose own documentation disclaims state sync. A mutual-exclusion group whose whole point is that the compositor's real session state, not HA's last command, is the truth cannot be backed by a control model that never learns out-of-band changes. The unsynced-switch problem is a dashboard annoyance on an incumbent; on a kiosk session switcher it is a wrong-state machine.

Third, the reliability provenance argument inverts on inspection. The incumbent's public fix history proves the bug class is generic, not that the incumbent is immune for this fleet's shape: adopting go-hass-agent means inheriting two devices per host, unsynchronised controls, an MQTT v5 broker requirement, and manual command-line registration — configuration and polish problems, admittedly — while the custom agent's problems are existence problems, admittedly worse today but precisely scoped to two lines in one file, with a specification already written. "A split identity that works beats a unified identity that doesn't" is the strongest sentence in the objection, and it is time-bound: the unified identity stops not-working the moment the ConnAck supervisor lands, which is days of work, not a research programme.

Glances is Home Assistant's own documented monitoring path, and its record is a six-year cautionary tale: sensors renamed with `_2` suffixes after every restart ("This renaming is undone if I remove then re-add the integration... until the next restart. Telegraf's MQTT output plugin is real and current — protocols 3.1.1 and 5, QoS control, retain flags, homie v4 layout — but it emits measurement topics, not HA discovery payloads; making entities appear requires telegraf2hassio-style hub-side glue that subscribes to `telegraf/#` and re-publishes as discoverable sensors, putting the discovery logic on the far side of a translation shim [[telegrafpluginsoutputsmqttreadmemd-at-master-influxdatatelegraf-github]] [[hassio-addonstelegraf2hassio-at-master-joaoflhassio-addons-github]]. Netdata is the strongest monitoring product and the worst per-hardware-class fit, and here the corpus genuinely disagrees: the vendor prices the default agent at 100–200 MB RAM on an empty system (250–350 MB in typical production, ~4 GiB disk, 1–5 % of a core), while community deployments report 200–1000+ MB ("From 200-400 MB for regular servers to 700-1000+MB for kvm hypervisors. USED memory. And that's just in a single month") and the maintainer-endorsed production recipe disables most of the product — alloc mode, ML off, health off — to fit edge hosts [[resource-utilization-netdata-agent-learn-netdata]] [[insane-netdata-memory-usage-help-netdata-community-forums]] [[agent-performance-optimization-guide-configuration]]. Both sides are right in scope: the official figures describe an empty system, the community figures metric-heavy reality, and the per-metric cost model (16 KiB per unique metric; 26 KiB per actively-collected metric on a parent) explains the divergence [[ram-utilization-resource-utilization-learn-netdata]]. For TCxWave-class kiosks the *effective* Netdata is the stripped one — at which point a purpose-built agent is the lighter choice before any feature argument begins. node_exporter is eliminated by direction: HA's Prometheus integration exposes HA entity metrics to an external scraper; it does not ingest host metrics into entities [[prometheus-home-assistant]].

The concession table stays on the record, because improve-don't-adopt is only honest with costs named: ~25 % of go-hass-agent's sensor coverage; eight test functions against 3,909 commits; three backends carrying the repo's own unverified-live flags; a notify path that is currently a payload-hack button rather than an entity. None of these is a reason to adopt. They are the scope discipline the roadmap must respect: fix the lifecycle, keep the sensor surface deliberately minimal per host class, and spend features only where jupiterOS actually consumes them. The verdict — improve, don't adopt — holds because the maintenance asymmetry only pays off when the differentiating layer is genuinely unbuildable upstream, which is true here precisely for the launcher select model and the server backends, and because the bespoke path's worst defects are already audited to the line, which is more than can be said for inheriting a split-brain and gluing around it.

## 5. NixOS Fleet Architecture: From Kiosk-Only to Every Host in jupiterOS

A NixOS host runs services in two shapes: system services, managed by the system manager and ordered against the network and each other, and user services, managed per-user and unable to order against system units "by design" [[what-is-the-difference-between-systemdservices-and-systemduserservices-help-nixo]]. The agent currently ships as a user service with linger (a mechanism that keeps a user manager alive without a login). In 2026, that boundary moved, and the fleet's design sits on the wrong side of it.

**The boundary redraw.** The old reason to retire user units was staleness — switches did not restart them. PR #517768, merged May 2026, made it worse: switch-to-configuration-ng now runs a full per-user switch for any user with an active manager, and the source confirms the mechanics — enumerate users via `logind.list_users()`, stat `/run/user/{uid}` as the liveness check (linger included), and for each live manager spawn a setuid child running daemon-reload plus stop/reload/restart passes with literal `restart_unit` calls [[switch-to-configuration-ng-harden-user-unit-migration-second-pass-by-r-vdp-pull]] [[mainrs]]. The regression fired on real fleets within days: users kicked out to GDM mid-switch as user-manager restarts collapsed `graphical-session.target` — a one-way teardown, since the target declares `RefuseManualStart=yes` — with one reporter hitting seven occurrences in 57 switches and session units stopping 150–730 ms after the daemon-reload, never to return [[anyone-seeing-nixos-rebuild-switch-kick-you-out-to-gdm-andor-log-gpf-errors-spec]]. So the user-unit shape now combines both failure modes: for lingered-but-not-logged-in users, changes wait for a reboot; for active users, switches tear sessions down mid-switch. For an appliance fleet, retire the shape entirely.

**The system-service design.** One `systemd.services.ha-linux-agent` per host, `User=io`, `Restart=on-failure`, `RestartSec=5s`, `After=network-online.target`, plus a `role` option — `kiosk | server | minimal` — driving mkIf branches for the host-class bits [[interim-report-fleet-service-model-by-host-class]]. The two facts that were supposed to force the user/system split both dissolved. Session-bus reachability: a `User=io` system service reaches the per-user bus at `/run/user/1000/bus` with two `Environment=` lines (`XDG_RUNTIME_DIR` + `DBUS_SESSION_BUS_ADDRESS`), because access control on the per-user bus is purely the socket's filesystem mode, and jupiter-os's own `mkSessionLauncher` already proves the pattern from the system side for cage sessions [[interim-report-fleet-service-model-by-host-class]] [[d-bus]]. Headless boxes without a session bus produce the "Failed to connect to bus: No medium found" ladder, which is precisely why the agent's generic backend already degrades to warn-and-disable where no session exists — correct behaviour on europa [[systemduser-archwiki]] [[openclaw-gateway-status-fails-on-ec2headless-servers-due-to-missing-user-level-s]]. Declarative linger (closing a nine-year gap in NixOS 23.11) stays useful for the cage sessions, not the agent — and the linger option's habit of disabling undeclared users' managers is a footgun worth remembering when it is enabled [[enabling-persistent-user-instance-systemd-issue-3702-nixosnixpkgs-github]] [[nixosusers-groups-add-user-option-to-enable-lingering-by-toxicfrog-pull-request]].

**The zero-capability privilege ladder — the design, not the fallback.** The strongest internal disagreement the investigation produced is direct: one committed position holds `AmbientCapabilities=CAP_SYS_ADMIN CAP_SYS_RAWIO` where SMART is enabled; the live-proven evidence is that every subsystem has an unprivileged channel, so the capability grant becomes the named, explicitly-rejected alternative [[interim-report-fleet-service-model-by-host-class]] [[interim-report-headless-privilege-ladder]]. The kernel capability matrix makes the stakes concrete: NVME_IOCTL_ADMIN_CMD requires CAP_SYS_ADMIN at the kernel level, and as the Scrutiny maintainer puts it, "there is nothing you can do except grant that" — the "new root" catch-all, to displace a daemon that already runs [[clarification-of-volume-permissions-issue-26-analogjscrutiny-github]]. The ladder, per subsystem:

- **SMART:** smartd `-M exec` hooks. smartd already runs privileged on europa at the fleet's chosen interval with scheduled self-tests; the hook receives the full event context via `SMARTD_MESSAGE`/`SMARTD_FAILTYPE`/`SMARTD_DEVICE` environment variables and hands it to the agent, which never touches the ioctl — inheriting smartd's scheduling and self-test logic for free, with the one man-page caveat that "smartd will block until the executable PATH returns", so the hook is fire-and-forget [[smart-archwiki]] [[smartdconf5-smartmontools-debian-testing-debian-manpages]]. The exporter shape — smartctl_exporter, root by design, 60-second polls — remains a per-host opt-in for sub-minute freshness no current host needs [[github-prometheus-communitysmartctl_exporter-export-smartctl-statistics-to-prome]].
- **ZFS:** `/proc/spl/kstat/zfs/<pool>/state` procfs reads — the node_exporter-proven unprivileged path, plain file opens, no /dev/zfs, no ioctl — for state polling, plus a zedlet as the push channel: ZED (the ZFS event daemon) is root-only and already auto-enabled on ZFS hosts, so it publishes *into* the agent's channel; `services.zfs.zed.settings` renders the configuration NixOS already ships [[interim-report-headless-privilege-ladder]] [[zed8in]] [[zfsnix]]. The current backend's shell-outs to `zpool list` are root-equivalent today; the rewrite removes an avoidable root requirement. Thresholds from the monitoring literature: capacity warn 80 %, critical 90 %; fragmentation 30/50; any non-ONLINE state as the binary_sensor problem [[how-to-monitor-zfs-pool-health-and-status-on-ubuntu]].
- **systemd unit health:** system-bus D-Bus match rules, live-proven on callisto — a logrotate timer's `JobRemoved` signal was delivered to an unprivileged io subscriber with zero polkit grants, alongside 27 PropertiesChanged signals in the same window, while unprivileged job *creation* remains correctly gated [[interim-report-headless-privilege-ladder]]. Two subtleties: Manager signals require an explicit `Subscribe()` call at startup (PropertiesChanged does not — a lazy-signals design), and the daemon shape has a production precedent in systemd_mon, which has subscribed "no polling, and no busy-loops" since the v204 era, queuing rapid intermediate transitions into one notified change [[github-joontysystemd_mon-monitor-for-systemd-to-alert-failed-services-github]]. The rejected alternative is the OnFailure drop-in pattern, which needs root-owned writes into `/etc/systemd/system/` [[see-also-3]].
- **Backlight:** raw sysfs writes (the ABI contract: `brightness` 0..max_brightness, `actual_brightness`, `bl_power` 0/4) with the broken chmod replaced by one udev `GROUP="video"` rule plus io-in-video membership — the fleet's own existing pattern for the customer-display hidraw nodes [[sysfs-class-backlight]] [[backlight-support-the-linux-kernel-documentation]] [[interim-report-fleet-service-model-by-host-class]]. The read side upgrades to push for free: the kernel emits a `KOBJ_CHANGE` uevent and a `sysfs_notify` on `actual_brightness` after every store attempt, hotkey path included, so the 1-second poll-everything default becomes event-driven plus a slow heartbeat [[interim-report-headless-privilege-ladder]].

Summed: no AmbientCapabilities, no sudo, no root anywhere in the fleet. The complete privilege surface is system-bus socket access, optionally the session bus via the Environment block, and the existing polkit rule pattern for the specific units the launcher may start/stop. Delete `ha-linux-agent-sysfs-perms` entirely — it grants group-root write that the only intended consumer cannot use.

**The rollout.** The module moves from the kiosk profile to common, role-switched:

| Host | Class | Agent today | Target role |
|---|---|---|---|
| amalthea, adrastea, metis, thebe | TCxWave kiosks | running, 1-second polling, broken backlight writes | kiosk |
| callisto | broker + arcade host | deliberately absent | kiosk/minimal — the broker host finally runs its own agent |
| europa | ZFS NAS, syncthing, headscale | absent despite the purpose-built backends | server (SMART hook, procfs ZFS, zed bridge) |

Secrets wiring is unchanged: sops-nix's system module decrypts to `/run/secrets` with per-secret owner and `restartUnits`, so `sops.secrets.mqtt_ha_linux_agent.owner = "io"` works identically for a system service. One live test — send a notification from HA to a `User=io` system service on a kiosk — retires the risk outright, and belongs in the roadmap's verification checklist.

## 6. JupiterOS-Specific Feature Gaps

The gap list is jupiterOS-shaped, not generic, and it doubles as the privilege design: every gap closes through a channel either unprivileged by design or pushed from a privileged incumbent the host already runs. The feature design IS the privilege design.

**systemd unit health (callisto, europa, kiosks).** The fleet's service inventory — mqtt, postgres, syncthing, headscale, the iscsi target, model-router, the kiosk power services — currently has no HA-side health surface at all. The D-Bus Subscribe() design from §5 delivers per-unit binary sensors with push semantics, and the watched-unit list generates from the same jupiterOS configuration that defines the launcher profiles [[interim-report-headless-privilege-ladder]]. The launcher backend's 1-second `systemctl is-active` polls move to the same channel — the push design eliminates the poll rather than tuning its interval.

**SMART/NVMe (europa; opt-in elsewhere).** The smartd hook design keeps smartd as the privileged detector and the agent as consumer [[interim-report-headless-privilege-ladder]]. This survives smartd's scheduling and self-test logic for free — displacing it would cost a capability grant and a polling loop to replace a daemon that already runs the fleet's chosen tests [[smart-archwiki]]. Callisto, which has repeatedly destroyed local NVMe drives and keeps none, has no customer for even the opt-in.

**Verified ZFS status (europa only).** The procfs-state plus zedlet two-channel design, with the premise correction that scopes it:callisto's only ZFS exposure is the iSCSI zvol with no local pool, where the backend's `detect()` already returns false — correct today [[interim-report-headless-privilege-ladder]] [[repo-map-ha-linux-agent]].

**Mesh/exit-node health (callisto, fleet visibility).** The tailscale `ipnstate` schema is the stable surface for peer and exit-node state — PeerStatus with HostName, Online, and ExitNodeStatus for the current exit node's liveness [[ipnstate-package-tailscalecomipnipnstate-go-packages]]. The gap is not the schema but that an unverified backend maps onto the host where the mesh hub runs; the schema is authoritative but explicitly unstable-by-policy across versions, so the parser is version-tolerant.

**Nix generation/boot health.** With switches now restarting user units disruptively, a booted-vs-current-generation sensor converts the new switch behaviour from a surprise into an observable — telling HA which hosts run a stale generation after a switch, cheap to read, fleet-relevant for the first time [[anyone-seeing-nixos-rebuild-switch-kick-you-out-to-gdm-andor-log-gpf-errors-spec]].

**Remote reboot/poweroff.** Present through the launcher and systemd backends [[repo-map-ha-linux-agent]]; what is missing is the idempotency contract — non-idempotent commands are exactly the class a replayed stale message would damage, which is part of why the persistent session is rejected in §2.

**Notifications, end to end.** notify.mqtt replaces the payload-hack button (HA 2024.5+; callisto's HA qualifies), one-way [[add-mqtt-notify-platform-by-jbouwh-pull-request-115653-home-assistantcore-github]] [[mqtt-notify-home-assistant]]. The kiosk last mile is the customer-display VFD overlay, not session-bus notifications. Actionable notifications have no Linux implementation anywhere, so they stop being priced into the decision; what little interactivity is needed is recoverable in-pattern — expose notification actions as buttons on the device, automations listening on those command topics.

**CPU performance knobs (kiosks).** The global boost switch lives at `/sys/devices/system/cpu/cpufreq/boost` (values 0/1, the recommended interface over the legacy per-policy AMD knob) — a natural governor/EPP sibling for the hardware backend's existing write path, gated by the same udev video-group pattern [[cpu-performance-scaling-the-linux-kernel-documentation]].

**The future desktop host class.** A niri-based desktop host is speculative (niri appears in zero jupiterOS host configurations), but its boundary is solved from source: the compositor's IPC socket is created as `niri.{wayland_socket_name}.{pid}.sock` under the user's runtime directory — filesystem-permission-gated, so a same-UID `User=io` system service reaches it by globbing, no session unit required — and the event-stream contract delivers complete state up-front followed by updates, so "your state can never 'desync'" [[serverrs]] [[ipc-niri-msg-niri]]. The system-service design covers a desktop host class without a shape change.

## 7. Testing a Hardware-Touching Daemon

A hardware-touching daemon resists testing because its inputs live in `/sys`, on D-Bus, and on the network; a gate is only a gate if it runs in CI, fails loudly, and cannot hang. The testing verdict rests on one general principle worth stating explicitly: web consensus optimises the generic case, and fleet ground truth overrides it. The corpus's four-source consensus names mosquitto-in-testcontainers as the right harness — `Mosquitto::default().start()`, broker URL from the mapped port, no authentication [[testcontainers-mosquitto-module]] [[mosquitto-in-testcontainers_modulesmosquitto-rust]]. The audited fleet facts refute it on arrival: no docker or podman on any jupiterOS host, no container runtime in any host configuration, and the Nix remote builders cannot expose container sockets inside build sandboxes at all — a testcontainers gate would be dead on arrival, not merely awkward [[interim-report-testing-gate-for-hardware-daemon]]. The harness therefore borrows testcontainers' hard-won lessons (URL always derived from the harness, never hardcoded; ready-probe before assertions; per-test exclusive broker) and swaps the spawn primitive for a subprocess.

**The sandbox-legality proof, from the Nix source itself.** Can a build-sandbox derivation even open a TCP socket pair? The Nix source answers at the syscall level: the builder performs `ioctl(SIOCSIFFLAGS)` on `lo` with `IFF_UP | IFF_LOOPBACK | IFF_RUNNING` inside a network namespace cloned for every non-fixed-output derivation, and the design comment states the builder "only has a private loopback interface" by intent — in-sandbox client-server pairs are upstream-blessed by construction [[local-derivation-goalcc]]. So the mosquitto-subprocess harness inside `craneLib.cargoTest` — bind a `TcpListener` to `127.0.0.1:0`, read the port, hand it to `mosquitto -p <port>` (the no-config default is anonymous and loopback-only), TCP-probe with a fail-fast, kill on Drop — needs no `__noChroot` escape and no VM [[mosquitto8-mosquitto-debian-unstable-debian-manpages]].

**The seven-step ladder, in dependency order** [[interim-report-testing-gate-for-hardware-daemon]]:

1. **Fix the clippy lint** (`map_or` → `is_some_and` at `backend-hardware:117`) so `nix flake check` can go green at all — the gate currently cannot gate.
2. **Wire `craneLib.cargoTest`** — this runs the existing eight pure tests for zero new code, the single cheapest reliability win available, and the moment the "8 tests, none running" posture ends.
3. **sysfs-root injection** — parameterise backend-hardware on a `PathBuf` root, build tempfile fixtures as synthetic `/sys` trees (std::fs is a module, not a mockable trait, so injection is the canonical path), and unit-test parsing plus warn-not-panic behaviour on unwritable nodes.
4. **Extract the `Agent::run()` seam** — config-injectable jitter bound and shutdown channel, so the lifecycle is testable in-process — the same refactor the supervisor requires, so ladder and reliability phase are one work item.
5. **The mosquitto-subprocess harness plus five defect-named regression tests**, with rumqttc itself as the observer client (the production stack, not a mock): `broker_restart_resubscribes_and_reasserts_availability` (kill -9 the broker, restart on the same port, publish a command, assert the agent handles it — the exact event `agent.rs:190` currently swallows — then assert a fresh subscriber reads retained "online"), `birth_message_triggers_discovery_republish` (jitter injectable to 0), `sigterm_publishes_offline_then_disconnects`, `hung_backend_doesnt_starve_sensors` (one backend whose poll never returns plus one healthy; assert the healthy one still publishes), and `decommission_zero_payload`. Every await wrapped in `tokio::time::timeout(5 s)` — a reliability gate that can hang is not a gate.
6. **A private dbus-daemon harness** (`--session --print-address` into a tempdir, exercising the zbus plumbing with the `pkgs.dbus` buildInput) — bounded honestly to plumbing tests, because a private bus hosts no `org.freedesktop.systemd1`.
7. **`runNixOSTest` for the module** — the out-of-tree invocation the NixOS manual documents, headless in QEMU where a full system bus and real systemd exist, cribbed from nixpkgs' own mosquitto test with a single node (the kiosk failure mode is local): enable the module, `wait_for_unit("ha-linux-agent.service")`, assert retained "online", then `machine.systemctl("restart mosquitto.service")` mid-test and assert re-subscribe and availability return — the module-level replay of the two root defects, and the gate that pins the §5 unit shape in one stroke [[nixos-manual]] [[mosquittonix]].

Two boundaries committed: real systemd signal tests belong to the NixOS test, because build sandboxes do not provide systemd; and a KVM availability check on the remote builders decides whether the VM gate runs per-check or nightly. The testcontainers notes stay filed for the day the project gains hosted CI with Docker — the test bodies are deliberately harness-agnostic below the spawn primitive.

## 8. Ordered Improvement Roadmap

The order is the argument: nothing else is observable while the agent is deaf, the fleet phase's module test plugs into the reliability phase's ladder, and the feature bar is now known precisely enough to spend features only where jupiterOS consumes them.

**Phase 0 — unblock the gate (days, no behaviour change).** Fix `backend-hardware:117`; add `craneLib.cargoTest`; `nix flake check` green with all eight tests executing for the first time. Remove or wire the dead `tls` knob at `config.rs:88`; document backend-hardware in the README; land the notify.mqtt discovery entity — strictly better than the payload-hack button, and independent of everything else [[test_notifypy]].

**Phase 1 — the ConnAck supervisor (one to two weeks, on rumqttc 0.24.0, no dependency churn).** ConnAck-driven re-subscribe and retained-availability re-assert on every connect; birth subscription with 0–30 s jitter (config-injectable to 0 for tests); channel capacity 0 with per-tick publish timeouts; per-backend and per-command task isolation with 5 s HTTP timeouts in backend-syncthing; SIGTERM offline-then-`disconnect()`; exponential reconnect backoff 1→60 s with ±20 % jitter so a broker restart cannot synchronise the fleet; `--decommission` zero-payload mode. Broker pairing on callisto: `persistence true` plus `persistence_location`, and a `$SYS` drop-counter check — hygiene at current scale, load-bearing the day entity counts grow. Steps 4 and 5 of the test ladder land here as the definition of done, with `broker_restart_resubscribes_and_reasserts_availability` as the named acceptance test. Exit criteria: the five regression tests green in `nix flake check`; a live kiosk survives `systemctl restart mosquitto` on callisto with entities recovering inside the keepalive window; the live presenting symptom is gone.

**Phase 2 — the fleet service model (one week, mostly Nix).** Rewrite the module to ship `systemd.services.ha-linux-agent` with `User=io`, `Restart=on-failure`, and the role switch; delete the user unit and the broken sysfs-chmod oneshot (fixing the false comment either way); the udev `GROUP="video"` rule plus io-in-video for backlight writes; the Environment block on lingered hosts only; sops wiring unchanged; rollout to europa (server role) and callisto (kiosk/minimal — the broker host runs its own agent deliberately rather than by omission); the runNixOSTest gating the module in both roles;

**Phase 3 — features, each with its privilege design settled (two to three weeks, severable).** The smartd-hook SMART bridge on europa; backend-zfs rewritten onto procfs state plus the zedlet bridge; the D-Bus Subscribe() unit-health backend replacing the launcher's 1-second is-active polls; KOBJ_CHANGE-driven backlight sync; version-tolerant headscale parsing; the nix generation/boot-health sensor; notify-to-VFD on the kiosks; the boost switch. Explicitly out of scope: the mobile_app actionable-notification contract (no Linux implementation exists to inherit) and the incumbents' sensor long tail that the fleet does not consume. Exit criteria: each feature carries at least one ladder-level test; none adds a capability, a sudo, or a root-owned write.

**Forward-looking.** Six to twelve months out, the agent stops being a kiosk accessory and becomes jupiterOS's observation plane: every host emitting unit health, storage health, and session state over one supervised MQTT lifecycle, with the module's role switch absorbing new host classes without code changes. Three developments would legitimately reopen settled questions and deserve standing watch: a merged-and-released rumqttc #1052 (which would let the raw ConnAck match become a reconnect signal and trigger the version bump — but would not change the design, since subscriptions stay application-owned); an incumbent shipping native select controls with state sync or a NixOS service module (go-hass-agent's zero-occurrence record through v14.15.1 is the current evidence against); and an end-to-end MQTT v5 decision (which loosens the clean-session reasoning and makes message expiry the stale-command cure — the v5 module already ships inside the pinned version) [[changelogmd]] [[interim-report-rumqttc-dependency-fitness]]. The deeper strategic point stands behind all of them: the fleet's deciding feature — declarative mutual-exclusion session control fused to systemd units — is one fleet's idiom, and no general-purpose agent will ever prioritise it. Owning twelve small crates whose worst defects are file:line-diagnosed is a better maintenance position than gluing that idiom onto an agent that cannot express it.

## Opinionated Synthesis

**ha-linux-agent is two bugs away from reliable, and the fix is fully specified; the rest is order.** The "never reliable" complaint decomposes into subscribe-once plus a swallowed ConnAck and availability-published-once — both located to lines, both mechanically explained by rumqttc's documented reconnect-without-re-subscribe contract, with even the in-pipeline upstream fix leaving subscription ownership where it belongs, in the application. Around those two bugs sit three default-shaped traps — the amnesiac broker, the capacity-64 stale queue, the timeout-less HTTP client that turns one hung daemon into fleet-wide lying telemetry — and the supervisor spec fixes all of it without dependency churn, with named regression tests, on the pinned version. The strongest objection — adopt go-hass-agent, express the launcher as configuration around it — fails on packaging and expressibility, but it stays live as named flip conditions: an incumbent NixOS service module plus select controls with state sync would reopen the generic-host arithmetic (not the launcher layer, inexpressible in a commands-file vocabulary); an end-to-end MQTT v5 decision would loosen the clean-session reasoning; a desktop host class is already covered by the same-UID socket boundary. Until one of those fires, the evidence points one way.
